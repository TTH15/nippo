# 車両点検・チェックイン/チェックアウト フロー 設計叩き台

ステータス: ドラフト（合意形成中）／最終更新: 2026-06-21
基盤: `docs/platform-design.md`（車両グローバルID §5）。連携: `parking-location-flow.md`, `notification-flow.md`。
関連方針: `構成A`。オドメーターOCRは**端末側**で完結（外部API不要）。

---

## 0. 目的

稼働前/稼働後に車両の**状態（傷・こすり）**と**走行距離**を記録し、損傷の責任所在とオイル交換管理に使う。返却（チェックアウト）時に点検＋オドメーター＋駐車位置を1本に束ね、運営へ通知。送信忘れを防ぐ。

---

## 1. 車両点検（状態写真）

- **目的**: 傷・こすりの検出と責任所在（誰の稼働中か）。
- **タイミング**: 稼働前（受取り基準）＋稼働後（新規損傷検出）。
- **撮影セット＋SVGガイド**: 標準セット（前後左右 / 角4箇所 / 8点 等）を用意し、**各角度にSVGのガイド絵を重ねて撮影誘導**。どのセットを使うかは **org選択**。
- **既定は必須／運営がスキップ可（ドライバー単位）**: 「この車両は不要」でなく「**この人は不要**」。→ **org設定でドライバー(membership)単位にスキップ/頻度低減**（毎日同車の信頼ドライバー向け）。車両単位の上書きは設けない。
- **UX原則**: スキップ設定は一覧で人ごとにトグル等、分かりにくくしない。
- **損傷判定**: 当面は運営の目視（稼働前/後を比較）。AI損傷検出は将来。

---

## 2. オドメーター OCR（端末側で完結）

- **目的**: 走行距離を保存 → 既存のオイル交換管理／日報メーターに接続。
- **OCRは端末側（ML Kit等）推奨**: 数字のみ・無料・オフライン・PIIなし。免許証OCR（保留）と異なり**今すぐ安全に実装可**。外部API課金不要。
- **写真も必ず保存**（OCRは利便、**写真が真実**。誤読は運営/ドライバーが写真を見て補正）。
- **承認→自動記録は現状踏襲**: 取得距離は既存の「承認→自動記録」パイプラインに乗せて車両走行距離を更新 → オイル交換アラート＋日報メーターへ流用（二重入力削減）。※接続先（オイル交換管理/日報メーター）は実装時に現行コードで確認。

## 3. データモデル

```sql
CREATE TABLE vehicle_inspections (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  vehicle_id uuid NOT NULL REFERENCES vehicles(id),
  org_id uuid NOT NULL,                 -- 使用org（貸与中は借用org）
  recorded_by uuid,                     -- membership
  phase text NOT NULL,                  -- 'pre' | 'post'
  work_date date,
  odometer_reading integer,             -- OCR結果（補正可）
  odometer_photo_path text,             -- 真実
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE vehicle_inspection_photos (
  inspection_id uuid NOT NULL REFERENCES vehicle_inspections(id),
  angle text NOT NULL,                  -- front/back/left/right or corner1..4 等
  photo_path text NOT NULL
);
CREATE INDEX ON vehicle_inspections (vehicle_id, created_at DESC);
```

## 4. 車両QR（1車両=1QR）と返却チェックアウト

### 4-1. QRは車両に1つだけ
- **1車両 = 1QR = vehicles.id**（platform-design §5 のグローバル一意IDをそのまま符号化）。業務開始（乗車）・返却・会社間貸与の引き取り・将来追加機能も**全てこの1つ**。
- スキャンの意味は**アプリが文脈で判断**（チェックイン中=乗車開始、チェックアウト中=返却、別org=貸与引き取り）。QRを増やさない＝わかりやすい。
- **QRラベルはorg画面からいつでもDL**: 1車両ごとに **QR＋車番＋会社名** を載せた **ベクターPDF＋画像** を生成・再ダウンロード可（紛失/破損時に再印刷）。= 「運営画面からQR配布」モデルの実体。

### 4-2. 返却（チェックアウト）シーケンスと送信忘れ防止
返却時に **稼働後点検 → オドメーター → 駐車位置（`parking-location-flow.md`）→ 運営通知** を1本のチェックアウトに束ねる。IoTに頼らず**ソフトの強制力**で防ぐ:
1. **チェックアウトを必須ゲート**: 返却完了まで当日の勤務を「完了」にできない（シフトがopenのまま）。完了は**車両QRスキャン**で確定。
2. **リマインド→エスカレーション**: 時刻まで未返却ならドライバーへpush、なお未了なら運営へ通知（通知システム流用）。
3. **運営ダッシュボードに「未返却」一覧**。
4. **日報提出に統合**して飛ばせなくする。
- 位置は **GPS＋写真**（屋内精度は写真/メモで補完）。鍵ボックスや場所QRで物理強制・屋内精度が欲しい会社は**任意アドオン**（標準ではない）。

## 5. Storage 戦略（点検写真が最大の増加要因）

- 試算: 圧縮後1枚~300KB、1稼働3〜5MB/人 → **月3〜6GB/社（50人）**。超過単価は安い(~$0.021/GB/月)が**削除しないと無限増**。
- **保存期間を各社設定にして料金差（ティア化: 3/6/12ヶ月）**。期限超過は自動削除 → 各社が定常状態で頭打ち。コスト制御＋課金レバー。
- **端末側で圧縮してアップロード**（長辺上限・JPEG品質）。
- 点検写真は「書いて滅多に読まない」性質 → 高コスト化したら**R2等の安価ストレージへ退避**（egress無料・~$0.015/GB）。まずSupabase＋圧縮＋保存期間でstart。

---

## 6. org設定（各要素は独立）

- 点検写真・オドメーター・駐車位置は **各々独立に 必須/任意/スキップ**（例: 点検写真はスキップ可、オドメーターと位置は必須）。
- 撮影セット選択、スキップのドライバー単位設定、リマインド時刻、保存期間（料金ティア）も org 設定。

---

## 7. テナント／貸借

- `org_id` は使用org（貸与中は借用org）。点検・オドメーターも借用org文脈で記録。
- **所有org（owner_org_id）には走行距離・点検（状態写真）をフル開示**（自社資産の状態管理のため）。ただし**借用側ドライバーの個人情報はスコープ内に留める**（見せるのは車両の状態であって人ではない）。位置と同じ貸借スコープ拡張（platform-design §5）。

## 8. エッジケース

| ケース | 挙動（案） |
|---|---|
| OCR誤読 | 写真を正として運営/ドライバーが手修正 |
| 点検スキップ設定中（その人） | 写真省略、オドメーター/位置は別途要否に従う |
| 稼働後点検で新規傷発見 | 稼働前と比較できるよう両phase保持。損傷フラグ＋運営通知（将来） |
| 未返却のまま放置 | エスカレーション（§4-2） |
| 貸与車両 | org_id=借用org。所有orgは距離・点検・位置を閲覧（人は除く） |
