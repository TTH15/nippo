### 教訓: 保存形式を変えたら「既存データの移行」まででワンセット（2026-07-22）
車両画像を data URL（base64・DB直）→ Supabase Storage に変えたが、**コードだけ直して
既存6件を変換していなかった**。読み出しが「data URL ならそのまま返す」二重対応だったため
画面は正常に見え、**遅いという症状でしか気づけなかった**（一覧が毎回 3.7MB を DB→サーバー→
ブラウザと2回運んでいた）。
- 移行スクリプト `apps/web/src/scripts/backfill-vehicle-images.ts`（✅ 2026-07-22 実行済み・6件成功）。
  確認モード（引数なし）→ `--apply` の2段。アップロード成功後に DB を書き換える順序で、
  途中失敗しても画像を失わない。移行済みはスキップ＝冪等。
- **再発防止**: 一覧 API の `select("*")` を列指定に変更済み。列を明示しておけば、
  将来また data URL が紛れ込んでも一覧レスポンスは太らない。
- 同種の未移行が残っていないか: **請求書添付（`invoice_documents.payload.attachments[].dataUrl`）も
  同じ二重対応のまま**。新規保存は Storage へ行くが、既存データは data URL のはず。要確認。

### H. お金の「確定（締め）」の設計 ★2026-07-22 に課題として明確化
> 正本: `docs/money-handling-current.md` §9。
> 車両回収を月次確定にしようとして、**単独では解けない**ことが判明した。

- 現状、お金の数値は**どれも「その時点の集計結果」でしかなく確定していない**。
  `payrolls` 未使用も `extraOutsourcing` の手入力も同じ根っこ。
- **確定の起点は実入出金**（元請けの入金 → 自社口座からの振込 → 会計を締める）。
  日報でも集計でもない。車両回収だけ別の締めを持たせるとズレが増えるだけ。
- **車載QR の本運用まで使用車両を実績として確定できない**（現状は自己申告）。
  日額リース回収の根拠自体が未確定なので、金額を確定させられない。
- [ ] 着手条件: ①車載QR 本運用（`qr_flow.md` / `vehicle-session-flow.md`）②入出金突合の仕組み
- [ ] 給与・請求・車両回収を**同じ「締め」に乗せる**設計（単発で確定テーブルを足さない）
- ※ 検討過程で書いた migration 114（`vehicle_daily_lease_closed`）は**削除した**。
  未適用の migration を残すと `apply-migrations.ts` が新環境で必ず適用してしまうため。
  案の骨子は `money-handling-current.md` §9 に記録済み。
- ✅ 当面の実害（回収額の過少計上）は解消: PostgREST の1000行打ち切りに気づかず
  `.limit(100000)` を信じていた → `fetchAllRows` 化（2026-07-22）。
  ※同じ落とし穴の注意書きと対策関数は `pagination.ts` に既にあった＝**使い忘れ**。

### K. 地図 → 配車作戦盤（2026-08-03 方針確定）

admin の /admin/map。Mapbox Standard・3Dモデル（model レイヤー）・拠点ピン（map_places）まで実装済み。
「可視化β」から**配車の作戦盤（みんなで見ながら車を動かして話し合う場）**へ段階的に育てる（ユーザー合意 2026-08-03）:

- [ ] **Stage 0: 実データ化** — mobile P2 バックグラウンド位置トラッキング＋プレート吹き出しの located 接続（下の既存項目）。
- [ ] **Stage 1: 共有ビュー** — 同じ地図に複数人が入り、参加者の在席（presence）・カーソル・視点追従（フォロー）を
      Supabase Realtime broadcast で同期。通話は当面 LINE 等で補完（リアルタイム通話インフラは持たない）。
- [ ] **Stage 0.5: 位置の時系列化＋ドラッグ配置**（GPS 不要・今すぐ着手可能・2026-08-06 設計）—
      `vehicle_positions`（出どころ付きの時系列）を新設し、地図上でプレートをドラッグして
      `source='manual'` を**追記**できるようにする。GPS が入ったら `source='gps'` を流すだけで UI は不変。
      設計: [docs/design/map-board.md](design/map-board.md)
- [ ] **Stage 0.6: 履歴スクラブ** — 日付＋タイムラインで「何月何日◯時の位置」を as-of で引く（GPS 不要）。
- [ ] **Stage 2: what-if シミュレーション** — シフトの割当ドラフトを地図上でドラッグ、時間スライダーで1日を再生。
      ドラフトは下書きテーブル（`sim_scenarios` / `sim_moves`＝実績とは別）に置き、確定でシフトへ反映。
- [ ] **Stage 2b: 動画エクスポート** — 再生をそのまま録画して書き出す
      （案A: `canvas.captureStream` + MediaRecorder で webm。サーバーレンダリングは必要になってから）。
- [ ] **Stage 3: AI 合流** — 音声メモ→制約の構造化（driver_constraints）と AI 配車提案の出力先をこの作戦盤にする
      （AI は叩き台を置き、人がドラッグで直して確定）。

- [ ] **ナンバープレートの数字・かなを SVG グリフ化**（本人希望: 余裕がある時に一気に作る）。
      現状は Web フォント頼みで実車の書体（トレーラー書体）と乖離。プレート吹き出し
      （地図 VehicleLabel）と VehiclePlate コンポーネント共通の資産として作る。
- [x] 車両 3D モデル: Kenney Car Kit の delivery van（CC0・軽バン同寸）に差し替え済み（2026-07-30）。
      （将来: 車両写真から image-to-3D API で自動生成する構想は継続）。
- [x] **プレート吹き出し・3Dモデルを実データに接続 ✅ 2026-08-07**（ハードコードのデモ車両10台を撤去。
      位置が記録された車両にナンバー吹き出しと 3D モデルを出す。状態は稼働セッションから導出）。
- [ ] 車両撮影（ガイド枠つき4方向）→ 差分での傷検出の企画（打刻フローへの組み込み想定・
      3D生成とは独立の CV タスクとして設計する）。
