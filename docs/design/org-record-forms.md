# org別の記録・報告フォーム基盤

更新: 2026-08-31
状態: 共通UI・本番用API・永続化を実装済み。migration 154を開発DBへ適用し、受け入れ検証済み。
本番DB適用・公開は未実施。リリース手順は `docs/deployment/record-forms.md`。

## 目的

案件、日払い、その他の運営メモ、ドライバーからの諸報告を、共通のフォーム定義と記録基盤で扱う。
「案件」「日払い」は製品に固定した特別画面ではなく、初期テンプレートとして提供する。
orgはテンプレートをコピーして、名称・項目・選択肢・必須条件・公開範囲を変更できる。対応状況は共通の3状態を有効・無効にする。

カテゴリは整理のための分類、フォームは入力項目と権限を持つ記録の種類とする。
カテゴリ変更によって暗黙に閲覧権限が変わらない設計にする。

## 人の区別

- 記入者: システムへ入力した認証ユーザー。自動保存する監査情報であり、手入力で変更できない。
- 報告者: 事実を報告した人。通常は記入者と同じ。代理入力・転記時だけ別人を指定できる。
- 対象者: 記録が誰についてのものか。案件の当事者、日払いの支払先など。報告者とは別の意味。

フォームの項目としてメンバー選択を追加でき、表示名は「対象ドライバー」「支払先」等へ変更可能。
対象者を複数にする、未登録者の名前を許可する等は明示的な設定とする。
本人の記録へのアクセス判定は自由記入の名前ではなく、認証済みの記入者ID・対象者ID等で行う。
フォームに対象者が不要なら置かない。記入者・報告者を一律に重複入力させない。

## 既存資産

- `server/reportKinds/fields.ts`: 短文、長文、数値、単一/複数選択、日付、時刻、真偽、添付の定義・検証。
- `@repo/core/types`: Web/モバイル共有のReportField等。
- `/admin/report-kinds`: フォームビルダーと種類設定。
- `server/reportKinds/answers.ts`: 回答の表示と既存固定カラムとの橋渡し。
- 今回の対応記録: 訂正・追記履歴、競合検出、一覧・検索、DatePicker/CustomSelectを使う画面。

既存の `loadReportKinds` と管理APIはorgによる絞り込みを行っていない。
これをそのままorg別の編集基盤には使わない。現状の共有定義の利用状況を確認し、共通テンプレートと
org所有のフォームを分離する。既存報告は固定カラムと回答JSONの混在もあるため、一括置換しない。

## orgが設定すること

| 設定 | 例 |
|---|---|
| 種類 | 案件報告、日払い記録、備品購入、引き継ぎメモ |
| 入力項目 | 型、表示名、並び順、必須、選択肢、補足、入力制約 |
| 関連先 | メンバー、車両、コース。任意または必須 |
| 対応状況 | 使う／使わない。使う場合は未対応・対応中・解決済みの共通3状態。未対応から開始し、解決済みが対応終了 |
| 一覧 | 表示列、件名に使う項目、日付・対象者・状態などの絞り込み |
| 入力対象 | 運営のみ、特定ロール、ドライバー本人からの提出 |
| 回答の閲覧 | 指定ロール、記入者本人、対象者本人などを別々に設定 |
| 更新 | 新規作成、本人の修正、全件編集、状態変更の権限 |

フォームごとに新しい `can_view_xxx` をコードへ追加する方式は採らない。
フォーム定義を管理する能力と、各フォームの記録にアクセスするロール別権限を分ける。
設定者が自分の権限外のフォームを編集・公開できないよう、管理権限の範囲も検証する。

## 「ドライバーに公開」の分解

単一の公開スイッチではなく、少なくとも次を別々に制御する。

1. ドライバーがフォームを見つけて提出できるか。
2. 自分の提出した記録を読める・修正できるか。
3. 自分を対象とする記録を読めるか（自分への支払記録等）。
4. 運営が付けた内部メモ・履歴を読めるか。

フォームの公開は回答一覧の全員公開を意味しない。初期値は非公開・最小権限。
運営専用の追記は提出内容と区別し、本人向けAPIから本文・履歴・検索結果・添付URLを漏らさない。
初期版は複雑な項目別権限を避け、「提出内容」と「運営専用追記」の2領域で始める案。
過去分へ閲覧権限を広げる変更は、対象件数・影響範囲を表示して明示的に適用する。

## 固定して残すもの

- org境界、認証、監査情報、アクセス制御、添付ファイルの安全性。
- 項目型ごとの検証（数値・日付・メンバー参照など）。表示名に依存した判定はしない。
- フォームの公開版・項目ID・選択肢ID。名前変更でデータの意味を変えない。
- 記録保存時のフォーム版。項目廃止・選択肢の名称変更後も当時の回答が読める。
- 車両距離更新や経費処理などの配送固有の処理。明示的な連携設定でのみ実行する。

「金額」という項目を作っただけでは会計に反映しない。日払いテンプレートの連携はなし。
日報からの報酬計算・シフト・車両稼働そのものを、今回すべて汎用フォームへ置き換えることはしない。
任意コードやSQLをorgが実行できる機能は設けない。

## 画面構成案

- 記録・報告: 日常業務の入口。利用権限のある種類を選び、一覧・入力・詳細・追記を扱う。フォームの追加・設定ボタンは置かない。
- フォーム管理: 管理者用の独立した入口。フォーム一覧から対象を選び、「○○の設定」で項目、一覧表示、公開・権限を設定する。フォーム追加もこの入口に集約する。現在の「報告種別」の統合先とする。
- ドライバーの報告画面: 提出を許可されたフォームだけを表示する。

左メニューは「記録・報告」と「管理者設定 > フォーム管理」に分け、現在位置を強調する。
記録の入力・詳細からは「○○の一覧に戻る」、フォーム追加・設定からは「フォーム一覧に戻る」で親へ戻す。
記録側で選択中の種類と設定対象のフォームは独立して保持する。左メニュー経由の移動でも未保存の変更を破棄する前に確認する。
新しいフォームはひな形選択時には登録せず、「フォームを作成」の確定後に一覧へ追加する。途中で戻った場合は未完成のフォームを残さない。

頻繁に使う種類はショートカットとして置けるが、種類ごとに専用ページを実装する必要はない。
種類作成画面には案件・日払い等のテンプレートを用意し、最初から全項目を作らせない。

## 移行手順

1. 設計とプレビューを共通フォーム前提に更新。今回のmigration 153は適用せず保留する。
2. org所有のフォーム、公開版、ロール別アクセス、記録・履歴の保存を実装する。
3. 案件・日払いを初期テンプレートとして載せ、org内で変更可能にする。
4. 既存報告種別を、利用中の組織と過去回答への参照を確認して段階的に移行する。
5. 車両距離・経費の既存連携、モバイル、添付、本人向け閲覧を回帰検証してから入口を統合する。

固定版の画面・API・専用権限は汎用版へ置換済み。未適用153は `docs/design/archive/` へ移動した。
現行の諸報告・報告種別、会計、シフトの保存処理は変更しない。


## 2026-08-30 プレビュー実装

- ソース: `apps/web/src/app/preview/records/`。Next.jsでは `/preview/records`、今回のアプリ内ブラウザでは同じコンポーネントを `http://127.0.0.1:3187/` で表示。
- 認証・DB・会計・実際のorg設定には接続しない。Reactの画面内状態だけに保持し、リロードで初期データへ戻る。
- 案件、日払い、引き継ぎメモの3テンプレート。コピーして新しいフォームを追加でき、新規フォームは管理者だけに公開する。
- 9形式の入力項目（短文・長文・数値・単一/複数選択・日付・時刻・真偽・メンバー）、追加・削除・複製・ハンドルでのドラッグ並べ替え、必須・選択肢・数値範囲・単位・一覧表示を編集。
- 件名/日付/対象者に使う項目を設定。対応状況はフォームごとにオン・オフのみを設定し、未対応・対応中・解決済みを共通定義として使用する。状態の追加・名称編集・完了判定の設定は設けない。解決済みでも編集・追記できる。案件はオン、日払い・メモはオフで開始する。オフへの変更は新規記録から適用し、登録済みの対応状況は保存時の定義で保持する。既存のDatePickerとCustomSelectを再利用。
- 編集画面はWYSIWYGの一列構成。項目名はカード上部で直接編集し、入力欄もカード内に表示。選択肢はその場で編集。独立したプレビューは置かず、試し入力は保存しない。設定適用は確認後で、既存記録は登録時の定義を保持する。
- 一覧の表示項目は「一覧・状態」タブの「記録の一覧に表示する項目」で設定。件名は見出しとして表示し、その下に載せる回答を選ぶ。実際の一覧と共通の部品で表示例を即時更新する。オフでも詳細・検索対象・必須条件・権限は変えない。既存記録の件名は登録時の版を保持する。
- 入力形式は共通FieldTypeSelectのアイコン・名称・説明で選択。新規項目は名前から形式を自動選択し、450msの入力待ち・IME変換中の停止・元に戻す・ON/OFFを実装。既存/手動/複製の形式を保護し、選択肢編集や数値制約の指定でも手動へ移行する。
- 推定はブラウザ内の規則のみ（支払日→日付、金額→数値等）。外部AIへの送信なし。Google Formsの広い文章理解や回答候補生成までは対象外。`typeSelection`はフォーム定義に保存する編集メタデータ。
- 単一選択はラジオ、複数選択はチェックボックスで回答する。「その他」は`allowOther`で定義し、選択時に自由入力を表示・必須化（最大500文字）。専用の追加/削除操作を設け、回答は選択肢IDと自由入力を分けて保持する。表示/検索/編集は保存時の定義で処理する。案件種別・支払方法の初期テンプレートも自由入力付きに変更。
- 参考：[Google Formsの質問形式](https://support.google.com/docs/answer/7322334?hl=en)、[質問形式の推定に関するGoogleの説明](https://workspace.google.com/blog/product-announcements/five-new-ways-reach-your-goals-faster-g-suite)。外観はハコ虎の配色・共通部品を維持。
- 記録の追加・編集・追記・検索・期間/状態絞り込み。記入者は自動、報告者は代理報告時だけ指定。
- 管理者/運営担当/経理担当/ドライバーの表示を切替。フォームの権限・本人提出/対象者閲覧設定が画面表示に反映され、ドライバーには内部追記を表示しない。
- これらは架空データ上のUIシミュレーションであり、サーバーの認可・版管理・監査を実装したものではない。
- 添付・実際のorg別ロール・実名簿・公開版のDB保存・既存報告種別の移行は次段階。シフトメモは統合しない。


## 2026-08-31 本番用実装

- 日常業務 `/admin/records`、管理者設定 `/admin/record-forms`、本人向け `/me/records`。マイページから本人向け画面へ移動する。
- `lib/recordForms` を本番とプレビューで共用。プレビューの架空ロール・メンバーは `app/preview/records` のみが供給する。本番のフォーム・回答は空から開始する。
- ロールの `can_access_records` は画面の入口のみ。フォーム内の実在ロールIDに `none / view / edit` を設定する。フォーム設定時に入口権限を補うが、閲覧／編集は毎回フォームの現在設定で再判定する。
- `can_manage_record_forms`（`can_manage_org_settings` に含意）はフォーム設定と全フォームの記録管理を許可。会計担当・運営担当には自動公開しない。
- 本人向けの提出・記入者本人閲覧／編集・対象者本人閲覧は独立設定。本人画面のメンバー候補は本人のみ。本人から報告者の偽装、対応状況変更、内部メモの書き込みはできない。
- APIはJWT内のorg・roleを正本にしない。activeなdrivers／organizationsと現在ロールをDBから取得し、全クエリをorgとform、必要に応じrecordで限定する。
- 40項目・100選択肢・入力512KB上限。数値・日付・時刻・メンバー・「その他」等はサーバーで検証する。添付・外部送信・会計連動なし。
- フォーム版・記録版は別々に管理。古いフォーム画面からの保存、同時編集は409。新規作成の再送には同じUUIDを使用し、二重登録を拒否する。通信失敗時は入力を維持する。
- 対応・追記は詳細に直近100件まで表示。全変更のスナップショットはDBに保存（履歴の全件閲覧／差分UI・添付・モバイルアプリへの接続は後続）。
- 設定変更後も登録時の項目・状態定義・氏名を保持する。無効化されたメンバーの既存回答は、値を変えない場合のみ編集で維持できる。
