# 写真を起点にした日報とメーター記録

> **現在の順序（2026/09/26）**: 日報は稼働中から先に送れる。退勤時には点検4方向を保存し、駐車時にメーター写真を撮る。以下の2026/09/23〜24の「終了後に日報と駐車を必須2項目として送る」節は当時の案として残す。現在のフローは[開始・終了撮影と駐車](mobile-capture-parking-lifecycle-2026-09.md)を参照する。

2026/09/23。既存Webの `SubmitPageClientV2.tsx`、`ReportSourceImageField` と実アプリの `DailyReportForm` / `ReportSourceImagePicker` を参照。画面確認は本番API・DB・外部AIから隔離する。

## 今回の方針

- ドライバーは走行距離・燃料残量の数字を読んだり転記したりしない。出退勤の確認画面と日報からメーター入力を削除する。写真は原本として保存する。
- 日報は既存Webのコース・便・報告単位・項目定義を使う。コースごとの先頭に「配完表・実績の画像」を置き、その下に高さ56px以上・20px文字の入力欄を縦に並べる。
- 画像の値は選択したコース・便だけへ入れる。同じunitを持つ別便へ流用しない。未知/未読は0を補完しない。日報の請求・報酬への影響は既存の確認方針に従う。
- メーター写真はフラッシュ初期オフ、標準レンズ、速度計・燃料計・オドメーターを含む計器盤全体の外周ガイド。表示を点灯し、反射を避けるよう短く案内。必要に応じフラッシュ自動へ切替可能。
- 確認画面は写真だけを確認し、未検証の端末OCRを確定走行距離として送らない。反射・ぶれの実判定器は未接続。プレビューの警告は架空の品質結果。

## 稼働終了と駐車の順序（ユーザー承認済み）

2026/09/24更新: 稼働時間は終了操作で止め、その後は「終了の手続き」に日報と駐車記録の必須2項目を表示する。**両方の送信成功後にだけ「お疲れ様でした」と次回予定**へ移る。日報先行も駐車先行も可能。駐車先行なら送信後そのまま日報へ進む。まだ駐車できない場合は日報だけ先に送れるが、駐車記録の未完了表示を残す。GPSの取得失敗だけで完了を止めず、写真が受理された場合は運営の位置確認へ分離する。稼働時間の終点と、車両の返却時刻・返却距離は別に保存する。

ユーザーは「先に稼働終了・日報、駐車後に写真」を選択済み。**Expo Goとブラウザの隔離プレビューに順序変更を実装**。通常アプリの既存WorkScreenは保存API未対応のため、終了メーターの必須撮影をまだ維持する。本番経路を切り替える前に以下を実装する。

1. `ended_at` と `parked_at`、`end_odometer` と `return_odometer` の意味を分離。後で撮影した返却距離を稼働終了距離へ遡及コピーしない。返却距離は次の利用開始距離と照合できる。
2. 既存の駐車記録を本人用の独立APIから保存できるようにする。session/vehicle/driver/orgと写真用途を検証し、日報に紐付けなくても移動のみで提出可能にする。
3. 駐車確認→車内で点灯中にメーター撮影→車外の駐車場所撮影→送信。車体4方向の終了点検タイミングもこの時点で整合させる。
4. 駐車写真が後回しでも稼働終了・日報を巻き戻さない。GPS失敗は位置未確定として写真を保存し、運営地図に架空の座標を打たない。
5. 再起動後も未完了タスクを復元。通知は補助で、ホームから再開できる。終了後のmotion/位置追跡は同意・停止条件を別途確定する。常時追跡を無断で開始しない。

## バックグラウンド解析

ローカル実装: `apps/web/src/server/ai/meterReading.ts`。既存の `getAnthropic()` と構造化出力を再利用。モデルは `HAKOTORA_METER_AI_MODEL` で明示指定し、未設定では呼ばない。モデル選定・実写真での精度評価・外部送信の開始は未実施。

- `odometerKm`: ODO総走行距離のみ。TRIP、航続距離、燃費、単位不明を採用しない。
- `fuelFraction`: メーターのE〜Fに対する表示割合。実リットル数・給油量とは別物。給油量や支払額はレシート画像を別用途で読む。
- `issues`: 反射/ぶれ/暗さ/見切れ/不確実/別画像など。読めない値はnull。形式・範囲・終了理由もサーバーで検証する。
- `candidate` は未確定の読取候補。初期運用は全件を運営確認へ。モデル自身のconfidenceだけで自動採用しない。実写真の評価後、前回ODO、車両・時刻、増分、複数画像の一致等を含む採用基準を決める。
- ドライバーへの復帰は「角度を変えて撮り直す」。再撮影困難・再失敗は運営確認へ回し、数字の転記を要求しない。通信エラーと写真不良を区別し、通信エラーに再撮影を要求しない。

### 永続ジョブと保存（未接続）

1. 写真保存と認可済みセッションへの紐付けが確定した時点でoutbox/jobを永続登録。HTTP応答後のfire-and-forgetだけでは実装しない。
2. jobにはorg/driver/vehicle/session、撮影用途、原本ID・hash・revision、撮影/受信時刻、model/promptVersion、状態、attempt/nextRun/leaseを保存。`sourceImageId + revision + promptVersion` の一意キーで再送を抑止。
3. workerがleaseを取得して非公開原本を読み、LLMを呼ぶ。鍵はサーバーのみ。元画像URLを任意に受け付けない。画像の内容検証、会社・本人・用途の認可はモデル呼出前に行う。
4. queued → processing → candidate/needs_review、通信失敗は上限付き再試行、上限後failed。撮り直しで旧revisionをsupersededにし、遅れて完了した解析や次の利用者の値で上書きしない。
5. 読取結果と採用値を別保存し、誰がどの原本から何を採用したか記録。既存の確定値・手修正・承認済み日報を後着のAIで上書きしない。
6. 運営Web/Baseへ原本・候補・理由・採用操作を提供。写真期限/削除時はジョブと派生画像も後片付け。画像に記載された指示を実行しない。

DB migration、worker起動経路、再撮影通知、運営確認画面、地図連携は後続。今回の読取関数は呼出元をつないでおらず、AIや本番に写真は送っていない。

## 日報APIの互換性と公開順

`reports/v2` はmeterValueの省略を「同じ車両なら既存値を維持（車両訂正時は旧車両の値を解除）」、数値/nullの明示を従来の更新として扱う。モバイルは省略する。新規日報は解析待ちのnull。Web版の既存入力要件は今回変更していない。

**APIの省略対応を先に公開し、その後モバイルを配布する。** 旧APIに新モバイルを向けると省略がnullに変換されるため同時配布可と扱わない。読み取り未接続中は写真だけ保存され、走行距離に依存する整備計算等へ自動反映されない。

## 画像入力の拡張順

1. 配完表・実績スクリーンショット: 既存の原本アップロード＋端末テンプレートOCRを再利用。コース/便を限定し、日付・重複・合計の検算を維持する。
2. メーター: 写真保存後のLLM解析、運営確認、確定値更新。日報の送信成功と解析完了を分離する。
3. 給油レシート: 日付/給油量/金額/車両との対応、重複や支払者を確認して経費へ。燃料計の針だけで給油実績を生成しない。
4. 未対応形式の日報画像: 対象course/cycle/unit/fieldと照合できるLLM抽出を追加。全項目の人手照合を常態化せず、不確実な項目だけ運営へ。画像があっても誤読は起こり得るため原本・検算・訂正履歴を残す。

### 即時確認と後処理の責務

1. 停車した状態で、メーター照明をつけ、全体を撮影。フラッシュ初期オフ。暗い時に無条件で発光させず、反射を避ける。撮影時の自動合格表示は今回実装しない。
2. 撮影直後の静止画で「走行距離」「燃料計」を個別に確認。全画面の白飛び率だけでは判定しない。両領域の解像度、ブレ、遮蔽、反射、暗さ、枠外、ODO/TRIP識別を評価する。針式・液晶バー式・機械式桁の違いを含めて検証する。ガイド形状は補助情報であり、領域がそこにあると断定しない。
3. 反射は角度/フラッシュ、ブレは固定/ピント、欠けは引いて撮影、暗さは計器照明、TRIPのみならODOへの切替を短く案内。数値の転記は求めない。
4. 未接続・通信失敗・形式不正・6秒タイムアウトは `unavailable`。合格扱いにせず写真を保持し、目視で確認して使うか撮り直すかを選択。判定中は確定不可。警告時の続行も「目視で確認して使う」と明示し、運営確認を前提とする。後続APIではこの例外理由と写真revisionを必ず保存する。
5. 非同期の詳細読取は既存設計の `meterReading.ts` と永続ジョブでODO値/燃料割合を候補化し、運営が承認。即時の「写り確認済み」は、数値の正しさや運営承認を意味しない。
