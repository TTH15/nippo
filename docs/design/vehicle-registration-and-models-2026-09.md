# 車検証からの車両登録と型式別3Dモデル

2026-09-14 調査・提案。ユーザーの「GLBが増えている。型式の登録が必要か／車検証写真から車両登録したい」という相談に対する実装前の整理。以下は相談時点の記録であり、同日後半の実装状況は末尾と [実装・プレビュー手順](../development/vehicle-registration-preview.md) を参照。

## 提案

型式は任意のままにし、分かる車から型式に合う3Dを表示する。新規登録は「車検証を読み取る → 内容を確認・修正 → 登録」の入口を既存画面へ足す。従来の手入力も維持する。

必要なのは「全車の型式入力を必須にすること」ではなく、「車両の識別情報」と「表示するGLB」の対応表。同じ型式でも前後期・ルーフ・外観仕様が複数ある場合は候補を表示し、利用者が見た目を確認できるようにする。初度検査年月だけで製造年や外観を断定しない。

## 現状の実装で確認できたこと

- `supabase/migrations/128_vehicle_model_code.sql` に `vehicles.model_code` の追加定義がある。今回、本番DBの適用状態は再照会していない。
- 車両登録・編集画面には任意の型式選択と自由入力があり、APIも `modelCode` を受け取る。新しい入力欄を一から作る必要はない。
- `apps/web/src/lib/vehicleModels.ts` は現状3車種のGLBを提供する。DA17V/DA64Vはともに `every`、S700V/S321Vはともに `hijet` になる。2026-09-06の「当面は車種単位」の方針によるもの。
- `resolveModelKey` は型式をtrim・大文字化した後に完全一致で探す。車検証の接頭辞を含む型式や全角入力を照合する正規化はない。
- `mapModelKeyForVehicle` は保存済み `model_key` を優先し、型式を受け取らない。対応表だけ増やしても既存の汎用キーで表示が固定されるため、解決規則の変更も必要。
- ナンバープレートGLBもモデルIDごとの雛形を使う。車体の切替と同時に、対応する前後プレートの形状・位置を揃える必要がある。
- 調査したWebの車両登録API・画面に、車検証写真から項目を抽出する実装は見当たらなかった。初度検査年月・車台番号の保存欄も別途設計が必要。
- 本番画面の再利用元は `apps/web/src/app/(admin)/admin/(resource)/vehicles/page.tsx`。隔離fixtureは `scripts/previews/fixtures/vehicles.ts` に存在する。

## GLB制作台帳との照合

制作元 `~/Developer/assets/keivan-3d/catalog/roadmap.json` は現在20仕様を登録している。READMEの一部は16/19仕様の記録が残っているため、現行台帳と各 `model/asset-manifest.json` を確認した。全20仕様の台帳状態は `in-progress`。以下は取り込み候補であり、本番採用済み・品質確認済みの一覧ではない。

| 制作元の対象 | 仕様数 | ハコ虎側で必要な区別 |
|---|---:|---|
| エブリイ DA52V系・DA62V・DA64V・DA17V・DA18V | 5 | 世代ごとの独立キー |
| エブリイ 黒ボンネット写真仕様 | 1 | 型式未確定。自動照合から外し、外観選択の候補として扱う |
| ハイゼット S300系前期・S700系 | 2 | 世代・前期顔を区別。写真個体の型式候補を確定値にしない |
| クリッパー U71V/U72V系・DR64V・DR17V | 3 | 古いU系までエブリイへ一括変換しない |
| ミニキャブ U6系・DS64V・DS17V | 3 | U6系とスズキOEMを区別 |
| スクラム DG64V・DG17V | 2 | 世代別・エンブレム等の外観差分 |
| アクティ HH5 | 1 | 制作元の現行版を検証して更新 |
| アトレー S220G/S230G候補 | 1 | 貨物V系と乗用G系を混同しない。登録型式は未確定 |
| サンバー S321B・ピクシス S321M | 2 | S300前期顔のOEM仕様。別世代へ一括流用しない |

取り込む版はmanifestが指定するファイルとハッシュで固定する。最大連番のGLBを自動選択しない。まず現在の3車種とDA17Vなど世代差の明確な組合せで接続を検証し、その後にOEM・外観差分へ広げる。

## 型式と表示モデルの扱い

1. 車検証に書かれた型式は接頭辞を含めて保持する。照合用に全半角・大文字小文字・ハイフン等を整えるが、原表記を失わない保存方法を決める。
2. 照合用の基本型式を取り出す（例示入力 `HBD-DA17V` → `DA17V`）。単純な部分一致でワゴン/バン・EV・別世代を混ぜない。未知の接頭辞や「改」は確認対象とする。
3. メーカーと型式から車種・世代の候補を求める。書類の「車名」をそのまま通称車種名にしない。メーカー不一致は候補の自動確定を止める。
4. 候補が1つなら推奨モデルを表示し、複数なら外観を選ぶ。型式が不明なら従来の車種別代替表示で登録できるようにする。
5. 既存 `model_key` は自動選択と手動指定を区別していないため、手動の外観指定を表す情報を設計する。旧来の汎用キーは型式照合を妨げない一方、明示した外観選択は上書きしない。
6. 地図・編集時の3Dプレビュー・サーバーのプレート生成が、同じ解決結果とモデル版を使う。切替時は車体だけ新世代でプレートが旧世代、という組合せを配信しない。非同期生成中・失敗時の表示と再試行を決める。

## 写真からの登録フロー

入口の文言は「車検証を読み取る」。写真の撮影・選択と「自動車検査証記録事項」のPDFを対象にする。読取直後には保存せず、既存の登録フォームへ候補値を入れ、元画像と照合してから確定する。

| 項目 | 扱い |
|---|---|
| ナンバー・型式 | 書類から読み取り、確認・修正できるようにする |
| 車台番号 | 読取候補。保存欄を追加する場合は同じ会社内の重複確認に利用 |
| メーカー・車種 | 車名欄と型式を照合。車種は対応表から候補を出す |
| 初度検査年月 | 書類にある場合の読取候補。保存欄は新設が必要 |
| 車検満了日 | 記載されている資料からのみ読む。券面に無い日付を推測しない |
| 燃料・EV判定 | 記載内容から候補を出す。未読・不明は既存値を上書きしない |
| 車体色・現在の走行距離 | 手入力。検査時の走行距離を現在値として自動採用しない |
| 購入費・リース代・保険料・担当者 | 既存の入力・設定を使う。書類から推測しない |

電子車検証の券面には有効期間・使用者住所・所有者情報が記載されない。[国土交通省の説明](https://www.denshishakensho-portal.mlit.go.jp/user/)。満了日まで取り込む場合は、最新の記録事項の写真/PDF、または閲覧アプリの出力データを使う。記録事項PDFとJSON/XML/CSVの出力が公式に用意されている。[車検証閲覧アプリ](https://www.denshishakensho-portal.mlit.go.jp/user/application/)。

公式の軽自動車記録事項の見本でも「車名」は「スズキ」、型式は接頭辞付きで記載される。OCRで「エブリイ」という通称を必ず直接取得できる想定にはしない。[軽自動車検査協会の見本](https://www.keikenkyo.or.jp/Portals/0/files/information/computerization/0000058057.pdf)。

読取できない項目は空欄と「確認が必要」で示す。再撮影・ファイル選び直し・手入力で続けられるようにする。既存車への読取は、変更対象を比較してから反映し、手入力中の内容を無条件で消さない。重複候補は自社の登録車だけを調べ、既存車の更新へ進むか利用者が選ぶ。

読取エンジンは未選定。実書類の利用許可・送信先・保存方針を明らかにして、旧紙/電子券面/記録事項、暗い写真・傾き・反射・和暦で精度を検証する。公式出力のJSON取込はOCRと独立した追加経路にできる。読取エンジンの結果だけで車両登録や業務更新を実行させない。

原本を保存する場合は、公開の車体画像 `image_url` と分離する。自社の車両管理権限を検査し、会社ごとの非公開保存・短期署名URL・削除の経路を揃える。読取に不要な所有者住所等を車両項目やログへ展開しない。原本の恒久保存は必須にせず、読取専用の一時利用も選択肢とする。

## 実装の順番と完了条件

- **V-1 型式とGLBの接続**: 世代・OEM・外観仕様のカタログ、型式正規化、旧キーとの互換、地図/編集/プレート生成の統一。制作元GLBの座標・実寸・塗装・灯火・前後プレートを検証する。
- **V-2 車検証登録の隔離プレビュー**: 既存の本番ページとfixtureを使い、読取中/一部未読/失敗/重複/型式不明/複数候補/保存失敗を架空データで操作できるようにする。読取はこの段階ではfixtureであり、実OCRの精度を検証済みとしない。
- **V-3 写真/PDFの読取接続**: エンジンと保存方針を決定し、読取APIの権限・会社範囲・ファイル上限・失敗復帰を実装。必要な車台番号等のDB変更を開発DBで検証。原本と項目値を比較し、利用者の確認後に既存登録処理へ渡す。
- **V-4 既存車への反映**: 型式不明の車へ順次追加できる導線と、既存値との差分確認。モデル追加時のプレート再生成・キャッシュ更新を確認。公式JSON取込は必要に応じて追加する。

UI着手時は `npm run preview:admin -- admin --port 3197` で `/preview/admin/vehicles?scenario=normal&role=admin` を開く。既存画面の表示を先に確認してから改修し、PC/スマホ幅・admin/accounting/viewer・標準6シナリオと上記読取状態を監査する。実データ・本番APIから隔離し、GLBは実ファイルで確認する。

相談時点の完了範囲はコード/制作台帳/公式資料の照合と本設計案の記録までだった。
