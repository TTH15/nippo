# 配車作戦盤 — 位置・時間軸・シミュレーションの設計

2026-08-06 起票。ユーザー要望:
①GPS が入る前の今から**ドラッグで車の現在地を示したい** ②**車移動のシミュレーションを動画で書き出したい**
③**「何月何日の車の位置」**を見たい。

> 2026-09-01補足: 下記の「現状」は起票時点。現在のリポジトリにはmigration 122の `vehicle_positions` と134の最新位置取得、地図の読取・手動配置APIがある。日報から駐車申告を入れ、将来QR＋端末位置へ拡張する [共通基盤の計画](daily-report-parking-foundation.md) を追加した。既存の位置観測と駐車申告、予定は区別して扱う。本番DBの適用状態をこの文書から推測しない。

現状は `/admin/map` が「打刻GPSの最終地点を出す可視化β」。位置は `vehicle_sessions` の
出勤/退勤の座標から**その場で導出**していて、位置そのものを保存するテーブルが無い。
①②③はいずれも「位置を時系列で持つ」ことが前提になるので、まずそこから設計する。

## 1. 中心となる考え方

**位置は「1車両につき1つの現在値」ではなく、「出どころ付きの時系列」として持つ。**

この1点で3つの要望が同じモデルに乗る:

| 要望 | モデル上の操作 |
|---|---|
| 現在地を出す | 各車両の最新行を取る |
| 何月何日◯時の位置 | `at <= T` の最新行を取る（as-of クエリ） |
| ドラッグで置く | `source='manual'` の行を**追記**する |
| GPS が入ったら | `source='gps'` を流し込むだけ。UI は変えない |

**上書きではなく追記**にするのが肝。上書きだと「置き直した経緯」が消える。追記なら
それ自体が履歴＝③の材料になり、後で AI に食わせるデータにもなる
（「誰がいつどの車をどこへ動かしたか」は既に残す方針）。

### 1-1. この作戦盤をデジタルツインにする条件

3D地図や車両モデルだけではデジタルツインとは呼ばない。現実の車両と画面上の1台が同じIDで結ばれ、
次の4層を混ぜずに重ねて確認できる状態を目標とする。

1. **実績**: 日報、打刻、手動配置、将来のQR・GPSから、いつ・どこにいたかを出どころ付きで受け取る
2. **予定**: シフト、次の利用、車両移動の手配を、実績とは別の正本として持つ
3. **時点再現**: 指定日時以前の最後の観測から、当時わかっていた状態を再現する
4. **差分と予測**: 予定と実績のずれを示し、将来のシミュレーションは事実と分けて扱う

現在の `/preview/map-operations` は、この見せ方と操作を確かめる**デジタルツイン画面のモック**である。
固定データで本番の記録源と同期していないため、現段階ではデジタルツイン本体ではない。

## 2. データモデル

### 2-1. 実績の位置（`vehicle_positions`）

```sql
CREATE TABLE vehicle_positions (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id       uuid NOT NULL,
  vehicle_id   uuid NOT NULL REFERENCES vehicles(id) ON DELETE CASCADE,
  at           timestamptz NOT NULL,     -- 「いつの位置か」。記録時刻ではない
  lat          double precision NOT NULL,
  lng          double precision NOT NULL,
  heading      real,                     -- 進行方向（GPS のみ・任意）
  accuracy_m   real,                     -- 精度（GPS のみ・任意）
  source       text NOT NULL CHECK (source IN ('punch','manual','gps')),
  recorded_by  uuid REFERENCES drivers(id) ON DELETE SET NULL, -- manual では必須
  note         text,                     -- 「センター戻り」等の一言
  created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON vehicle_positions (org_id, vehicle_id, at DESC);
CREATE INDEX ON vehicle_positions (org_id, at DESC);
```

- `source` を**必ず持つ**。手動で置いた点と GPS を見た目でも集計でも混ぜない
- **集計（請求・稼働時間・走行距離）には `manual` を使わない**。あくまで「今どこにいるか共有するための付箋」
- `punch` は既存の `vehicle_sessions` から移行時に一括生成し、以後は打刻のたびに1行追記
- 保持期間は当面無期限（1日1台あたり数十行なら年間でも軽い）。GPS が入って秒間隔になったら
  「生ログは90日、以降は5分間隔へ間引き」を検討する

### 2-2. シミュレーション（`sim_scenarios` / `sim_moves`）

**実績とは絶対に同じテーブルに入れない。** 盤面で動かした「もしも」が実績として残ると、
地図の信頼性が根本から崩れる。

```sql
CREATE TABLE sim_scenarios (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id      uuid NOT NULL,
  name        text NOT NULL,            -- 「8/10 雨天想定」
  base_date   date NOT NULL,            -- 何日の配車を検討しているか
  created_by  uuid REFERENCES drivers(id) ON DELETE SET NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE sim_moves (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  scenario_id  uuid NOT NULL REFERENCES sim_scenarios(id) ON DELETE CASCADE,
  vehicle_id   uuid NOT NULL,
  driver_id    uuid,                    -- 誰が乗る想定か（未定なら null）
  minute       int NOT NULL,            -- base_date 0:00 からの経過分。時刻を持たず相対で持つ
  lat          double precision NOT NULL,
  lng          double precision NOT NULL,
  kind         text NOT NULL CHECK (kind IN ('start','via','stop')),
  label        text                     -- 「センター」「◯◯様宅」
);
CREATE INDEX ON sim_moves (scenario_id, vehicle_id, minute);
```

- キーフレーム方式。点と点の間は再生時に補間する（既定は等速直線。道路追従は将来 Directions API）
- `minute` を相対で持つので、同じシナリオを別日に流用できる

## 3. 画面設計

### 3-1. 現在の3つのモード（画面上部で切替）

```
┌─────────────────────────────────────────────┐
│ [いま] [車両移動] [履歴]                         │
│ 履歴: [2026/9/1（火）] [18:00] [前の記録] [次の記録] │
├─────────────────────────────────────────────┤
│                                              │
│              （地図・全画面）                    │
│                                              │
└─────────────────────────────────────────────┘
```

- **いま**: 各車両の最新位置と次の利用を見比べる
- **車両移動**: 未完了で別の場所へ運ぶ必要がある車両だけを出し、選んだ1台の手配を確認する
- **履歴**: 日付と時刻を指定し、その時刻の as-of 位置を出す
- **シミュレーション**は将来の第4モードとし、固定データの履歴や現在の移動手配とは混ぜない

### 3-2. ドラッグで置く（要望①）

- プレートピンを `draggable` にし、drop で `vehicle_positions` に `source='manual'` を**追記**
- 表示で必ず区別する:
  - `gps` — 実線リング・「◯分前」
  - `punch` — 実線グレー・「出勤時の位置」
  - `manual` — **破線リング＋「手動」バッジ**・「◯◯が◯分前に配置」
- 権限は `can_dispatch`。置いた人を `recorded_by` に必ず入れる
- 共有ビュー（Stage 1 の Realtime broadcast）に乗せ、**他の参加者の画面でも即座に動く**。
  これがあると「電話しながらみんなで盤面を動かす」が成立する
- 元に戻す: 追記モデルなので「1つ前の位置に戻す」は直前行の復元＝もう1行追記で表現する

### 3-3. 時間軸（要望③）

- 日付を選ぶとその日の `vehicle_positions` を1回だけ取得（1日分は数百行で軽い）
- 日時の変更中はサーバーに問い合わせず、取得済みデータからクライアントで as-of を解決する
- 打刻・日報・手動配置のように記録が疎な段階では、連続スライダーを出さない。存在しない中間位置まで
  観測したように見えるため、**日付＋時刻の明示指定**と「前の記録」「次の記録」で移動する
- 地図には指定日時以前に記録がある車両だけを出す。右の詳細は、その時点の場所・記録日時・記録者・
  出どころだけを表示し、現在の「次の利用」「移動の手配」を履歴へ混ぜない
- **点の間を勝手に繋がない**。打刻や手動配置は離散的な事実なので、既定は
  「その時刻時点の最後の位置にスナップ」。GPS が入って点が密になったら
  初めて再生タイムラインを検討する。補間する場合も実測点と推定区間を見た目で区別する
- 副産物: 「この日この時間、この車はどこにいたか」が答えられる。
  事故・遅延の振り返り、請求の根拠、AI の学習データになる

### 3-4. シミュレーション（要望②の前半）

- シナリオを作る → 車両を選ぶ → 地図をクリックしてキーフレームを置く → 時刻を割り当てる
- 実績レイヤーと**重ねて**表示（実績＝実線、シミュ＝点線・別色）。「いつもの動き」と比べられることが価値
- 再生速度は 1分/秒（24時間＝24分）〜 60分/秒（24時間＝24秒）。既定は 30分/秒（＝48秒）
- 確定すると割当ドラフトとしてシフトへ反映（roadmap トラック K Stage 2 の既定路線に接続）

## 4. 動画エクスポート（要望②の後半）

### 案A: クライアント録画（推奨・まずこれ）

```ts
const stream = map.getCanvas().captureStream(30);
const rec = new MediaRecorder(stream, { mimeType: "video/webm;codecs=vp9", videoBitsPerSecond: 8_000_000 });
// 再生を走らせながら録画 → stop() で Blob → ダウンロード
```

- **長所**: 追加インフラ不要。見たままが撮れる（3D建物・ライティング・カーソルも入る）。今日から作れる
- **短所**:
  - **実時間かかる**（48秒の動画なら48秒待つ）。再生速度で尺を決める設計にしておく
  - タブを裏に回すとフレームが落ちる → 録画中は「このタブを表示したままにしてください」と出す
  - 出力は webm。**LINE で配るなら mp4 が要る** → `ffmpeg.wasm` でブラウザ内変換（数十秒・重い）か、
    当面は「webm のままダウンロード＋PCで再生」で運用する
  - Mapbox の canvas は `preserveDrawingBuffer` 無しでも captureStream は取れるが、
    描画が止まっているとフレームが出ないので再生中は `map.triggerRepaint()` を回す

### 案B: サーバーで決定的にレンダリング（将来）

headless Chrome + Mapbox GL でフレームを吐き、ffmpeg で mp4 化。

- **長所**: 尺・解像度・fps が正確。実時間を待たない。4K も出せる
- **短所**: Vercel の関数では重すぎる（別ワーカー／コンテナが要る）。Mapbox のトークン利用条件も要確認
- **判断**: 「取引先や社内へ配る資料として使う」段階になったら着手。最初から作らない

### 案C: GIF

画質とサイズで不利。採用しない。

## 6. 決めておきたいこと

1. **手動配置を「実績」テーブルに入れてよいか**
   本設計は `source` で区別したうえで同じテーブルに入れる案（現在地の解決が1本のクエリで済む）。
   完全に別テーブルにする案もあるが、「最新位置を引く」処理が二重になる。
   → **集計には絶対使わない**という運用で担保する想定。
2. **履歴の点を線で繋ぐか**
   既定は繋がない（離散の事実として扱う）。GPS が入ってからの切替とする。
3. **動画の出力形式**
   まず webm で始めてよいか。mp4 必須なら `ffmpeg.wasm` を最初から入れる（重い）。
4. **シミュレーションの経路**
   直線補間で始めてよいか。道路に沿わせるなら Mapbox Directions API を使う（コストと精度の話になる）。

## 7. 車両3Dモデル（2026-08-10 追記）

ユーザー方針: **NISSAN クリッパー / スズキ エブリイ など代表的な軽バンを、色を変えられる形で
用意して選べるようにする**。

- DB: `vehicles.model_key`（どのモデルで描くか）/ `vehicles.body_color`（#RRGGBB）— migration 123
- 地図は Mapbox の `model-color` で着色する。**着色を効かせるにはモデル側の車体マテリアルを
  無彩色（白〜薄グレー）**にしておく必要がある。濃色やテクスチャを焼き込むと色が乗らない
- 窓・タイヤ・ライトは車体と別マテリアルにしておくと、車体だけを着色できる
- 車種の出し分け（`model-id` の切替）はモデルが2種類以上揃ってから実装する

### 7-1. 地図上の大きさと輪郭（2026-09-02 HH5実測）

- 車両の長さは**地図表示部分の幅の9%**を目標にする。ズームと表示幅が変わるたびに、緯度を含むMapboxの1px当たりメートルから倍率を計算する。
- 画面上で9%を保つための倍率が1を下回るところまで近づいたら、`model-scale = 1`で止める。それ以降は実寸の投影サイズが9%を超え、地図を拡大するほど車両も自然に大きく見える。
- アクティHH5は、車体の5材質（Body White、Hood、前後Bumper、Body Crease）、窓・タイヤ・灯火・継ぎ目等の固定色27材質、前後プレート1材質を、形状と原点を変えず3つのGLBへ分けて同位置に重ねる。車体だけ`model-color`を強く混ぜ、固定色側には混ぜない。
- Mapboxのmodelレイヤーへ太い輪郭線を直接足すのではなく、車両の足元へ白地＋細い濃色線のリングを置く。地図面との境界だけを補助し、車体の形は固定色の窓・タイヤ・継ぎ目で読ませる。状態や警告の意味はリング色へ持たせない。
- 分割は `scripts/split-vehicle-map-model.mjs` で再現する。HH5では車体93KB／固定色274KB／プレート34三角形で、1台の合計8,602三角形は分割前から増やしていない。

### 7-2. ナンバーのSVG共用と3D面への貼付（2026-09-02）

- 地図上の車両札は簡易テキストを廃止し、実画面の `VehiclePlate` と同じ寸法・SVG字形をCanvasへ一度だけ描画した1枚画像をMapbox Marker内へ置く。複数のCSS maskを移動中に再合成しないための地図専用最適化で、一覧・詳細の `VehiclePlate` 自体は変更しない。選択はプレート外側のアンバーリング、要確認は上部の小バッジで示す。
- 車両札は車両IDごとのMarkerを保持し、地図のパン・ズームでは作り直さない。Mapboxの3D遮蔽によるopacity低下と標準の0.2秒フェードを無効化し、車両座標に追随する画面向きの札として、車両が表示範囲内にある間は常時表示する。
- 3D側は、画面に向く別マーカーを車体前端へ置く方式を採用しない。拡大時に素材面から浮き、車両の回転・遠近と一致しないため。
- HH5の `License Plate Front` 材質が持つ前後プレート34三角形だけを小さなGLBへ分離する。`scripts/build-vehicle-plate-model.mjs` が既存SVG字形から512×256のプレート画像を生成し、前後面へUVを追加してbase color textureとして直接貼る。
- 画面の `VehiclePlate` は添付実車写真に合わせた既存の大きい文字比率を維持する。`vehiclePlateLayout.json` に上段29／かな27／一連58、字間とハイフンの相対寸法を240×120基準で集約し、3D生成側も同じ値とSVGの可視領域を使う。3D側だけの文字高・上寄せ・ハイフン拡大を持たせない。
- 車体・固定部品は全車で共用し、プレートGLBだけを車両番号ごとに差し替える。プレビュー4台では各36〜38KB。Mapboxの同じGeoJSON featureに `plateModel` を持たせ、3枚目のmodelレイヤーの `model-id` で選ぶ。
- 通常倍率では物理的に文字を読めなくてよい。近接確認時もプレートを誇張せず、実寸倍率のまま最大ズーム24まで寄れるようにする。

### 7-3. 移動予定は空中アーチで示す（2026-09-02）

- 移動予定をMapboxの地表lineレイヤーへ描かない。3D車両や地図道路の下へ潜って見えるため、緯度経度の始点・終点を画面座標へ投影し、地図Canvasより前面のSVGに太いアーチとして描く。
- アーチはアンバーの8px実線、白15pxの縁取り、大きな矢尻と始点リングを使う。車両モデルより前、DOMのナンバー札と操作ボタンより後ろの重なり順とし、車両識別を隠さない。
- 「車両移動」モードで、未完了かつ別の場所へ運ぶ必要がある車両だけを地図へ表示する。通常の「いま」と履歴ではアーチを出さず、移動モードで選んだ1台の方向を確認する。同じ場所での受け渡しと到着済みは対象に含めない。
- 始点は手配に保存された車庫の代表座標ではなく、地図に表示している車両の最後の記録位置とする。これにより、選択車両のモデルから線が出る。詳細欄の「豊中車庫 → 吹田車庫」等は手配内容として維持する。
- 始点または届け先が画面外なら、線をそれぞれ地図の外まで伸ばしてクリップする。始点の丸と届け先の矢尻は、その実座標が表示範囲にあるときだけ出す。地図端を仮の始点・到着点に見せない。
- 空中アーチはMapboxの `move` ごとに画面座標だけを更新し、React画面全体を再描画しない。車両倍率・ナンバー札の高さはズーム・リサイズ・移動終了時に差分がある場合だけ更新する。パン中はMapboxが保持中のモデルとMarkerを同じ地理座標から動かし、車両札の破棄・再生成を行わない。
- 動きを示す点線アニメーションや地図上の追加ラベルは使わず、詳細欄の届け先・期限・担当者を正確な情報表示として残す。

120m 以内に停まっている稼働中**を積み込み中と見なす。あくまで推定であり、

## 9. 拠点の編集と「範囲」での登録（2026-08-10 追記）

要望: 登録した地点を**移動・名称変更**したい。**点ではなく範囲で登録したい**場合もある。

- **編集**: 拠点ピンをクリック → 編集パネル（名称・種別・範囲）。**ピンはドラッグで移動**できる。
  キャンセルで元の位置に戻す（サーバーの値を取り直す）
- **範囲は段階を分ける**（migration 124 で `shape` / `radius_m` / `geometry` を用意）:
  - `point` … 従来どおり1点
  - `circle` … 中心＋半径。**まずこれを実装**。敷地や「この辺り」を表すには十分で、
    UI がスライダー1本で済む。「積み込み中」の判定半径にもそのまま使える
  - `polygon` … **配達エリアは map_places ではなく courses が持つ**ことにした（2026-08-10 合意）。
    同じ「範囲」でも意味が違う: 拠点の円＝その場所の広がり / コースの面＝担当する区域。
    → `courses.delivery_area`（GeoJSON・migration 125）。描画は `@mapbox/mapbox-gl-draw` を採用
- 円は Mapbox に円プリミティブが無いため、**64角形の GeoJSON ポリゴンに落として**塗る
- 配達エリア（polygon）はコースと結びつける想定（roadmap A4-b / トラック K Stage 2 の土台）

## 10. Meshy.ai の出力を地図に載せるまで（2026-08-10 実測）

**結論: Meshy の出力をそのままは載せられない。ただし Blender は必須ではない。**
`scripts/prepare-vehicle-glb.mjs` で自動整形できる。

実測（NISSAN クリッパーの生成結果）:

| | 元（Meshy generate） | 整形後 |
|---|---|---|
| 三角形 | 1,991,960 | 16,000 |
| ファイル | 34 MB | 277 KB |
| 寸法 | 1.9 単位（正規化） | 3.40 × 1.92 × 1.96 m（実寸） |
| 原点 | 中心 | **底面中心** |
| 属性 | POSITION のみ | POSITION + NORMAL |
| マテリアル | 無し | 無彩色1つ（`model-color` で着色可） |

スクリプトがやること: ①目標三角形数まで簡略化 ②実寸へスケール ③原点を底面中心へ
④法線が無ければ生成 ⑤マテリアルが無ければ無彩色を付与。

- **Draco 圧縮はしない**。Mapbox の model レイヤーが `KHR_draco_mesh_compression` を読める保証がなく、
  現に動いている `truck.glb` も非圧縮のため（16k 三角形なら非圧縮 277KB で十分軽い）
- **Meshy 側でやってほしいこと**: 「テクスチャ」工程まで回す。generate 段階の出力は
  **POSITION しか持たない**（UV も法線もマテリアルも無い）。テクスチャ版なら法線・UV が入るので、
  スクリプトの④⑤が不要になり、見た目も良くなる
- **車体は白〜薄グレーのまま**にしておく。`model-color` で着色するため、濃色を焼き込むと色が乗らない

## 11. 見た目の方針: 写実ではなく「地図の抽象度」に合わせる（2026-08-10）

Meshy のテクスチャ版は写真из起こしたような質感で、**暗く抽象的な地図（Standard の
フラットな建物）から浮く**。ユーザー指摘「いくら何でもリアルすぎる／ハコ虎の画面に合うように」。

**方針: 既定は `style=flat`**（`scripts/prepare-vehicle-glb.mjs` の第6引数）。

- テクスチャ（base_color / metallic_roughness / normal）と **UV・接線を外す**
- 無彩色（#eef0f5 相当）・metallic 0・roughness 0.75 のフラットなマテリアルにする
- 結果: エブリイ 1.26MB → **443KB** / クリッパー 1.91MB → **717KB**

**なぜ写実を捨てるか**:
1. 地図の縮尺では質感は見えない（車は画面上 数十px）
2. 焼き込まれた影・汚れが `model-color` の着色を濁らせる。**車体色を選べる**設計と相性が悪い
3. 建物がフラットな面で描かれている中で、車だけ写真的だと**視線が car に張り付いて地図が読めない**

実物に寄せたい場面（車両詳細のプレビュー等）が出たら `style=photo` で別ファイルを作ればよい。

## 12. ナンバープレート（2026-08-10）

**背景**: モバイル側で 3D モデルを画面に出す予定（明日使う車・いま使用中の車）。
そこでは車が大きく映るため、プレートの見た目が効いてくる。
生成モデルのままだと「EVERY」のロゴや黄色いプレートが出て、デジタルツイン感が落ちる。

**いまやったこと**: `scripts/prepare-vehicle-glb.mjs` が
**プレート面を別マテリアル（`plate`）に切り出す**。判定は幾何条件:

- 車体の端（X方向の外側6%）にある
- 地上 0.25〜0.72m（軽バンのプレート位置）
- 中心から ±0.22m（プレート幅33cm）
- 前後を向いた面（法線のX成分 > 0.75）

前後2枚で 370〜380 三角形が該当。既定色は **#111827（事業用＝黒ナンバー）**。
第7引数で色を変えられる（自家用の白ナンバーなど）。

- **マテリアルを分ける意味**: モバイル（three.js 等）で**プレートだけ差し替え・着色できる**。
  将来プレート番号のテクスチャを貼るときの受け皿にもなる
- Mapbox 側は `model-color-mix-intensity` を 0.85 → **0.55** に下げた。
  強く混ぜると車体色がプレートの黒まで染めてしまうため

**次**: ユーザーが Illustrator で**プレート書体を SVG 化**する（2026-08-10 判断）。
既存フォントは著作権が怪しく、余白がばらつき、環境によって別フォントに化ける。
SVG グリフが入ったら ①地図の吹き出し ②`VehiclePlate` コンポーネント
③3Dモデルのプレート用テクスチャ（モバイル用）の3箇所で共用する。

2026-09-02追記: 地図作戦盤プレビューでは、地図上の札に `VehiclePlate` と同じSVG字形・配置から作る1枚画像を使い、MapboxのHH5も前後プレート面へ同じSVG字形から作ったテクスチャを貼った。前者は車両座標へ追随する常時表示の識別札、後者は車体と同じ回転・遠近で描画する実寸プレートとして役割を分ける。本番の車両登録・番号変更時に小さなプレートGLBを生成・キャッシュする処理は未実装。

## 13. 車体色と窓の両立: 「塗り分けマスク」方式（2026-08-11 確定）

**問題**: テクスチャを捨てると窓まで車体色になり粘土のように見える。
かといって面で窓を選び分けられない（スマートトポロジー版は**窓が描いてあるだけで形状が無い**）。

**解**: テクスチャを**白黒の塗り分けマスク**に変換して残す（`prepare-vehicle-glb.mjs` の `style=masked`・既定）。

- 明るいところ（車体）は白へ持ち上げ、暗いところ（窓・タイヤ・グリル）は暗いまま残す
- 描画側で色を**乗算**すれば、車体だけが指定色になり窓は暗いまま
  - three.js（車両プレビュー・将来のモバイル）: `material.color` がテクスチャと乗算される＝そのまま成立
  - Mapbox: `model-color` は乗算ではなく**混色**なので、`model-color-mix-intensity` を 0.45 に抑えて
    窓が塗り潰されないようにする
- 副産物: グリルやドアの筋・ライトの陰影も残るので、フラット版より**形が読みやすい**
- ファイルは 512px のグレースケール PNG 1枚ぶんだけ増える（620KB〜1.2MB）

## 14. 3Dモデルの見せ方（2026-08-11）

生成モデルは**リアの造形が実車と違う**ことが多い（Meshy は1枚の写真から裏側を想像するため）。
また細部の質感は写真から起こしたぶん甘い。**見せ方でごまかすのではなく、粗が出ない角度に固定する。**

- **ぐるぐる回さない**。前寄りの斜め45度で止め、±8度ゆっくり揺らすだけ。
  見たい人は**ドラッグで回せる**（逃げ道は残す）
- **接地影**を敷く。浮いていると玩具に見える
- **ACES トーンマッピング**で白飛びを抑える。既定のままだと明るい面が潰れて「粘土」になる
- モバイルで大きく出すときも**前面〜斜め前の固定アングル**にする（リアは映さない）

### 夜のヘッドライト・テールランプ ★2026-08-11 実装済み

地図は既に時間帯で `lightPreset` を切り替えている（dawn/day/dusk/night）。
夜だけ車両に**発光を足す**ことは、モデルを作り直さなくても実現できる:

- three.js: ライト位置（前面下部の左右・背面下部の左右）に**小さなスプライトを置く**。
  位置はバウンディングボックスから算出できるので、車種ごとの調整は不要
- Mapbox: 車両位置に**発光する点のレイヤー**を重ねる（`circle` + blur、夜だけ表示）
- **モデルに手を入れる必要がない**のが利点。実装コストは小さい

**実装（2026-08-11）**

- **地図**: `vehicle-lights` レイヤー（glow + core の2枚の circle）。
  **夜（JST 17時〜5時）かつ稼働中の車両だけ**灯す。履歴表示中は出さない
  - **単なる演出にしない**: 光っている＝まだ外に出ている車。「誰がまだ帰っていないか」が
    夜の地図で一目で分かる情報になる
- **車両プレビュー（three.js）**: 車体の前後端4隅に発光スプライトを置く。
  位置はバウンディングボックスから算出するので**車種ごとの調整が不要**。
  夜は環境光を落として灯りを際立たせる
  - **どちらが前かは生成モデルから判定できない**ため、両端とも電球色にした。
    赤（テールランプ）を前に付けてしまう方が事故なので、確実な側に倒している

## 15. 目指す質感（Google マップ型）と、そこへの道（2026-08-11）

ユーザーが目標として挙げたのは **Google マップの車両アイコン**の質感:

- **様式化されたおもちゃ的な造形**。写実ではない
- **面が平らで滑らか**。ノイズ（凹凸）が無い
- **窓は1本の暗い帯**として単純化（1枚1枚作り込まない）
- タイヤは単純な黒い円盤。グリルやモールは省略
- 柔らかい均一な光。**車体色＋窓の暗色**の2色構成
- 足元に**淡い楕円のリング**

### 差はレンダリングではなく「モデルそのもの」

トゥーンシェーディングや輪郭線を足しても届かない。理由は明確で、
**Google のモデルは低ポリで手作りされており、面が意図的に平ら**なのに対し、
**こちらのモデルは写真から起こしたぶん表面が波打っている**。
波打った面はどう陰影を付けても波打って見える。

### 判断: **当面**は様式化した「軽バン」1体に集約する（車種別は将来ちゃんとやる）

> **重要（ユーザー・2026-08-11）**: 「エブリイとアトレーは、現場では全く別物」。
> 車種の違いは現場感覚として確実に効く。**1体に集約するのはあくまで当面の段取り**であって、
> 車種別をやらないという判断ではない。様式化の型が1体で固まったら、
> 同じ型で車種を作り分ける（そのときはトポロジーも見た目も揃うので、比較して意味が出る）。

**Google も車種ごとのモデルは持っていない**（セダン/SUV/ハッチ/ピックアップの体型別）。
軽バンはどれも似た箱型で、しかも**クリッパーはエブリイの OEM**（実車が同一）。
つまり**車種ごとの作り分けは、この縮尺では意味を持たない**。

- **1体だけ、きちんと様式化された軽バンを用意する**（手作りの低ポリ or 低ポリ素材集の流用）
- 色は既存の仕組み（`body_color`）で変える。窓は暗いまま
- 車種の違いは**ナンバープレートの吹き出し**が担う（すでに実装済みで、こちらの方が確実に読める）
- Meshy 由来のモデルは「暫定」として残し、良い1体ができたら差し替える

### レンダリング側でやること（モデルが揃ってから）

- トゥーン寄りの階調（2〜3段）＋輪郭線
- 足元の楕円リング（Google と同じ）
- 車体色は彩度を保ったフラットな塗り

## 16. 車両移動・地図作戦盤の次段階（2026-09-02）

アクティHH5の暫定完成版が利用可能になったため、当面の汎用軽バン1体だけを前提にせず、**完成した車種から実モデルへ差し替える**。エブリィなど制作中の車種は完成前の見た目を推測せず、共通モデルをフォールバックにする。

地図は予定や実績を直接編集する正本ではなく、次の3情報を見比べる作戦盤とする。

1. シフト: 次に誰が、どこで、いつ使うか
2. 移動手配: 誰が、どこからどこへ、いつまでに運ぶか
3. 日報・将来QR: 実際にどこへ停めたか

PCは地図と360pxの選択車両詳細を左右に置き、スマホは地図の下へ同じ詳細を積む。広域では全車のナンバー札と要確認、選択中の空中移動アーチを優先し、近接表示で実モデルを確認する。状態は色や灯火だけに依存せず、「確認が必要」「運ぶ人 未設定」などの文字を併記する。現在位置と履歴位置は同じフィールドを上書きせず、表示モードだけで切り替える。

実装順は次のとおり。

1. 隔離プレビューでHH5の描画負荷・見かけサイズ・PC／スマホの判断導線を確定する。
2. `model_key` から車種別GLBとフォールバックを選ぶアダプターを整理し、車体色を掛ける部位と窓・タイヤ・灯火を分ける。HH5は33材質を持つため、全体への一律着色は暫定に留める。
3. 既存の車両移動・受け渡しデータを地図の空中移動アーチと詳細へ接続し、シフト側を予定の正本として維持する。
4. 日報の駐車記録を `map_places`／`parking_slots`／`vehicle_positions` へ安全に反映し、再送・過去日報・手動補正を扱う。QRと端末位置はこの保存口を共用する。
5. 権限・会社境界・競合・通知予約・多数台性能を検証してから本番画面へ段階的に接続する。

検討用画面と起動方法は [ログイン不要プレビューの標準手順](../development/preview-workflow.md#車両地図移動作戦盤2026-09-02) を正本とする。この段階では本番DB、GPS、日報、QR、通知へ接続しない。
