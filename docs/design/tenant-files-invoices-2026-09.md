# 他社データ・非公開ファイル・請求書住所の保護

2026年9月12日。対象は B-3 → B-4 → B-5。実装と隔離プレビューを検証してから、本番適用を別途判断する。

## 影響と方針

- 報告の承認・却下は、報告と関連するドライバー・車両の所属を更新前に確認する。車両は自社所有または報告日の正式な貸与を許可する。他社IDと存在しないIDは404。対象外の場合は承認、走行距離、経費、単価スナップショットを変更しない。正規の経費加算・控除の符号、走行距離の前進更新、再承認の扱いは維持する。
- 報告種別は現在全社共通の設定。migration 163で適用時点の設定を各既存会社に複製し、以後は会社内だけで参照・編集する。既定会社のIDを維持し、他社分は新しいIDとする。過去の報告が持つ種別キー・回答・金額は変更しない。
- 非公開ファイルは、認可済みDB行と認証文脈から決まる保存範囲を必須にする。会社の添付・画像・印影は会社ID、本人確認はidentity ID、旧諸報告はdriver ID、点検写真は会社ID/driver IDを使う。保存・署名・削除で同じ検査を使い、既存の正規パスは移動しない。
- 請求書住所は文字列として描画し、従来のbr改行だけを改行文字へ変換する。保存済み住所の一括更新、金額・ページ分割・印刷方式の変更は行わない。

## 検証と戻し方

- 架空の2社を使い、他社ID・破損した関連ID・他社パス・不正な住所を回帰テストする。本番DBへのテスト書き込みは行わない。
- 本番ページを使った隔離fixtureで、PC・スマホ、正常・空・長文・取得失敗・保存失敗を確認する。PDF・画像は実ファイルと生成経路を分けて監査する。
- migration 163を開発DBで検証した後、DB→Webの順に適用する。旧Webは分離後の種別を全社分取得してしまうため、適用中の報告種別の読み書きを止める手段と切替時間を決めてから本番作業する。Webのロールバック先も会社境界を保つ必要があるため、問題の経路を停止する修正版を優先する。分離後の種別を全社共通に戻す自動逆移行はしない。
- 複数テーブル更新の原子性は既存の課題。今回は所属の確認と各更新の条件を固定し、承認・経費の完全なトランザクション化は別途扱う。

## 実装・検証の到達点

- B-3/B-4/B-5のコードと隔離fixtureを実装。新規会社には会社別の既定報告種別も作成する。
- 全125ファイル・1,177テスト、Web本番ビルド、TypeScript検査を通過。会社別クエリのAST検査は48テーブルで指摘0。id指定だけを安全とみなす旧除外を廃止し、認可済み親ID・基盤管理などは理由付きコメントを個別に確認した。AST検査は実行時認可やデータフローの証明ではない。
- 開発DBでmigration 163の設定複製・ID維持・会社内一意性・他社更新0件・再実行を確認し、全変更をROLLBACK。本番DB・本番Storageの変更、Web公開は行っていない。
- 住所タグの非実行、保存済みbr改行の互換、非公開ファイルの保存/署名/削除の範囲検査を回帰テスト。PDFと画面の詳細は[UI・出力監査](../development/ui-export-audit.md)。


## 2026年9月14日の本番反映

DB163とb009d45のWeb公開を完了。共有4種別を2社へ4件ずつ複製し、既定会社のID・設定・日時の保持、所属必須、一意索引、一般ロール権限0、台帳記録を確認。対象APIを停止し、旧処理の終了待ち後にDB→Webを切替、対象APIを復帰した。認証付きの業務更新を本番で試験していないため、正規業務の網羅的なE2Eは別途行う。[公開記録](../deployment/tenant-scope-163.md)。
