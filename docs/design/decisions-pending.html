判断待ちの一覧

2026-08-06 時点。設計は進んでいるがユーザーの判断がないと確定できないものだけを集めた。 各項目に推奨を書いてあるので、「全部推奨で」と言えば進められる状態にしてある。 決まったものはここから消し、各設計書と roadmap に反映する。

A. 地図・配車作戦盤（map-board.md）

# 論点 推奨 判断がずれると何が起きるか
A1 手動でドラッグして置いた位置を、実績テーブル（vehicle_positions）に source='manual' として入れてよいか 入れる。source で必ず区別し、集計（請求・稼働・走行距離）には使わない 別テーブルにすると「現在地を引く」処理が二重になり、履歴スクラブも二重実装になる
A2 履歴表示で、位置の点と点を線で繋ぐか 繋がない（打刻・手動配置は離散の事実）。GPS が入って点が密になってから補間へ切替 繋ぐと「通っていない道を通ったこと」になる。事故検証で使えなくなる
A3 動画の出力形式 webm で開始。mp4 が要るなら ffmpeg.wasm（ブラウザ内変換・重い）を足す LINE で配るなら mp4 が要る。最初から要るなら実装量が増える
A4 シミュの経路 直線補間で開始。道路追従は Mapbox Directions API（従量課金） 直線だと見た目の説得力が落ちる。ただし初手としては十分

B. プランと課金（plans-and-billing.md）

# 論点 推奨 補足
B1 席の定義（「5アカウント」「20人」の1は何か） status='active' の membership 数（運営者も含む） pending/inactive は数えない。実装済みの状態をそのまま使えるのが強い
B2 スターター（5席）を無料にするか 無料にする。ただしサポートは掲示板/メールのみ 無料枠は獲得に効く一方、原価（SMS・Vercel）とサポート工数は発生する
B3 年払いを用意するか 後回し。まず月額だけで始める キャッシュフロー改善は魅力だが、解約返金の扱いが増える
B4 AI 機能は上限方式か従量課金か 上限方式（プランごとの月間トークン枠） 「使ったら青天井」の不安を与えない。足りない声が出たら増枠を売る
B5 支払い手段 カード（Stripe）＋請求書払い（銀行振込）の二択 運送業はカードを嫌う会社が多い。カード必須は導入障壁
B6 制限のかけ方 「増やす操作」だけ止め、打刻・日報は止めない 支払い遅延でも現場を止めない。止める方が損害が大きい
B7 価格そのもの 原価とサポート工数を積み上げて再計算（たたき台は設計書の表） ここは経営判断

C. 元請け／下請け連携（prime-sub-reports.md）

# 論点 推奨 補足
C1 共有する報告にドライバー氏名を含めるか 既定は含めない。必要なら scope で下請けが明示的に有効化 第三者提供の論点。専門家レビュー前提
C2 元請けの閲覧専用アカウントを課金の席に数えるか 数えない（無料）。最小 capability に限定 元請けが導入しやすく、本契約への入口になる
C3 最初に作るもの エクスポート（CSV/PDF） → トークン閲覧リンク → org 間 in-app 共有 モデル変更がほぼ要らず、需要が確実

D. 請求・単価（設計未着手）

# 論点 現状
D1 単価モデル（従量 course_unit_rates ＋ 固定 course_fixed_rates）を作り直すか 設計の議論から。自動保存の機械的な適用は保留中
