# プランと課金の設計

2026-08-06 起票。他社へ提供するにあたり、プラン（席数・機能制限）と課金の形を決める。
既存の前提: org 発行は `/apply` → `/platform/applications` の審査フロー（Phase 1 実装済み）、
`platform-design.md §2-5` は「公開セルフサーブ価格なし・エンタープライズ価格を導入相談で提示」。
本設計はそこに**公開プランを足す**もの。

---

## 1. まず決めるべきは価格ではなく「席の定義」

「5アカウントまで」「20人まで」を実装する前に、**何を1と数えるか**を決める必要がある。
ここが曖昧なままだと、請求も上限判定も UI も全部ぶれる。

候補と評価:

| 定義 | 長所 | 短所 |
|---|---|---|
| A. `status='active'` の membership 全部（運営者含む） | 数え方が一意。実装済みの状態をそのまま使える | 月1日しか乗らない人も1席 |
| B. `works_as_driver=true` の active のみ | 「ドライバー課金」として説明しやすい | 運営専任者が無料になり、管理機能だけ使う会社が実質無料 |
| C. その月に1回でも稼働 or ログインした人（実働課金） | 実態に近い・繁閑に強い | 請求額が月末まで確定しない。上限judgment がリアルタイムにできない |

**推奨: A（active な membership 数）。**
理由は3つ。①`drivers.status` が既に正本で追加実装がほぼ要らない ②上限チェックが
「増やす操作」の瞬間に確定できる ③運営者も価値を受けている（管理画面が本体）ので
除外する理由がない。

- `pending` / `rejected` / `inactive` は**数えない**。承認前の申請で席を食わない
- 退職者を `inactive` にしないと席を圧迫する → 上限に当たったとき
  「稼働終了した方を整理すると席が空きます」と**その場から名簿の稼働終了タブへ誘導**する
- 将来 C（実働課金）に寄せたくなったら、`vehicle_sessions` と監査ログから算出できるので後付け可能

## 2. プランはコードの分岐ではなくデータ

プラン名を `if (plan === "mini")` のように散らすと、価格改定・個別対応のたびにコードを触ることになる。
**プランは行、機能は集合**として持つ。

```sql
CREATE TABLE plans (
  code              text PRIMARY KEY,        -- 'starter' / 'minimal' / 'standard' / ...
  name              text NOT NULL,
  max_members       int,                     -- NULL = 無制限
  monthly_price_jpy int  NOT NULL DEFAULT 0,
  features          text[] NOT NULL DEFAULT '{}',  -- 'line','ai','map_sim','export','api'
  ai_monthly_tokens bigint,                  -- NULL = 対象外（features に 'ai' が無い）
  line_monthly_limit int,                    -- 既存 org_notification_settings と同じ意味
  is_public         boolean NOT NULL DEFAULT true,  -- エンタープライズは false
  sort_order        int NOT NULL DEFAULT 0
);

CREATE TABLE org_subscriptions (
  org_id             uuid PRIMARY KEY REFERENCES organizations(id) ON DELETE CASCADE,
  plan_code          text NOT NULL REFERENCES plans(code),
  status             text NOT NULL DEFAULT 'active',   -- active / past_due / suspended / canceled
  started_at         timestamptz NOT NULL DEFAULT now(),
  current_period_end date,
  cancel_at          date,
  -- 個別対応（エンタープライズ・特例）。NULL ならプランの値を使う
  max_members_override int,
  features_override    text[],
  price_override_jpy   int,
  note               text,          -- 「◯◯商事様 3年契約・席50→80へ増枠」
  updated_at         timestamptz NOT NULL DEFAULT now()
);
```

コード側の入口は2つだけにする:

```ts
await assertSeatAvailable(orgId);        // 「増やす操作」の直前
await assertFeature(orgId, "ai");        // 機能ゲート
```

**エンタープライズは新しいプランを作らず、`*_override` で表現する。** 個別対応のたびに
`plans` に行が増えると、あとで誰も全体像を把握できなくなる。

### プラン表（たたき台）

| code | 名前 | 席 | 月額 | 機能 |
|---|---|---|---|---|
| `starter` | スターター | 5 | ¥0 | 日報・シフト・車両。**LINE / AI なし** |
| `minimal` | ミニマル | 20 | ¥15,000 | ＋LINE 連携・通知 |
| `standard` | スタンダード | 50 | ¥30,000 | ＋AI（シフト取込・承認支援）・地図 |
| `pro`（仮） | プロ | 100 | ¥55,000 | ＋シミュレーション・エクスポート |
| `enterprise` | エンタープライズ | 個別 | 個別 | ＋個別機能・SSO・専用サポート |

※価格は要検討。1席あたりでは starter 無料 → minimal ¥750 → standard ¥600 → pro ¥550 と
逓減していて、SaaS として素直な形にはなっている。

## 3. 制限のかけ方 — 「増やす操作」だけ止め、業務は止めない

**これは技術ではなく思想の話なので、先に決めておきたい。**

運送の現場は、日報が出せない・打刻できないだけで給与計算と請求が破綻する。
支払いが遅れているからといって当日の稼働を止めると、こちらの損害賠償リスクの方が大きい。

| 状態 | 止めるもの | 止めないもの |
|---|---|---|
| 席の上限に到達 | 招待発行・申請承認・新規メンバー作成 | 既存メンバーの全操作 |
| `past_due`（支払い遅延） | 招待・新規作成・エクスポート・AI | **打刻・日報・シフト閲覧** |
| `suspended`（長期未払い・合意解約） | 管理画面全般 | 直近3ヶ月のデータのエクスポート（1回） |
| `canceled` | 全部 | 削除前の猶予90日（§5） |

- 上限到達時のメッセージは行き止まりにしない。**「◯人まで」「今◯人」「稼働終了を整理する」「プランを上げる」**
  の4点を必ず出す（ログインできない人に「PINを使いません」とだけ出していた反省・2026-08-05）
- 機能ゲートは**隠すのではなく見せて誘導**する。AI 取込のボタンは出すが、押すと
  「スタンダード以上で使えます」と出す。使えると分かって初めてアップグレードの動機になる

## 4. 課金手段

日本の運送業が相手なので、**カード必須にすると導入障壁になる**（銀行振込・請求書払いが主流）。

**推奨: 二択を用意する。**

1. **カード（Stripe Billing）** — セルフサーブ。starter → minimal の自動アップグレードはここ
2. **請求書払い（銀行振込）** — 月次で請求書を発行。エンタープライズと、カードを嫌う会社

請求書払いの実装で面白いのは、**自社の請求書機能がそのまま使える**こと（ドッグフーディング）。
ただし**プラットフォーム利用料と、org 内の運送請求は会計上まったく別物**なので、
テーブルは分ける（`platform_invoices`）。混ぜると税務も監査も破綻する。

### 原価がある機能は枠を持たせる

- **AI**（Anthropic / OpenAI）はトークン原価が直接乗る。`ai_monthly_tokens` をプランに持ち、
  実消費を記録して超過時は停止 or 翌月まで待機。従量課金にするのは「使ったら青天井」の
  不安を与えるので、**まずは上限方式**を推す
- **LINE** は既に `org_notification_settings.line_monthly_limit` の土台がある（migration 111）。
  プランの値を初期値として流し込む形にすれば二重管理にならない
- **SMS（OTP）** も1通数円の原価。招待の乱発を防ぐ意味でも、月あたりの発行上限を持たせる

## 5. 解約とデータ

- 解約後 **90日は削除しない**（誤操作・再契約・法定保存の要請）。この間は読み取り＋エクスポートのみ
- 90日経過で物理削除。**削除したことを監査ログに残す**（`platform_audit_logs`）
- 顔写真・免許画像は先に消す（保持理由が消滅するため。§2-5 のガードレール⑤）
- エクスポートは解約前に必ず案内する。「データが人質」に見える設計は信用を失う

---

## 6. 移行（今の本番をどうするか）

- 現行の本番 org は `enterprise` + `max_members_override = NULL`（無制限）で登録し、**挙動を一切変えない**
- `assertSeatAvailable` は `org_subscriptions` の行が無い org では**常に通す**（フェイルオープン）。
  課金の仕組みが未完成なことで既存顧客の業務が止まる方が損害が大きい
- プラン UI（/platform 側の契約管理）は Phase 2 の項目7としてロードマップにある

## 7. 元請け／下請け連携との関係

下請けが本システムを使い、元請けは**閲覧だけ**という構図が想定される（§4・別紙）。
このとき元請けの閲覧アカウントをどう数えるかで、プランの意味が変わる:

- **案1: 閲覧専用は席に数えない**（無料）。元請けにとって導入コスト0 → 使ってもらいやすく、
  「元請けが自社の下請け全体を管理したい」となったとき本契約への入口になる（成長ループ）
- **案2: 席に数える**。収益は素直だが、元請けが導入を渋って共有自体が進まない

**推奨は案1**。ただし閲覧専用アカウントは `can_view_reports` 相当の最小 capability に限定し、
共有されたコースの報告以外は一切見えないようにする（scope で遮断）。

## 8. 決めたいこと

1. **席の定義**を A（active membership 数）でよいか。運営者を席に含めるか
2. **スターターを無料にするか**。無料枠は獲得に効くが、サポート原価は無料枠から発生する
3. **年払い**を用意するか（2ヶ月分割引などのキャッシュフロー改善）
4. **AI は上限方式か従量か**。上限なら「足りない」と言われた時の増枠の売り方を決める
5. **閲覧専用（元請け）を無料にするか**（§7）
6. 価格そのもの。上表はたたき台で、原価（Vercel / Supabase / Twilio / LINE / AI）と
   サポート工数を積み上げて再計算する必要がある
