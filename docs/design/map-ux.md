# 地図UIの再設計 — 軽貨物の現場から考え直す

2026-08-10 起票。ユーザー提起:
「そもそも地図UIを、軽配送の業者がどう使うのか、運営サイドとドライバーサイド両方で検討して考え直したい」。
あわせて「駐車スペースは多角形（長方形）で指定して、**その向きに合わせて車が停まってほしい**」。

いまの `/admin/map` は「機能を足してきた地図」であって、「誰かの仕事を片づける画面」にはなっていない。
ここでは**場面から**考え直す。

---

## 1. 誰が・いつ・何のために地図を見るのか

### 運営（配車担当・管理者）

| 場面 | 知りたいこと | いまの地図で答えられるか |
|---|---|---|
| **朝（5:00-8:00）** | 誰が出勤したか。まだ来ていないのは誰か。どの車が出たか | ✗ 出勤済みは分かるが「未出勤の人」が地図に出ない |
| **日中（9:00-16:00）** | 遅れている人はいるか。どのエリアが詰まっているか | ✗ 位置が打刻時点のまま。進捗の概念が無い |
| **突発** | 事故・故障の場所。近くに応援できる人はいるか。代車はどこか | ✗ 「近くの誰か」を探せない |
| **夕方以降** | 全車帰庫したか。明日の配車のためにどこに置かれたか | △ 退勤地点は出るが、駐車区画までは分からない |

### ドライバー

| 場面 | 知りたいこと | いまの地図で答えられるか |
|---|---|---|
| **出勤時** | **今日乗る車がどこに停まっているか**（駐車場の何番か） | ✗ そもそもドライバーは地図画面を持っていない |
| **移動中** | センターのどこに着ければいいか（入口・荷受け場所） | ✗ 拠点は1点で、入口の情報が無い |
| **配達中** | 自分の担当エリアの範囲。次に行く方面 | △ エリアは引けるようになったが、ドライバーには見えない |
| **困った時** | 近くの給油所・トイレ・休憩場所 | ✗ 検索は運営画面にしかない |

**いちばん大きい気づき: ドライバー側に地図が無い。** 地図は運営の監視ツールとして育ってきたが、
**日々いちばん地図を必要としているのはドライバー**（車の場所・センターの入口・担当エリア）。
ここを埋めないと「監視されている」だけの道具になり、現場の協力が得られない。

## 2. 提案する2つの画面

### 2-1. 運営: 「今日の盤面」（/admin/map の作り直し）

**制約（2026-08-10 ユーザー指摘）**: 未出勤が確認できないのは問題。**ただし地図が小さくなるのも良くない**。
サイドリストで画面を割ると、地図の情報量が落ちて本末転倒になる。

→ **リストで画面を割らない。3つの手を組み合わせる。**

#### ① 「本来いるはずの場所」にゴーストピンを出す

未出勤の人を地図の外に追い出すのではなく、**その人が今いるべき場所**に薄いピンを立てる。
候補は既にデータがある:

- 割り当て車両の**駐車区画**（`parking_slots.vehicle_id`）＝「車は置きっぱなし」が一目で分かる
- コース／シフトの**集合場所**（`courses.meeting_place` / `shifts.meeting_place`）

空の駐車区画に灰色の人影が立っている絵は、「来ていない」を地図の言語で表現できる。
**地図を狭めずに、地図の中で解決する。**

#### ② 要対応だけの細いストリップ（1行）

地図の上に重ねる薄い帯。**何も無ければ出さない**。

```
⚠ 未出勤 2人  山田 太郎 / 佐藤 次郎        [ 一覧 ]
```

タップで展開 → 半透明のオーバーレイ（**地図を押し縮めない。上に重ねる**）。

#### ③ 行から即アクション（ワンタップ電話）

未出勤への対応は「電話をかける」で始まる。展開した行に置くのは:

- **電話**（`tel:` リンク。スマホならワンタップで発信）
- LINE（`line://` / 友だち追加済みなら通知送信）
- 代走を探す（近くにいる稼働中のドライバー＝将来のD）

電話番号は PII なので **`can_view_members` を持つ人にだけ**出す（名簿と同じ扱い）。

### 2-2. ドライバー: 「今日の道具」（mobile に新規）★リアルタイムGPS導入後

**前提（2026-08-10 ユーザー判断）**: これは **mobile アプリの機能**であり、
**リアルタイムGPS（mobile P2）が入ってから**着手する。いま作っても位置が打刻2点しか無く価値が出ない。

また、番地・表札まで確認できる精度が要る場面（郵便局系の配達など）があり、
そこは **ゼンリンAPI の導入**が前提になる。Mapbox の地図では番地レベルの表示に限界がある。

**運営の地図の縮小版を作らない。** ドライバーが必要なのは俯瞰ではなく、次の3つだけ。

1. **今日の車がどこにあるか** — 駐車場の区画番号＋そこまでの道順（外部地図アプリへ渡す）
2. **センターの入口** — 「◯◯センター 荷受けは北側シャッター」まで含めて
3. **担当エリア** — 自分のコースの面。今日の範囲が視覚的に分かる

加えて「近くの給油所」だけは持たせる価値がある（給油は毎日発生し、経費精算にも繋がる）。

## 3. 駐車区画のモデル（要望: 向きに合わせて停める）

拠点の中に**区画が複数ある**（「サンパルク伏見桃山 12番」）。これは `map_places` の
1行では表せないので、**区画を別テーブルにする**。

```sql
CREATE TABLE parking_slots (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id     uuid NOT NULL,
  place_id   uuid NOT NULL REFERENCES map_places(id) ON DELETE CASCADE, -- どの駐車場か
  label      text NOT NULL,          -- 「12番」
  geometry   jsonb NOT NULL,         -- 矩形（GeoJSON Polygon・4点）
  bearing    real NOT NULL,          -- 車体の向き（度・北=0）。矩形の長辺から自動算出
  vehicle_id uuid REFERENCES vehicles(id) ON DELETE SET NULL, -- 定位置が決まっているなら
  created_at timestamptz NOT NULL DEFAULT now()
);
```

- **人に向きを指定させない**（2026-08-10 ユーザー判断: 「向きまで指定させますか？その時々でしょうし」）。
  矩形を描けば**長辺の方向が自動的に車の軸**になる。前後どちら向きに停まっているかまでは決められないが、
  **区画に沿って収まっていれば十分**（180度逆でも実用上の違和感は小さい）
- 将来 GPS/モーションが入れば、入庫時の進行方向（heading）から前後を推定して精度を上げられる。
  それも「推定であって指定ではない」を保つ
- 車両を描くとき、その位置が区画の中なら **`model-rotation` に区画の `bearing` を使う**。
  区画外なら進行方向（GPS の heading）、それも無ければ既定の向き
- 区画に `vehicle_id` を持たせると「◯◯号車の定位置」が表現でき、**ドライバーの「今日の車どこ？」に直接答えられる**
- 描画は配達エリアと同じ `@mapbox/mapbox-gl-draw`（矩形モードは自前で「2点で長方形」を作ると楽）

**なぜ大事か**: 航空写真に重ねたとき、区画に対して斜めに車が刺さっていると一気に嘘くさくなる。
逆に区画にぴたりと収まっていると「本当にそこにある」感じが出る。デジタルツインの説得力は
こういう細部で決まる。

## 4. 段階

| 段階 | 内容 | 効く相手 |
|---|---|---|
| **A** | 運営: 左リスト主役の再構成（未出勤・遅延を地図の外に出す） | 運営（毎朝） |
| **B** | 駐車区画（`parking_slots`）＋車の向き合わせ | 両方 |
| **C** | ドライバー地図（今日の車・センター入口・担当エリア） | ドライバー（毎日） |
| **D** | 「近くの誰か」検索（応援・代車の割り当て） | 運営（突発時） |
| ~~E~~ | ~~進捗（何件配ったか）を地図に乗せる~~ → **やらない**（下記） | — |

**C（ドライバー地図）がいちばん費用対効果が高い**が、**リアルタイムGPS の後**（上記 2-2）。
先に着手できるのは **A（未出勤の可視化）と B（駐車区画）**。

### 進捗の地図表示は「やらない」（2026-08-10 判断）

**構造的に不可能**なため、案として落とす:

- **ヤマト・Amazon はそれぞれ独自アプリ**を使っており、配達の進捗はそちらに入る。こちらからは見えない
- 郵便局系は1軒ずつ調べる運用で、GODOOR などゼンリン連携アプリを使う。**ゼンリン導入が前提**になる
- ACE CREATION はしばらくヤマトがメインなので、**自社アプリでの進捗管理は成立しない**

「取れないデータを前提にした画面」を作らないこと自体が設計判断。

## 5. 決まったこと / 残る論点

**決まった（2026-08-10）**

- ドライバー地図は作る。ただし **mobile アプリ機能・リアルタイムGPS の後**。番地/表札の精度が要る場面は
  **ゼンリンAPI の導入**が前提
- 駐車区画は作る。ただし**向きは人に指定させない**（矩形から軸を自動決定。前後は問わない）
- **進捗の地図表示はやらない**（各社の独自アプリに閉じており構造的に取得できない）
- 運営画面は**リストで地図を割らない**。ゴーストピン＋細いストリップ＋オーバーレイで解決する

**残る論点**

1. ゴーストピンの立ち位置は「駐車区画」と「集合場所」のどちらを優先するか
   （車が置きっぱなしなら区画、そもそも車が無いコースなら集合場所）
2. ワンタップ電話をどの権限に出すか（`can_view_members` 想定でよいか）
3. ゼンリンAPI の導入判断（コスト・契約形態。ドライバー地図の価値を決める分岐点）

## 6. 「場所」の意味を整理する（2026-08-10 ユーザー提起）

ユーザーの言葉:「駐車位置含め**稼働開始を押す場所**を『集合場所』とするのが良さげ。
センターなどのその後行かないといけない場所は、また別で」。

これは**モデルの整理**として重要。いまは `courses.meeting_place` が文字列1つで、
「出発地」と「行き先」が混ざっている。分けるべき:

| 概念 | 意味 | 具体例 | データ |
|---|---|---|---|
| **出発地**（＝稼働開始を押す場所） | その日の業務が始まる場所。ふつうは車の駐車位置 | サンパルク伏見桃山 12番 | `parking_slots` / 単発なら `map_places` |
| **立ち寄り先** | 出発後に行く場所。荷受け・積込 | ◯◯センター（荷受けは北側シャッター） | `map_places`（順序付き） |

- **ゴーストピン（未出勤）は出発地に立てる**（＝駐車区画。車が無い単発案件なら集合場所）。ユーザー判断どおり
- 名称の候補: 「出発地」「起点」「始業場所」。**「集合場所」は複数人が集まる語感**があり、
  1人で駐車場から始まる実態と少しズレる → **「出発地」を推す**（決定は保留）

## 7. 遅刻の予兆を検知して通知する（ユーザー要望）

「駐車位置と集合時間から計算して、稼働開始していないドライバーに通知。運営にも遅刻の可能性を連絡」。

**成立する前提**: 勤務時間外は GPS を取らない方針なので、**始業前のドライバーの居場所は分からない**。
したがって「あと何分で着くか」は計算できない。計算できるのは
**「出発地を何時に出れば立ち寄り先の時刻に間に合うか」**＝出発の期限。

```
立ち寄り先の到着時刻（センター 8:00）
  − 出発地→立ち寄り先の所要時間（20分）
  = 出発期限 7:40
      ↑ この時刻までに稼働開始（QR打刻）が無ければ「遅れる可能性」
```

- 所要時間は ①コースに手入力（確実・運用が楽）②Mapbox Directions で自動見積り（初回だけ引いてキャッシュ）
  のどちらか。**①で始めて、必要なら②を足す**
- 通知の段取り:
  - **T−15分**: ドライバーへ「そろそろ出発の時刻です」（押し忘れ防止も兼ねる）
  - **T+5分**: ドライバーへ再通知
  - **T+10分**: **運営へ「遅れる可能性」**（ここで初めて運営を煩わせる）
- 既存の通知基盤（`notification_deliveries` / LINE / Web Push）に乗せる。判定は cron（5分間隔・朝の時間帯のみ）
- **誤検知を出さない工夫**: 希望休・欠勤登録がある人は対象外。既に稼働開始していれば当然対象外。
  1日1回だけ通知（何度も鳴らさない）

## 8. ゼンリンAPI は現時点で見送り（2026-08-10 判断）

概算: **初期 40万円弱＋月額6万円程度＋従量**。ユーザー判断は
「現時点で回収が容易に見込める金額ではない」。

- したがって**番地・表札レベルを前提にした機能は設計に入れない**
- ドライバー地図は Mapbox の精度で成立する範囲（車の場所・センターの入口・担当エリア）に絞る。
  この3つは番地精度を必要としない
- 郵便局系のコースを本格的に取る、あるいは複数社で費用を分担できる形（プラットフォームとして提供し
  利用社で按分）が見えた時点で再検討する
