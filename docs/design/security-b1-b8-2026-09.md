## B-6: 切替を止める条件

11所属すべてに電話番号の保存はあるが、保存されているだけでは本人確認済みではない。ユーザー指定により、個別案内の配信ではなく日報 `/submit` に本人向け案内を追加した（未公開）。その場でSMS確認→Passkey登録へ進め、日報の入力と提出は妨げない。勤務予定・稼働実績がなくても案内し、実際の利用停止の認可は維持する。現在のセッションや、既存の正式な招待/本人確認手順で移行する。未確認の番号を自動で検証済みに変更したり、復旧ログインの条件を緩めたりはしない。対象者の名前・番号は文書へ転記していない。

2026/09/17 11:15 JSTの読み取り専用照合では、使用済み招待記録から所属へ照合できたDRIVER 7名（active 6 / pending 1）はSMS確認済み7、Passkey登録0。招待APIはSMS確認を必須にするがPasskeyの登録完了は保証していない。使用記録が残らない既存所属の再参加・共有参加コード等はこの集計の対象外で、全訪問者の集計ではない。

- 集計SQL: `scripts/db/audit/pin-retirement-readiness.sql`。件数のみを返す。
- `167_retire_driver_pin.sql` は移行不足を検知するとハッシュ更新前に例外で停止。移行済みの場合でも削除対象はDRIVER/PENDINGだけとし、ADMIN等のパスワードは残す。

## B-7: 本人確認と鍵の管理

`strongAuthAt`/`strongAuthMethod` をOTP/Passkey成功時だけJWTへ入れる。更新APIは元の時刻を保持する。再確認トークンは5分・本人/所属/driver/世代/現在のBearerセッションに固定し、ブラウザのメモリだけに保持する。登録options/verifyと削除APIがサーバーで毎回検査する。

- SMSの再確認先は本人の検証済み番号だけ。リクエストの任意番号は使わない。
- 既存利用者の初回SMS確認も、本人の保存済み番号に限定。電話更新競合は409。運営権限を使った自分自身の番号変更/解除も拒否する。
- Passkeyの再確認は自分のcredential・UV必須・challengeの本人/セッション結合・一度だけの消費・counterの条件付き更新を検査。
- RPC166はservice_roleだけ実行可能。所属を再確認し、identity行ロックで鍵の同時削除を直列化。SMSが未確認なら最後の鍵を消せない。
- 鍵変更とインボックス通知を同じDBトランザクションで保存。通知保存が失敗した場合は鍵変更も取消。確定後に既存LINE/Pushへ配信し、外部配信失敗でも保存済みの本人通知は残る。SMSの変更通知を新設したわけではない。
- `/me` と `/admin/account` で共通 `PasskeyManagement` を使用。追加・削除確認・読み込み失敗・取り消し・再試行を用意。最新のUI指示に合わせ、見出しや操作と重なる説明文を削除した。

```sh

```

- `/preview/admin/account?scenario=empty`: 本番 `admin/account/page.tsx` と共通Passkey管理をそのまま使用。模擬SMSは `123456`。誤コード→訂正、追加→削除、取り消し、保存失敗→再試行を確認。

## 公開順と戻し方

1. 利用者移行とモバイル配布の完了条件を確認する。先にB-7/B-8だけ公開するなら専用差分へ切り分ける。
2. 対象を選別した公開差分でCI・型・所属検査・ビルド・CSP下の帳票/地図/OCRを確認する。既存の公開GitHub同期の送信承認待ちは別記録を参照。
3. **166を先に適用してからB-7のWebコードを公開**する。RPC未適用だと鍵保存は失敗する。新RPCは旧Webに影響せず、障害時はWebを直前の既知良好な版へ戻せる。保存済みの鍵・通知を消して戻さない。
4. B-6は移行不足0と旧モバイル移行を確認後、再度167のガードを通してWeb/API/配布を切り替える。167の適用後、漏れていた利用者の救済に旧PINを復活させず、正式なSMS/本人確認手順を使う。
5. 本番の正規利用者/未認証/停止/再確認/保存失敗を確認し、初めて該当項目を本番完了に更新する。

CSPの根拠: [Next.js公式 CSP/nonceガイド](https://nextjs.org/docs/app/guides/content-security-policy)。nonceは動的描画が前提で、管理画面のキャッシュ方式にも影響する。
