# 日報をスクリーンショット・画像から提出する

2026/09/17 ユーザー追加要望。RIMG-2（原本提出・保存基盤）を同日に実装し、2026/09/19 に RIMG-1・RIMG-3（様式の設定と読み取り）と RIMG-4（管理の確認）を実装した。**migration 169 / 181 はいずれも本番未適用**。モバイル（RIMG-5）は未着手。

## 方針

既存の件数入力に「画像から入力」を追加する。ヤマトの配完個数表などを選び、読み取った日付・件数を確認して提出する。画像を選ぶ前に報告形式を細かく決めさせず、当日のコース・荷主と画像の見出しから候補を絞り、不明な場合だけ選択を求める。既存の手入力は維持する。

**原本の提出とOCRの成功は別**。読めない画像も原本を保存でき、日報は「原本提出済み・件数確認待ち」を区別する。読み取れない値を0件で埋めない。集計・報酬・請求へ反映するのは本人が確認して確定した値だけとし、確認待ちを通常の提出完了として扱わない。

## 既存実装との接続

- Webの土台: `apps/web/src/app/(user)/report/page.tsx`、`/api/reports/v2`、`/api/me/report-form`、`server/reports/courseReportFields.ts`。荷主/コースごとの既存項目・単位へOCR結果を対応付ける。
- 添付の土台: `/api/reports/attachments` と `server/reportKinds/attachments.ts`。現在は「諸報告」の非公開添付（PDF/JPEG/PNG）、内容形式の検査・ランダム名・上書き禁止を持つ。日報との原本関連付け、日時の取得元、ハッシュ、OCR履歴は未実装。既存の「報告削除時に添付を消す」処理を原本保持へそのまま流用しない。

- プレビューは本番日報ページと管理の日報詳細を再利用し、架空画像・架空OCR応答で作る。実際の配完表を公開fixtureへコピーしない。

## 原本と日時

アップロード時に受領したファイルのバイト列を再圧縮・回転・切り抜きせず非公開保存する。縮小表示用とOCR用の画像は派生物として別にする。「原本」はハコ虎が受領したファイルを指し、端末や共有元ですでに編集されたかどうかを保証する言葉にはしない。

| 記録 | 取得元・扱い |
|---|---|
| 受領日時 | サーバー時刻。常に記録。画像作成日時・報告対象日と混同しない |
| 画像の作成日時 | 取得できたEXIF/画像内メタデータ、または写真ライブラリの作成日時。値・取得元・タイムゾーン/不明状態を保存 |
| ファイル更新日時 | Webの `File.lastModified` など。作成日時の代用にはしない |
| 画像に記載された対象日 | OCRの候補値と本人の確認後の値を別に記録 |
| 原本の属性 | サーバー計算のSHA-256、サイズ、検出MIME、画像寸法、元ファイル名、保存ID、提出者・所属・対象日報 |
| 確認履歴 | OCRの抽出値・テンプレート版・修正後の値・確認者・確認時刻 |

作成日時を取得できないスクショは「不明」のまま受け付ける。現在時刻を作成日時として捏造しない。Webのファイル選択では写真ライブラリの日時を必ず取得できるとは限らない。ネイティブでは選択画像のメタデータ取得を検証し、日時のためだけに写真ライブラリ全体の権限を必須にしない。

Appleの写真作成日時は変更可能な属性であり、画像内メタデータも信頼済みの証明ではない。ハッシュは**受領後に同じファイルか**の照合に使い、撮影日時や報告内容の真実性を保証しない。

## OCRと確認画面

1. 「画像から入力」→スクショ/写真を選択。原本を保持して送信待ち状態を出す。
2. 荷主・コースと見出しからテンプレート候補を特定。ヤマトの配完個数表を最初の対応候補とする。
3. 見出し・表の罫線・相対位置で読む範囲を絞る。固定ピクセル座標だけに依存せず、画面サイズ・倍率・余白・テーマ・版を検査する。
4. 配完・持出・不在・返品などを混同しない。日別/累計、件数/個数、便・コース、表の合計と明細を確認する。複数枚の重複部分を単純加算しない。
5. 原本と抽出値を見比べ、必要な値だけ直して提出。読み取り失敗・未対応形式では手入力または確認待ちへ。OCRの内部処理説明を常設しない。

テンプレートは版を付け、確定済み日報を再OCRで自動上書きしない。同じ原本の再送は同じ提出要求として扱い、二重日報・二重集計を防ぐ。別日・別人への原本流用や日付不一致は要確認とし、画像の日時だけで提出拒否・不正判定はしない。

## 保存・権限・復帰

- 原本の保存IDをサーバーで発行し、本人・所属・日報への関連付けを検証する。他人の添付パス指定、別会社での流用、署名URLの無認可発行を拒否する。管理画面の閲覧/書込権限も既存と揃える。
- 原本を差し替えず、訂正は新しい提出版を追加して旧版との関係を残す。誰が訂正したかと集計への採用版を記録する。
- アップロード途中・OCR中・送信失敗・オフラインを区別し、再試行で原本や提出が増殖しない。未提出の一時ファイルは猶予を設けて掃除し、提出済み原本は別の保持方針を適用する。
- 原本の保存期間、訂正/削除の権限、個人情報を含む画像の閲覧範囲は実装前に決定する。「原本を残す」を無期限保管と決めつけない。

## 2026/09/19 実装: 様式を設定できるようにする（RIMG-1・RIMG-3）

**migration 181 は本番未適用。** 様式が1つも無い間は従来どおり手入力のままで、画面の見た目も変わらない。

### 決めたこと: 形式はコードではなくデータにする

実サンプルを待って「ヤマトの配完表を読むコード」を書くのをやめ、**どの画面のどこにどの数字があるかを管理画面で決める**形にした。形式が増えても、ズレても、コードを書かずに直せる。

| 心配 | 対処 |
|---|---|
| 形式が増える | 様式は `report_image_templates` の行。管理画面で見本に枠を引いて報告項目へ結び付ける |
| 画面サイズが違う | 位置は固定ピクセルで持たない。見本と一致した語から倍率とずれを推定して枠を動かす |
| トリミングされている | 同上。見出しが切れた項目だけ「未取得」にする（0で埋めない） |
| 想定と違うスクショ | 見出しの一致点数で判定。届かなければ「未対応」として手入力へ戻す |
| 画面が回って写る | 様式に向きを持たせ、角度を試して一致した向きで読む |
| 読み違い | 確度が低い読み取りは値を見せたうえで「確認」に落とす。検算の不一致も知らせる |

### 実サンプルで分かったこと（2026/09/19・ヤマトの配達集計精算書）

- **表は画面の中で90度回って表示される**（縦画面に横長の表を収めるため）。回転を直さないとOCRは何も読めない。角度を試して一致点数の高い向きを採る（実測: 90度=86%、他の角度=0%）。
- **画面全体を一度に読む方法では表の数字がほとんど取れない**。欄を切り出して読み直すと確度93〜96%でほぼ全問正解だった。読み取りは二段構えにした。
  1. 全体を読んで見出しを探し、様式を判定して「値があるはずの枠」を決める
  2. その枠だけを切り出し、拡大して数字として読み直す
- 前処理は**白黒に落とすだけ**にする。コントラスト伸張（normalize）を入れると読めなくなった。
- 端末差をならすため、1段目は長辺3000px相当まで拡大してから読む。
- 列の見出し（計A・計B・持戻C）は読み取りが不安定だった。位置は見本座標＋ずれ補正で取り、見出しは様式の判定と位置合わせに使う。
- 表の対応: 配完=「計B」列、持戻=「持戻C」列、行は宅急便個数／ネコポス個数／合計。空欄（配完入力不可・受取店引渡）は未取得にする。合計＝内訳の和で検算できる。

検証した範囲（同じ実画像から作った変形）:

| 条件 | 結果 |
|---|---|
| 原寸 | 宅急便 44/2、ネコポス 3/0、合計 47。全問正解 |
| 上下を切ったトリミング | 全問正解（見出しの欠けは要確認として表示） |
| 表の端が切れたトリミング | 全問正解（同上） |
| 1.6倍に拡大 | 全問正解 |
| 0.55倍に縮小（実機では出ない小ささ） | 読み取れず→手入力へ戻す |
| 回転違い（0/180/270度） | 一致0%→読まない |

手元で測り直す手順: `npx tsx scripts/report-image/try-read.ts <画像> --template scripts/report-image/templates/yamato-settlement.json`。**実物の画像はリポジトリに置かない**（引数でローカルのファイルを渡す）。

### 撮影日時は当てにできない

LINEを経由した実サンプルの EXIF には**撮影日時が無かった**（解像度とサムネイルだけ）。iOSのスクショはそもそも日時を持たないことが多い。よって「その日の稼働のスクショか」の判定は次の材料を重ねる方式にし、**日時が無いことを異常として扱わない**。

| 材料 | 扱い |
|---|---|
| 画像の中の日付 | 様式に「日付として読む項目」を置けるようにした。対象日と違えば要確認 |
| 同じ画像の既出 | SHA-256 で照合。別日・別人・同日二重をそれぞれ要確認にする（拒否はしない） |
| EXIF の作成日時 | **サーバーがファイルの中身から読む**（端末の申告を信じない）。取れたら対象日と突き合わせ、翌朝までは食い違いにしない |
| ファイルの更新日時 | 記録だけ。作成日時の代用にしない |

手がかりがどれも無い場合は「確認できない」状態として黙って通す（スクショでは普通のことで、それだけで不正とは言えない）。

## 2026/09/19 実装: モバイルの原本提出（RIMG-5 の一部）

`DailyReportForm` に「配完表の画像」を足した。Webと同じAPI（`/api/reports/source-images`）へ、**選んだ写真をそのまま**送る。

- **Webと違い、写真の作成日時が取れる**。`expo-image-picker` の `exif` と写真ライブラリの作成時刻を見て、EXIF→ライブラリ→不明 の順で決める（`@repo/core/logic/imageCapturedAt`・テスト付き）。取れなければ「不明」のままにし、現在時刻で埋めない。サーバーはファイルの中身からも読み直す。
- 送信後は同じ判定（使い回し・日付の食い違い）を出す。提出は拒否しない。
- multipart の送信は `@repo/core/api` の `apiUpload` に寄せ、Web と実装を1つにした（`apiFetch` は Content-Type を JSON に固定するため使えない）。

### 端末内OCRを載せるには依存の追加が要る（未決）

読み取りの二段構えは**画像の回転と欄の切り出し**が前提で、モバイルには画像加工の手段が無い。

- 実機での読み取り時間・精度は未測定。Web の tesseract と ML Kit では結果が違うため、**様式の見出しはどちらでも拾えるものを選ぶ**必要がある。

判断が要る点: 依存を足して再ビルドしてよいか。足すまでは、モバイルは「原本を残して件数は手入力」で運用できる。

## 2026/09/20 実装: 隣の欄を読んでしまわないための守り

数字が並ぶ表では、**はっきり読めた数字を、別の欄から持ってくる**のが一番危ない。OCRの確度は
「字が読めたか」しか見ておらず、**場所が正しいかは何も保証しない**。守りを重ねた。

| 守り | 何を捕まえるか |
|---|---|
| 見本との当てはまり具合（Theil–Sen＋外れ値の割合） | 表の一部だけが動く変化（列の増減・欄の入れ替え）。**中央値は動かないので外れ値の割合で見る** |
| 欄の見出し（行・列）を覚えて差分で追う | 相手の画面が変わったときに欄を追い直す。ズレが大きければ確認に回す |
| 曖昧な見出しを使わない | 「持戻」は「配完＋持戻」にも一致する。同じくらい確からしい候補が離れた場所にあるなら**見出しを使わない** |
| 欄の中心からのズレ | 切り出しが2つの欄にまたがったとき |
| 切り出しの縁に文字が掛かっていないか | 同上（隣の欄を巻き込んだ読み取り） |
| 検算（合計＝内訳） | 1か所の取り違えは、たいていどれかの式を壊す。**合わなければ関係する項目をまとめて確認に回す** |
| 読み取りの確度 | 字そのものの読み違い |
| 本人の確認（原本の枠＋欄の切り出し画像） | 上のどれも捕まえられなかった場合の最後の砦 |

**捕まえたら値は消さず、「確認」に落とす。** 読み取った値は見せたまま、確定扱いにしない。

実際に踏んだ失敗（この守りを入れる過程で発見）:

- 列見出しに「持戻」を選んだら、`配完＋持戻` の行に吸い寄せられて**隣の列（B+C）の46を持戻として読んだ**。確度96%。
  → 曖昧な見出しを使わない規則を入れ、見出しの自動提案から数字と紛らわしい語を外した。
- 見出しへ欄を「寄せる」実装にしたら、行見出しが欄の下端にある様式で欄が下へずれた。
  → 見出しの**見本での位置と今の位置の差**だけ動かす方式に直した。

様式を作るときの自動提案（`suggestAnchors`）は、欄の上と左にある語から手がかりを選ぶ。
**数字は選ばない**（日によって変わる）。**他の見出しに含まれてしまう語も選ばない**。
管理画面では選ばれた見出しをその場で外せる。

### 限界（正直なところ）

- 列見出しが読めない様式（実サンプルの配達集計精算書がこれ）では、**列方向の位置は見本座標に頼る**。
  列が増減しても見出しで追えないので、当てはまり具合・検算・本人の確認で受ける。
- 検算は様式に式を設定してあるときだけ効く。**式を1本も設定していない様式は守りが1枚薄い。**
- 最後は人が見る前提の作りにしてある。自動で日報へ入れて終わり、にはしていない。

## 2026/09/20 実装: 毎回の目視確認をやめる（機械が答え合わせする）

「数字が並ぶ表だから、毎回画像と突き合わせて確認するのか」という指摘への答え。**確認作業を人に配り続けるのは負け筋**なので、機械が自分で答え合わせできるようにした。

### 考え方: 冗長性を証拠にする

配達集計精算書には、同じ数字が別の形で何度も出てくる。

- 各行: `配完+持戻(B+C) = 計B + 持戻C` / `計A = 配完+持戻`
- 各列: `合計 = 宅急便 + ネコポス`

日報に要るのは4つ（宅急便・ネコポスの配完と持戻）だが、**15セル全部を読んで11本の式が全部閉じるか**を見る。
欄を1つでも取り違えていれば、どれかの式が壊れる。閉じたなら、取り違えていないことを機械が示せたことになる。

そのため様式の項目に `role: "check"`（**検算のためだけに読む欄**。日報には入れない）を足した。

### 何を「裏が取れた」とみなすか

式が通っただけでは足りない。**読みに迷った値どうしで辻褄が合う**ことがあるため（実際に、列が1つ消えた画面で
「4」と「7」が揃って式を通してしまう例を再現した）。そこで:

> ある項目の裏付けになるのは、**残りの参加者が全部きれいに読めている式だけ**。

これで「きれいな値がその欄の値を1つに決めている」ときだけ確定へ進む。

### 画面の出し分け

| 状態 | 本人に出すもの |
|---|---|
| verified（式が1本以上通り、全部閉じ、迷いのある欄も裏付け済み） | 数字だけ。「表の合計11本と一致」と1タップの確定。**画像は畳んだまま**（「画像で確かめる」で開ける） |
| needs_check | 理由＋原本の枠＋欄ごとの切り出し画像。従来どおり見比べて直す |

管理の「別のスクショで試す」にも同じ判定を出す。**その様式で自動確定まで行けるかが、作った時点で分かる。**

### 実サンプルでの結果（2026/09/20）

| 画像 | 読み取り | 機械の答え合わせ |
|---|---|---|
| 原寸 | 15セル全問正解 | verified（式11本・不一致0） |
| 上下トリミング | 同上 | verified |
| 端が切れたトリミング | 同上 | verified |
| 1.6倍 | 同上 | verified |
| **列を1つ削った画面**（相手のUI変更を模擬） | 一部の欄がずれる | **needs_check**（「配完入力が確かめられていません」） |

つまり**通常の提出は数字を見て1タップで終わり**、相手の画面が変わった日だけ確認を求める。

### 残る注意

- 式を1本も設定していない様式では、この省略は働かない（確かめようがないため常に確認）。**様式を作るときは各行・各列の関係を入れる。**
- 行の入れ替えは足し算では捕まらない（順序を変えても和は同じ）。行は見出しで押さえる。列は式で押さえる。
- 「毎回確認しない」は**確認を省く判断を機械が説明できるとき**に限る。理由なしで省かない。

## 2026/09/20 実装: 他社の画面を運営画面だけで追加できるか（実測）

ヤマト以外の実画面（Amazon 配達プラン概要のライト/ダーク、郵便局 追跡件数確認）で確かめた。

### できるようになったこと

| 画面の違い | 対応 |
|---|---|
| **ダークテーマ** | 画像ごと明暗を反転してから読む（Webの tesseract は黒地に白文字が苦手）。**1段目だけでなく欄の切り出しにも同じ反転を掛ける**（別々にすると切り出しだけ読めない） |
| **一覧型の画面**（左に項目名・右に数字） | 欄は座標ではなく**見出しからの相対**で読む。管理者が囲んだ枠は「見出しからどれだけ離れた場所か」として覚える（帯ごと切り出すと矢印や隣の要素を巻き込む） |
| 表型の画面 | 従来どおり見本の座標＋行・列見出しの補正 |
| **数字1文字の欄** | 単独の「0」は eng 辞書で O や U と読まれる（実測: 確度87%で "U"）。**数字を入れる欄に限り**短い綴りを数字へ読み替える |
| 見出しの誤読 | 管理画面で見出しの文字を**その場で直せる**ようにした（自動提案が崩れて拾えないことがある） |

Amazon はライトで作った様式のまま**ダークでも読めた**（完了・問題とも一致）。
**ひな形は骨組みでしかない。見本画像を登録して初めて安定する**（見本の語が位置合わせの土台になる）。

### できなかったこと: 端末の画面を撮った写真

郵便局の追跡件数確認は**別の端末の画面をカメラで撮った写真**で、現状では安定して読めない。

- 行の左の項目名と右の数字が同じ高さに来ない（遠近のゆがみ）。見出しの自動提案も位置合わせも崩れる。
- 文字が滲み、実行するたびに「受入」が別の綴りに読まれる。見出しが安定しない。
- 傾き補正（数度）は入れたが、**ばらつきの大きい推定は使わない**規則にしてある。写真のゆがみは単純な回転では直らないため、これだけでは足りない。

→ この形式は「読めません・手入力」に落ちる（原本は残る）。まともに対応するなら**画面の四隅を見つけて台形を正す処理**が要る。未実装。

### 処理時間（Mac・開発機での実測）

| 画面 | 1段目（全体を読む） | 2段目（欄の切り出し） | 合計 |
|---|---|---|---|
| ヤマト 配達集計精算書（15欄） | 504ms | 97ms | **0.6秒** |
| Amazon 配達プラン概要（3欄） | 536ms | 21ms | **0.56秒** |

- 読み取り部品の起動は日本語 167ms・英数 78ms（言語データは自サイト配信・計6.2MB。日報画面を開いた時点で先読みしている）。
- 2段目は欄の数に比例するが軽い（1欄あたり5〜10ms）。**重いのは1段目**。
- 1段目の解像度は長辺3000pxが下限。2400pxまで落とすと**ヤマトもAmazonも読み違えが出た**ので、速度のために落とさない。
- 画面の向きが分からないと最大4方向試す。**様式に向きを持たせてあるので通常は1回**で済む。
- 原本の送信と読み取りは**同時に走らせる**（送信の待ち時間ぶん読み取りが遅れない）。

**その日の報酬見込みには影響しない。** 読み取りは画像を選んだ時点＝日報を送る前に終わっており、送信後の処理は一切変わっていない。

スマホ実機は未計測。同じ wasm を使うため、端末性能なりに数倍かかる見込み（要実測）。

## 2026/09/20 実装: コース単位で目視確認を省く（migration 182）

Amazonのように**件数が報酬に効かない（日当の）コース**では、読み取った件数を毎回画像と見比べる価値が薄い。
コース単位で確認を省けるようにした。ただし**「裏が取れない」と「食い違っている」は別物**として扱う。

| 判定 | 意味 | 確認 |
|---|---|---|
| verified | 表の中の関係が閉じて**証明できた** | **設定に関わらず省く**（1タップも不要） |
| unproven | 悪い兆候は無いが、突き合わせる材料が無い（画面に合計が無い等） | **コースの設定で省ける** |
| suspect | 合計が合わない／範囲外／裏付けの無い怪しい読み | **設定に関わらず本人に見せる** |

加えて、必須の欄が読めていない（`incomplete`）ときは、設定に関わらず本人に入力してもらう。
判定は `canSkipReview`（`@repo/core`）に集約してあり、Web・モバイルで同じ。

- 設定: コース編集の「画像の件数を確認なしで入れる」（`courses.report_image_auto_fill`）。
- 省いたときは日報のフォームに値が入り、「画像から入力しました（完了 1）」とだけ出す。**送信するのは本人**なので、値は送信前に必ず画面に出ている。
- 読み取りの記録は省いた場合も残る（採用版として保存）。管理の「画像の確認」から後追いできる。

この設定は**報酬に効く件数のコースでは使わない**前提。効くコースでは証明できた読み取りだけが自動で通る。
