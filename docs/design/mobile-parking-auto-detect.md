# モバイルの駐車位置 自動特定（端末の位置情報＋motion）

2026-09-08 起草。ユーザー方針: **モバイルの日報では Web のような「置き場所の候補を選ぶ」UI は出さない**。端末の位置情報と motion（停車・降車の検知）から駐車候補を保持し、本人の確認後にWeb 日報と同じ保存口（`vehicle_positions` の申告行）へ流す。Web 側の Phase 1 は [daily-report-parking-foundation.md](daily-report-parking-foundation.md) を正本とし、本書はモバイル側の「特定→保存」の設計。

## 2026/09/17 更新: 自然な確認・撮影への流れ

ユーザー要望: 位置情報を送信して駐車位置を記録する。motion等で候補を検知し、「駐車を完了しましたか？」という通知から確認・撮影へ進める。区画に入れてから車体の左右を撮らせる負担を避ける。**設計更新のみで、検知・通知・撮影フローの実装は未着手。**

- **位置の保存APIは先行可能、自動検知・バックグラウンド通知はモバイルの配布基盤後**。全面的なモバイル移行の完了まで待つ必要はない。まず本人の「ここに駐車」で位置・精度・測位時刻を送るM1を動かし、M2/M3で確認のきっかけを補う。
- 駐車候補の検知だけで `parked` や業務終了を確定しない。配送先での降車・信号待ち・渋滞と区別する。稼働車両あり、返却先/車庫付近、停車の継続、走行→歩行の遷移などを組み合わせ、本人確認で確定する。
- 通知は返却・終業の文脈に絞る。配送中の停車ごとに出さない。同一候補は1回とし、「まだ」で候補を保留、再走行で破棄、通知を見ない場合は次回起動時の確認へ。通知のタップだけでは位置を確定しない。
- **駐車位置の写真と車体点検の写真を分離する案**。駐車後は車・区画番号・周囲の目印が分かる写真1枚を基本候補にする。左右の状態確認は安全に撮れる出庫前/返却前の点検へ寄せ、同じセッションの写真を再利用する。ただし返却前写真を返却完了後の無傷の証明とせず、点検時刻・撮影対象を区別する。既存4方向点検の義務を黙って減らさず、運用を決めてから変更する。
- 狭い区画で側面が撮れない場合は「撮影できない」理由と撮れる範囲を残す案を検証する。駐車位置の記録を点検撮影のために止めず、必要なら「点検未完了」を別に残す。撮影のための再移動は求めない。
- 生の移動履歴を常時サーバーへ送らず、セッション内の候補を端末で保持する。終了・取消・ログアウトで監視と未送信通知を停止し、確認済み駐車点だけを送る。権限同意は位置/運動/通知を必要な段階で求め、拒否時は手動へ戻れるようにする。

想定フロー:

```text
返却先付近で停車・降車の候補
  →「駐車を完了しましたか？」 [確認する]
  → 車両・地図の位置を確認 [ここに駐車] / [まだ]
  → 駐車位置が分かる写真（必要な運用だけ）
  → 保存済み / 送信待ち
```

通知から開いた時点で車両・稼働セッション・候補の鮮度を再検証する。家に帰ってから終了した場合、現在地を駐車位置として黙って採用せず、稼働中の候補と時刻を出す。古い候補しかなければ未確定または地図訂正にする。

### SDKの再確認

Expo 57の現在の `expo-location` には `getMotionActivityAsync` / `watchMotionActivityAsync` が存在することをインストール済みソースと公式資料で確認した。従来の「Expo標準には活動認識がない」は訂正。ただし**motion監視は前景のみ**で、画面を閉じた後の駐車通知をこれだけで保証できない。バックグラウンド位置情報の権限・OS制約・必要なネイティブ実装は別に検証する。端末の生加速度だけを常時JSで監視する設計にはしない。

- [Expo Location: motion、バックグラウンド制約](https://docs.expo.dev/versions/latest/sdk/location/)
- [Apple CMMotionActivity](https://developer.apple.com/documentation/CoreMotion/CMMotionActivity?language=objc): `automotive` と `stationary` は信号待ちでも同時にtrueになり得る。駐車・降車の確定証拠にはしない。

## 0. 守ること（既存の決定）

- **勤務時間外は位置情報を取らない**（ユーザー指示・[mobile 撮影フロー] 2026-08）。取るのは稼働セッション中（QR で稼働開始〜業務終了）だけ。
- 逆ジオコーディングはしない（[parking-location-flow.md](../parking-location-flow.md) §1）。名前は登録済みの `map_places`／`parking_slots` から引き、当たらなければ座標だけを保存する。
- 位置の正本は `vehicle_positions` に一本化する。別テーブルを増やさない（[map-board.md](map-board.md) §2-1）。
- 権限ダイアログは理由を先に自分の画面で説明してから出す（`references/principles.md` §1）。
- 日報の送信を位置の取得失敗で止めない。位置が取れなくても日報は保存し、位置は「未確定」として運営が地図で直せる（既存「車の位置を直す」）。

## 1. 何を「駐車」とみなすか

駐車＝「車が止まり、人が車を離れた」。モバイルで取れる信号は3つ。確実な順に使う。

| 信号 | 取り方 | 確度 | 使い方 |
|---|---|---|---|
| A. 業務終了の操作 | 業務終了ボタン→撮影フロー（メーター・点検）の最後 | 高（本人が「終わった」と言っている） | **Phase M1 の唯一の確定点**。ここで1回だけ高精度に位置を取る |
| B. 停車の継続 | 位置更新の速度が 1 m/s 未満のまま N 分続く（既定 3 分） | 中（信号待ち・荷下ろしと区別しにくい） | Phase M2。セッション中の「最後に止まった場所」の候補を保持する |
| C. motion の遷移 | `automotive`→`walking`（iOS CMMotionActivity／Android ActivityRecognition） | 中（本人/車両の降車の確定証拠ではない） | Phase M3。B の候補に降車らしい活動変化を加味する |

**A から運用を始められる**。ただし押した現在地を無条件に駐車位置とはしない。「ここに駐車」の確認と測位の鮮度を必要とする。B・C は離れた場所から終了する場合や押し忘れを救う候補保持で、本人の確認を置き換えない。

## 2. 精度と時刻をどう申告行へ落とすか

### 2-1. 取得

- Phase M1: `Location.Accuracy.Highest` による測位を最終確認で開始する案。既存 `apps/mobile/src/location.ts` は `Balanced`。SDKの `getCurrentPositionAsync` に `timeout` オプションはないため、期限付きの位置購読を使い、成功・8秒超過・画面離脱・セッション終了時に必ず解除する。購読開始完了がタイムアウト後になった場合も解除する。精度不足・位置なしでも日報は送れる。
- 取れた値のうち保存するのは `lat` `lng` `accuracy_m`（水平精度）`fix_at`（端末が測位した時刻）。`altitude`・`speed`・`heading` は保存しない（駐車には不要・PII を増やさない）。

### 2-2. 時刻

- `at`（駐車日時）＝ **停車の開始時刻**。M1 では測位時刻 `fix_at` をそのまま使う（業務終了時＝停車直後とみなす）。M2 以降で B の候補がある場合は、その停車の開始時刻を `at` に入れ、`fix_at` とは別に持つ。
- 送信時刻や日報の対象日 0 時へ機械的に置き換えない（[daily-report-parking-foundation.md](daily-report-parking-foundation.md) の駐車日時の原則）。`report_date` は稼働セッションの営業日。

### 2-3. 登録済みの場所へのスナップ（サーバーで行う）

端末は座標を送るだけにし、**どの車庫・区画かはサーバーが決める**（車庫マスタは会社ごとで、端末に配らない）。

1. 候補は自社の `map_places` のうち `allow_parking = true` のもの（給油所・客先など候補外の拠点には当てない）。
2. 中心からの距離 `d` と、拠点の半径 `r`（`shape='circle'` なら `radius_m`、点なら 60 m）で判定する。`d ≤ r + accuracy_m` なら当たり。複数当たる・誤差円が拠点境界をまたぐ場合は確定せず、座標と候補を保持する。
3. GPSだけでは区画番号を自動確定しない。25mの水平精度では隣接区画を区別できないため、番号写真・区画QR・本人確認を利用する。拠点の候補と区画の確定を区別する。
4. 当たらなければ `place_id = null`・`place_name = null` で座標だけを保存する。地図には点として出る（「登録外の場所」）。名前を推測しない。

スナップ結果は返却し、端末の終了サマリーに「車は 豊中センター A-1 に記録しました」と1行で出す。

### 2-4. 保存する行

`vehicle_positions` に `kind='parked'` の1行。既存列は Phase 1 のまま、次の2列を足す（migration番号は実装時に最新の空き番号を採番。160以降は既に別用途で使用済み）。

| 列 | 型 | 意味 |
|---|---|---|
| `accuracy_m` | numeric null | 端末の水平精度（m）。Web の申告・手動配置は null |
| `detected_by` | text null | `session_end`／`stop`／`motion`。自動特定の根拠。Web 申告・手動配置は null |

- `source` は既存の `report` を使う（日報と一緒に出す申告）。GPS の連続追跡が入ったら `gps` は観測（`kind='observation'`）で別に流れるので、混ざらない。
- `driver_id`・`recorded_by` は本人。`client_key` は **稼働セッション ID＋`:parked`** にして、再送・遅延送信で上書きする（Phase 1 の `(org_id, vehicle_id, client_key)` 一意制約をそのまま使う）。
- `note` は端末では付けない（メモを打たせない）。

### 2-5. 信頼できない位置の扱い

| 状況 | 扱い |
|---|---|
| 位置権限なし・測位タイムアウト | 位置なしで送る。日報は保存。地図は「位置なし」に載り、運営が直す。端末には「車の場所は記録できませんでした」と1行 |
| `accuracy_m > 150` | 保存はするが拠点にスナップしない（座標だけ）。運営の地図では精度円を薄く描く |
| 前回位置から 200 km 超の移動 | 保存はする。運営の地図で「要確認」を付ける（`detected_by` と距離から表示側で判定。DB には持たない） |
| 車両なしの日報 | 位置を取らない（Phase 1 と同じ） |

## 3. 端末側の流れ（Phase M1）

```
業務終了ボタン → CaptureFlow（メーター → 点検 → 日報フォーム）
                                                  │
                                    送信の直前に測位（8 秒・裏で）
                                                  │
                    POST /api/reports/v2 { items, parking: { vehicleId, status:"parked",
                       coords:{lat,lng,accuracyM,fixAt}, detectedBy:"session_end", clientKey } }
                                                  │
                          サーバーがスナップ → 応答 { parking: { placeName, slotLabel } }
                                                  │
                     終了サマリー「車は 豊中センター A-1 に記録しました」  [ 違う ]
```

- 測位は日報フォームの表示と同時に裏で始め、送信時に結果を添える（待たせない）。
- **[ 違う ]** は候補一覧ではなく、地図で現在地ピンをドラッグして置き直す1画面（Web の「車の位置を直す」と同じ保存口 `POST /api/reports/v2` の再送・同じ `client_key` で上書き）。ここでも名前は付けさせない。
- 権限は初回だけ、業務終了の直前に「車の場所を自動で記録するために、業務終了のときだけ位置情報を使います」を自分の画面で出してから OS ダイアログを出す。拒否されても業務終了は続く。

## 4. Phase M2・M3（補強）

- **M2 停車の保持**: 前景だけなら `watchPositionAsync`、バックグラウンドも使う場合は権限・設定を整えた `startLocationUpdatesAsync` を使う。速度と停車継続時間の閾値は実機で調整し、3分等は仮値として扱う。最後の停車候補を端末に保持し、本人の確認後に採用する。`detected_by='stop'`、`at`＝停車開始。セッション終了で必ず止める。
- **M3 降車候補の検知**: Expo 57の `watchMotionActivityAsync` を前景で評価する。バックグラウンドで必要な動作は同APIの範囲外なので、OSの位置イベントやネイティブ活動認識との組み合わせを別途実機検証する。アプリ終了・省電力・通知拒否でも必ず通知できるとは扱わず、次回起動時と手動操作を残す。採用前に追加ライブラリを導入しない。
- どの段階でも、勤務時間外・セッション外では位置を取らない。

## 5. サーバー側の変更点

- `server/reports/parking.ts` の `parseParkingReport` に `coords`（`lat` `lng` `accuracyM` `fixAt`）と `detectedBy` を追加。`placeId`／`placeName` と `coords` は排他ではなく、`coords` だけの申告を許す（`kind='parked'` は「登録車庫か場所名」必須だったので、**座標だけの申告**も有効にする。新規migrationで CHECK を「車庫・場所名・座標のいずれか」に緩める）。
- `saveParkingReport` にスナップ（§2-3）を追加。純粋関数 `snapToPlaces(coords, places, slots)` を `server/reports/parkingSnap.ts` に切り出してテストする（当たる／半径外／精度で区画を決めない／`allow_parking=false` は無視／複数拠点で最寄り）。
- 応答に `parking: { placeName, slotLabel, snapped: boolean }` を返す。
- 地図 API（`/api/admin/map/vehicles`）は既に `kind`／`place_name` を返す。`accuracy_m`・`detected_by` を追加し、運営の地図の詳細に「自動記録（精度 12 m）」と出す。

## 6. 検証

- 単体: `snapToPlaces` の表（§2-3 の各条件）、`parseParkingReport` の座標だけの申告、`client_key` 上書き。
- 隔離プレビュー: `/preview/admin/map` の fixture に `detected_by='session_end'`・粗い精度の車を足し、詳細の表示を確認。
- 実機: 屋内（精度 50〜150 m）、権限拒否、機内モード、8 秒タイムアウト、業務終了を自宅で押す（自宅を自動確定しない）、配送中の短い停車、画面ロック・強制終了、通知拒否・二重通知、狭い区画・暗所の写真。
- 本番: 日報側の保存が先、位置は後（Phase 1 と同じ順）。位置の失敗で日報を落とさないことをログで確認。

## 7. 決めておきたいこと

1. 点の拠点の既定半径 60 m でよいか（センターの敷地は円で登録してもらう前提）。
2. 区画番号の確認方法（写真/QR/本人確認）。GPSだけで隣接区画を確定しない。
3. M1 の [ 違う ] を地図ドラッグにするか、当面は「運営に伝える」（何もしない）にするか。
4. `detected_by` を DB に持つか、`source='device'` を新設して区別するか。本書は既存 `source='report'`＋`detected_by` 列の案。


## 2026/09/17 実装: 座標だけの駐車申告（PARK-M1のサーバー側・本番未適用）

**migration 170 は未適用**。適用するまで座標付きの申告は CHECK 制約に当たるため、モバイルから送らない。`accuracy_m` / `detected_by` は端末の測位から来た申告のときだけ列に載せるので、未適用の本番でも従来の Web の申告・手動配置は影響を受けない。さらに、測位付きの申告が保存できなかった場合は例外にせず `parkingUnavailable` を返す（位置が記録できないことで業務終了の操作を止めない）。本人が車庫を選んだうえで端末も測位していた場合は、座標を拠点の代表点のままにして精度は持たせず、`detected_by` だけを残す（代表点に端末の精度を付けると別の意味になる）。

| 実装したもの | 場所 |
|---|---|
| `vehicle_positions.accuracy_m` / `detected_by`、申告の CHECK 緩和、`map_latest_positions` の列追加 | `supabase/migrations/170_parking_device_coords.sql` |
| 座標 → 拠点のスナップ（純粋関数） | `apps/web/src/server/reports/parkingSnap.ts`（`parkingSnap.test.ts`） |
| `coords` / `detectedBy` の検証、スナップ後の保存 | `apps/web/src/server/reports/parking.ts` |
| 型 | `packages/core/src/types/dailyReport.ts`（`ParkingCoordsReport` / `ParkingDetectionSource`） |
| 応答 | `POST /api/reports/v2` が `parkingPlaceName` を返す（終了サマリーの1行） |
| 地図 | `/api/admin/map/vehicles` の `position.accuracyM` / `detectedBy` |

決めたこと（§7 の宿題への回答）:

1. **点の拠点の既定半径は 120m**（`DEFAULT_PLACE_RADIUS_M`）。本書の初期案は 60m だったが、運営が地図で札を離すときのスナップが既に 120m を使っており、「その拠点の範囲」の定義を2つ持ちたくないため揃えた。狭めるなら両方を同時に変える。
2. **区画は座標から決めない**。`snapParkingCoords` は拠点までしか返さない（戻り値に区画を持たない）。
4. `source='report'` のまま `detected_by` 列で区別する案を採った。手動の申告は NULL。

スナップの規則: 誤差円が**1つの拠点にすっぽり収まるときだけ**確定する。境界をまたぐ（`edge`）・複数に触れる（`ambiguous`）・精度が 150m より粗い（`accuracy`）ときは確定せず、座標と候補だけを残す。精度不明は「良い測位」として扱わない。拠点が確定しても**座標は測位した値のまま**保存し、拠点の代表点で置き換えない。端末の測位から来ていない座標に `accuracy_m` を書かない。

未実装: 検知（M2/M3）、通知、撮影フロー、モバイル側の送信。位置の失敗で日報を落とさないことは Phase 1 の順序（日報が先・位置は後）をそのまま使っている。
