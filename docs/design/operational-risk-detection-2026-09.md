# 業務事故を当日前に発見するための残タスク

2026/09/15、ユーザーから「シフト表の入力ミスを当日まで誰も発見できない構造」を問題として残すよう依頼。まず調査・課題整理を行い、2026/09/17 に O-1 の一部を実装した（[実装の節](#20260917-実装-必要人数の共有本人確認未解決一覧本番未適用)）。migration 168 は本番未適用で、本番データの再集計・更新、通知送信は行っていない。

## 最優先: シフトが合っていることを事前に確かめる

今回の豊中9月後半は添付と一致したが、今後の入力の正しさや伝達完了を保証するものではない。メモから正式シフトへの反映機能は転記操作・差分確認・その操作中の競合を扱うが、予定自体の正しさは別の仕組みで検証する必要がある。同機能はローカル実装済み・本番未公開。

- **原本と正式シフトの照合**: 対象期間・会社・コース・便・人を確定し、原本の版と対応表を保存する。氏名を推測で結び付けない。入力に使った抽出結果だけを照合基準にすると同じ誤読が通るため、原本との独立した確認を残す。
- **必要人数を配置とは別に管理**: 日・コース・便ごとの稼働有無と必要人数を共有する。全員の配置が抜けた日でも不足を検知できること。空白を「休み」「未入力」「人数未確定」に区別し、未確定は正常扱いしない。現在の日別必要人数は個人メモの端末保存であり、正式シフトへの反映対象ではない。
- **本人が予定を確認する**: 日付・コース・便・集合時刻等の版に対して「確認済み／対応不可／未確認」を持つ。通知の既読とは分け、重要項目が変われば再確認が必要になる。
- **期限前に管理者へ未解決を集める**: 不一致・不足・未確認・対応不可・配車未完了を一覧に残し、担当者と解消期限を決める。前日夜が最初の照合にならない時期に確認を開始する。警告を一度閉じても、解決するまでは消さない。

完了条件は「意図的に1件抜く／別人にする／便や日付をずらす／確認後に変更する／通知を失敗させる」ケースを隔離データで作り、締切前に対象と対処者が分かること。PDF取込精度や保存成功だけを完了基準にしない。

着手時に決めること: 正式な原本と更新担当、日別必要人数の確定担当、本人確認の期限、未確認時の連絡担当と代替手段、正当な例外の記録方法。

決めたこと:

- **空白を3つに分ける**。行が無い＝未入力 / `closed`＝その日は動かない / `undecided`＝人数未確定。必要人数は NOT NULL にせず、未確定を 0 で埋めない。曜日の基準（`shift_staffing_baselines`）と日付の指定（`shift_staffing_requirements`）を分け、日付の指定が優先する。基準も指定も無い枠は日付ごとではなく枠ごとに1件だけ出す（毎日同じ警告で埋めない）。
- **配置が1件も無い日でも不足が出る**。人数の基準が配置と独立しているため、全員の配置が抜けた日を検知できる。
- **本人確認は版に対して成立する**。日付・コース・便・集合場所・集合/着車/終業時刻から版を作り、変われば確認は「要再確認」に戻る。車両は版に入れない（配車の入れ替えで再確認が頻発し確認が形骸化するため）。車両の未割当は別項目で見る。古い画面からの確認は 409 で拒否する。
- **未解決一覧は状態から毎回導く**。閉じた・見たという印を持たないので、解決するまで消えない。
- **解消期限は会社ごとの設定**（2026-09-18）。既定値はそれまでの固定値と同じ（人数・原本3日前／本人確認2日前／配車前日、先読み14日）。種類ごとに9つ設定させず、手を打つ相手が同じものを3区分にまとめた。先読みが一番長い期限より短いと期限前に一覧へ出ない日ができるので、DBのCHECKと入力の両方で拒否する。
- **原本照合は取り込み時の抽出結果が相手**（`shift_import_batches.extracted` と期間の `covers_start` / `covers_end`）。AI取り込みの適用時に読み取った全件を書き、照合は対象期間に重なるバッチだけを読む。1件抜く・別人にする・便や日付をずらす、をそれぞれ検知する。ただし同じ誤読は同じまま通るので、**原本そのものとの独立した確認を置き換えない**。
- **一覧が埋まらないようにまとめる**。「未確認」は日ごとに1件（`3人未確認`）、「配車未完了」は枠ごとに1件へ集約する。対応不可・要再確認は誰かが分からないと動けないので1人1件のまま。休みの枠にしか予定が無い人へ未確認は出さない。
- **1000行の切り詰めに当たらない**。シフト・必要人数・確認はすべて `fetchAllRows` と一意な ORDER BY で読む（順序なしのページングは「配置ゼロの日」を作り、実在しない不足を赤で出す）。

- 日付ごとの必要人数の編集（いまは曜日の基準だけ画面から編集できる。日付の例外は API のみ）。個人メモ盤の localStorage の日別人数からの移行も未着手。

## 2026/09/18 実装: 通知が届いたかを受信者ごとに残す（O-2の中心・本番未適用）

**通知を作ったこと＝伝わったこと ではない。** インボックスには必ず入るが、外向きの経路で鳴ったとは限らない。そこを受信者ごとに記録し、運営が代替連絡を取れるようにした。

直した穴:

- **Web Push の成否が受信者別でなかった**。バッチ内に1件でも成功があれば全員 `sent` と書いていたため、誰に届いていないか分からなかった。`sendWebPush` が受信者ごとの結果（送信数・失敗数・端末数）を返すようにし、配信ログもそれに従って書く。
- **LINE 未連携が記録されていなかった**（`continue` で捨てていた）。「送れなかった」ではなく**経路が無い**ことを `status='skipped'` / `error='unlinked'` で残す。会社で未設定は `not_configured`、Web Push の端末が1台も無い場合は `no_subscription`。
- **リポジトリの migration 108 が本番と食い違っていた**。本番の CHECK には `web_push` が追加済みだが 108 は `('line','push')` のままで、新しい環境に 001〜を流すと配信ログの保存だけが静かに失敗する状態だった。migration 173 で本番に合わせた。

追加したもの: 判定の純粋関数 `server/notifications/delivery.ts`（+ テスト）、`GET|POST /api/admin/notifications/undelivered`、通知画面の4つ目のタブ「届いていない」。

**再送するのは「送信に失敗」だけ**。未連携・端末なし・未設定は何度送っても届かない。さらに**「記録なし」も再送しない** — この機能より前の通知には配信ログが無く、実際には LINE で届いているものが多い。それを一括再送すると過去2週間ぶんの古い通知が端末へ連打される（外部送信なので取り消せない）。記録が無いことは届いていない証拠ではないので、運営が個別に判断する。

配信ログの保存は**チャネルごとに分けて insert** する。1行でも CHECK に当たると insert 全体が落ちるため、173 未適用の環境で web_push のせいで LINE のログまで失うことがないようにした。

本番の実データを読み取りで確認したところ、通知は 2026-07-20 の3件しか無く、配信ログもそれに対応する2件だけだった（通知機能そのものがまだほぼ使われていない）。

残り: 「通知したのに本人が確認していない」の追跡は O-1 の本人確認（`shift_plan_confirmations`）が担う。通知設定（`change_enabled`）に依存せず未確認を検知する点も O-1 側で満たしている。代替連絡の担当と手順は未決定。

## 2026/09/18 実装: 通常編集の競合検知と監査履歴（O-3の中心・本番未適用）

`/api/admin/shifts` の POST（シフト表のセル1つの割当）を RPC `assign_shift_driver`（migration 172）へ移した。

- **後勝ちを止めた**。画面で見ていた値（`expectedDriverId`）とDBの現在値を `FOR UPDATE` で押さえて照合し、違えば `40001` → API は 409 と「別の変更が保存されています」。画面は通信失敗と区別して伝え、最新を取り直す。
- **変更ログを同じトランザクションにした**。これまでは `void logShiftChange(...)` の投げっぱなしで、失敗しても保存は成功していた。
- **変更ログに便番号が入るようになった**。`logShiftChange` が `cycle_no` を渡しておらず、便を使うコースのログは全部 0 だった（`shift_change_logs.cycle_no` は migration 136 で存在していた）。
- コース・便・ドライバーが自社の有効なものかを RPC 側でも検証する（165 と同じ判定）。
- migration 172 が未適用なら従来の無条件 upsert へ落ちる（画面は止めない）。`p_expect_present=false` でも従来どおり動く。

使い捨ての一時Postgresで、空き枠への割当・期待値一致での差し替え・**期待値が古いときの拒否**・期待値なしの無条件保存・解除時の車両連動クリア・他社コース/無効な便/他社ドライバーの拒否・ログの便番号を実測した。

**方針を1つ反転した**: migration 121 は変更ログを「アプリ側でベストエフォート（失敗しても本処理は成功させる）」と定めていたが、172 では同じトランザクションに入れた。ログの欠けた変更を残さないことを優先している。代わりに `shift_change_logs` の障害が割当保存の失敗につながるので、この表に NOT NULL 列を足す・FK 先を消すといった変更は保存経路への影響として扱う。

同時に直したこと:

- **同じセルへの保存を直列化**した。「外す→別の人を入れる」を投げっぱなしにすると到達順が入れ替わり、誰も同時編集していないのに 409 が出ていた。
- **D&D の連日コピーを便に対応**させた。有効な便が1つだけならそこへ複製し、複数あるなら勝手に決めずスキップして理由を出す（従来は `cycle_no=0` の行を作っていたため、172 適用後は全件 404 になるところだった）。
- **ドライバー解除時に個別時刻も消す**（165 の「空枠の再利用」に当てるため）。ただし `import_batch_id` は残す — 取り込みの取り消しは `import_batch_id` で消すので、ここで NULL にすると手で編集した行だけ取り消せずに残ってしまう。そのぶん取込由来の空枠は 165 の再利用対象にならない。
- RPC が使えない環境（未適用・EXECUTE 権限なし）だけ従来経路へ落とす。判定はエラーコードのみで、メッセージの文面には依存しない。

知っていて残していること:

- **RPC の EXECUTE 権限が失われると、競合検知が無言で無効化される**。42501 は「migration 未適用」と区別できないため従来経路へ落とす（画面を殺さないことを優先）。`console.error` に `assign_shift_driver` を含めてあるのでログ検索で拾えるが、監視の当て先は未定。
- **409 の判別がサーバーの日本語メッセージの部分一致**。`apiFetch` が応答ボディを捨てて `Error(body.error)` にするため、`conflict: true` を画面から読めない。**サーバー側の文言が実質 API 契約**になっているので、変えるときは画面側も直す。

**配車（`/api/admin/shifts/vehicle`）にも同じ考え方を入れた**（2026-09-18）。こちらは migration が要らず、`UPDATE ... WHERE vehicle_id = <画面が見ていた値>` の条件で足りる。0行更新になったとき、枠が無いのか他の人が変えたのかを読み直して見分ける。画面側は割当と同じくセルごとに直列化し、直前に自分が保存した値を覚えて期待値にする（再取得を待たずに続けて操作しても誤検知しない）。配車ログにも便番号が入るようにした。

残り（O-3の全体としては未完）: 時刻（`/api/admin/shifts/times`）と取込（`import/apply`）には競合検知を入れていない。

## 調査で確認した関連リスク

以下はローカルの現行コードに基づく構造上のリスク。本番の事故発生・影響人数を確認した一覧ではない。優先度は発見が遅れた場合の業務影響を基準とした提案。

| ID・優先度 | 起こり得ること・現状 | 残タスク・完了の目安 |
|---|---|---|
| O-1 最優先 | 原本の誤読・転記漏れ・日付/便/人の誤りが、そのまま正式予定になる。個人メモの必要人数は正式側の共通基準になっていない | 上記の原本照合・共有必要人数・本人確認・期限前の未解決一覧を一体で設計する |
| O-2 最優先・**一部実装** | 変更通知の検知は通知履歴を基準にし、通知前の日には出ない。設定OFFなら検知自体が止まる。インボックス作成・LINE/Push配信・既読・本人の了承は別の状態 | 通知設定に依存しない未確認の検知と版による無効化は O-1 で実装。受信者別の配信記録・未連携の可視化・再送は 2026-09-18 に実装（本番未適用）。代替連絡の担当と手順は未決定 |
| O-3 高・**一部実装** | 通常のシフト/配車APIは読み取った版を条件にせず保存するため、複数管理者の更新が後勝ちになる。通常の変更ログは失敗しても保存処理が成功し、便番号も共通ログ関数に渡されない | ドライバー割当（migration 172）と配車（migration 不要）は 2026-09-18 に競合検知へ移行。ログの便番号も修正。**時刻・取込は未対応** |
| O-4 高 | 同じ車の同日利用は画面の確認で許可される。時間を分ける正当な利用はあるが、確認だけでは時間重複・引渡し未完了・実際の所在を保証しない | 使用時間、受渡し場所・期限・完了を管理し、未設定と競合を区別。配車があるだけで準備完了にしない。既存の使用不可・貸出中の拒否は維持 |
| O-5 高・対象データの確認が必要 | 単価履歴と承認時snapshotは実装済み。一方、snapshotのない旧日報は現在単価へフォールバックし、snapshotありでも現在の契約方式の影響を受ける。日額リースもコース設定から集計する。古い期間の再計算・帳票再作成時に金額が変わる余地がある | 影響する過去データを読み取りで抽出し、保存済み帳票・支払確定額との試算差分を確認。確定後の変更の扱いと再作成前後の比較を決める。今回、誤支払や二重控除が発生中とは確認していない |

### 根拠と既存対策

- O-1: `PersonalShiftMemoBoard.tsx` のlocalStorage保存・日別人数、`lib/shiftMemo/reflect.ts` の反映対象、[メモ反映設計](shift-memo-reflect-2026-09.md)。反映の追加/解除差分と未登録名の明示対応は実装済み。
- O-2: `server/notifications/pendingChanges.ts` の通知履歴基準と8日先までの検索、`api/admin/shifts/pending-changes/route.ts` の `change_enabled` 分岐。既読は `api/me/notifications/route.ts` にあるが、予定の版に対する本人の受諾状態ではない。
- O-2の配信追跡: `server/notifications/dispatch.ts` はインボックス保存後に外部配信する。同じdedupe keyの再実行は既存通知をスキップするため、この経路だけでは失敗分の再送にならない。さらにWeb Pushログはバッチ内の成功有無を各通知へ同じ状態で書くため、受信者別の到達確認には使えない。個別の配信結果と再送経路を調べて整える。通知履歴を「本人に伝わった証拠」として扱わない。
- O-3: `api/admin/shifts/route.ts` の無条件upsert、`api/admin/shifts/vehicle/route.ts` の日・コース・便・slotでのupdate、`server/shiftLog.ts` のベストエフォート保存。今回のメモ反映RPCには競合検知・ログの同時保存を入れたが、通常編集全体への適用は未実施。
- O-4: `shifts/page.tsx` の `setVehicleForDriverOnDate` は重複を確認後に許可。配車APIは使用不可・貸出中を拒否する。[受け渡しと通知の既存設計](vehicle-handoffs-and-notifications.md) も再利用する。
- O-5: migrations 138/139、`server/aggregation/load.ts` / `compute.ts`、`server/billing/invoiceDraft.ts`、`api/admin/payments/route.ts`。既存 `docs/money-handling-current.md` の「単価履歴がない」という古い記述を現状として引用しない。

## 既存の重大項目も維持する

[ロードマップ](../roadmap-2026-09.md) にある公開コードとGitHub mainの同期・アプリCI、Passkey追加/削除時の再本人確認、PIN経路の廃止準備は別軸の残タスク。9/14の確認記録に基づくため、着手時に最新の公開状況・設定を再確認する。他社データ保護・ログイン失効・認証再送防止の修正済み項目を未対応と混同しない。

今回の確認はコードレビューであり、これらの障害を本番で再現する操作や、網羅的な安全監査は行っていない。業務ルールと対象データを確かめてから個別の修正・プレビュー・回帰検証へ進む。
