# 案件記録・日払い記録

更新: 2026-08-30
状態: この固定項目案は廃止。org別の汎用フォームへ置換済み。未適用153は `docs/design/archive/153_response_records.sql` へ退避。以降は初期検討の記録として保持する。

最新方針案: [org別の記録・報告フォーム基盤](org-record-forms.md)。以下は固定項目版の実装記録であり、今後の最終仕様ではない。

## 確定した要件

- 案件と日払いの権限は分ける。
- 日払いは「誰に、いつ、どの稼働分を、いくら、どういう方法で支払ったか」の実績記録。
  例: 佐藤に6/18、6/17稼働分8,500円を銀行振込。売上との紐付けは不要。
- 案件は報告者、発生日、誤配等の案件内容、解決状況、備考・再発防止策を記録する。
  既存の報告文を貼り付けられるようにし、場所などの追加項目も扱う。
- 参照タスク「配送クレーム削減策を整理」（01a0476e-4c4b-7823-b6a4-cd2b808eb1da）を確認。
  発覚日、センター・コース、建物属性、顧客申告と配送側説明、原因、対応、再発防止、再発の有無を反映した。
  参照先の長期構想（KPI・配送ロス・点数評価等）は今回の実装範囲に含めない。

## 初期版の構成

共通の保存・検索・履歴部品を使い、画面の入口と入力項目は用途別に分ける。
自由な項目定義を持つ汎用メモシステムは作らず、第三の「その他メモ」も今回は追加しない。

| 項目 | 案件記録 | 日払い記録 |
|---|---|---|
| URL | `/admin/cases` | `/admin/daily-payments` |
| 必須 | 件名、発生日、報告者、案件種別、状態、案件内容・報告文 | 件名、支払日、支払先氏名、稼働日開始・終了、金額、支払方法、状態 |
| 状態 | 未対応・対応中・解決済み・取消 | 支払済み・取消 |
| 任意 | 関連ドライバー、発覚日、場所、建物属性、センター、コース、顧客申告、配送側説明、原因区分・根拠、対応・影響、再発防止策、再発の有無、指定/実際の時間・受渡方法、担当者、期限 | 支払方法の補足、支払対応者、備考 |
| 支払方法 | — | 銀行振込・現金・その他（補足必須） |

日払いの金額は実際に支払った額。1〜999,999,999円の整数とする。
稼働日開始・終了が同じなら単日、異なるならその期間の支払い。
依頼・承認・未払残額・分割払い計算・手数料計算は扱わない。
対象者は初期版では氏名の自由入力。未登録の応援者も記録できる。
APIは任意の既存ドライバーIDも受け付け、その場合は所属を検証して氏名をDBから確定する。
名簿選択UIやドライバー詳細への自動連携は未実装。

案件の「客原因」などは、原因区分と根拠へ記録できる。未確認・未選択も許可し、
報告文からの自動判定やドライバーの自動評価は行わない。
コース・センター・場所も初期版は文字列として記録する。

## 共通機能

- 作成、詳細表示、訂正・対応追記、取消。物理削除は設けない。
- 一覧は30件、履歴は20件ごとのページ分割。
- 件名・氏名・本文・詳細項目の部分一致検索、状態・発生日/支払日の期間絞り込み。
  対応担当者・場所・コース等も検索に含まれる。旧版と変更理由の全文検索は対象外。
- 更新時は変更理由または対応追記を必須にし、取消にも理由を要求する。
- 変更履歴に各時点の全文、版番号、記入者、記入時刻、変更理由を保存する。
- 版番号による同時更新検出。競合は409で返し、入力を保ったまま最新記録の再確認を促す。
- 新規記録のIDはフォーム表示時に1つ生成し、通信再試行でも同じIDを使う。
  二重送信は409となり、一覧で保存結果を確認する。支払先・日付・金額が同じ別支払いは許可する。
- 保存失敗ではフォームを閉じない。一覧へ戻る操作で未保存内容の破棄を確認する。
- ローカルストレージには機微な記録を保存しない。
- Web管理画面で提供し、スマートフォン幅にも対応。Expoへの追加は対象外。

## 権限

| 対象 | 閲覧 | 編集（閲覧を含む） |
|---|---|---|
| 案件 | `can_view_cases` | `can_manage_cases` |
| 日払い | `can_view_daily_payments` | `can_manage_daily_payments` |

初期付与はシステム管理者ロールだけ。他の既存ロール（経理・閲覧専用等）に暗黙には付与しない。
運用に合わせて既存のロール設定画面から個別付与する。
新規capabilityは既存のセッション同期で反映する。メニュー表示が古い場合は再ログインする。
一般ドライバーへの公開・申請・通知は追加しない。

## 保存と会計の境界

- `response_records` に組織・分類・検索用の日付/状態・JSON本体・版番号を保持する。
- `response_record_revisions` に更新ごとの全文を保持する。DBトリガーで本体と同一トランザクションに保存する。
- すべてのAPIで用途別権限とDBの所属を確認し、クエリを組織・分類で限定する。
  履歴取得も親記録の閲覧確認後に組織・記録IDで限定する。
- DBトリガーでも記入者と関連ドライバーの所属、版番号、組織・分類の不変性を検証する。
- RLS不使用の既存方針に合わせ、テーブルのanon/authenticated/PUBLICアクセスを剥奪し、service_roleによるAPI経由に限定する。
- 記入者・記入時刻・組織はサーバー/DBで決定する。
- 日払いは売上・報酬・請求・控除テーブルに一切書き込まない。振込も実行しない。
- 銀行明細との照合を保証する台帳ではないことを画面に明記する。

## 導入と検証

migration `153_response_records.sql` は2テーブル・履歴/検証トリガーを追加し、
システム管理者ロールに4つの権限を付与する。既存の金額・報告・シフトデータは更新しない。
DB未適用時は503で準備中を表示し、空データと見せかけない。
既存の未適用migrationを巻き込む一括適用は行わず、本番適用対象を別途確認する。

検証対象は、独立権限・組織越境防止・入力検証・支払日と稼働日の分離・競合・二重送信・取消理由・
未適用DBの明示・保存失敗時の入力保持・閲覧のみUI・未保存確認。
Web全体74ファイル・737テストが成功。最終UI調整後も関連49テストとTypeScript検査が成功。
DBに接続しない架空データの検証環境で、390px幅の日払い一覧・入力、1280px幅の案件入力を確認した。
実環境の画面はログイン状態の確認待ちで表示に到達できておらず、DBトリガーの実DB実行と本番での保存確認は未実施。
