# 単価の適用日・履歴・請求明細の設計

作成: 2026-08-28 / 状態: 設計（未実装）

2026-08-27〜28 の一連の事故と監査で見つかった構造的な問題への対処をまとめる。
3点は独立に見えるが、**適用日を選べるようにすると請求明細の行分割が必須になり、
その両方が正しい単価履歴を前提にする**ため、まとめて設計する。

---

## 1. いま何が壊れているか

### 1-1. 単価を変えても過去分がどうなるか分からない

単価設定画面で単価を保存すると、`course_unit_rates` / `course_fixed_rates`（現在値）が
上書きされ、`course_rate_versions` に「適用開始日 = 今日」の履歴が1件積まれる。

- **未承認の日報**: 現在値で計算されるため即座に変わる
- **承認済みの日報**: 承認時に `daily_reports_v2.rate_snapshot` へ焼き付けた値のままで変わらない

この境目が画面に一切出ない。運営は単価を直したあと、過去分が直ったのか直っていないのか
判断できない。2026-08-28 に OSA配下9コースを 157円 → 157.5円 にしたときは、
運営が画面で直すだけでは8月分が157円のままになるため、スクリプトでスナップショットを
焼き直す必要があった。

### 1-2. 単価履歴が信頼できない

`course_rate_versions.rate_data` には、保存APIが受け取ったリクエストボディがほぼそのまま入る。

- 適用開始日は「初回はコース作成日、2回目以降は保存した日」と自動で決まり、選べない
- 同じ `(course_id, effective_from)` は upsert で**上書き**される。同日に2回直すと1回目が消える
- 値の妥当性チェックが無い

実際、西宇治の `effective_from = 2026-07-31` の版は宅急便が**税抜15円**（正しくは157.5円）に
なっていた。2026-08-28 にこの履歴を遡って適用したことで、8月の売上が98万円下がる事故が起きた。
現状は「履歴を使わず現在値で焼き直す」`ignoreRateVersions` オプションで回避している。

### 1-3. 請求明細が単価ごとに分かれない

`computeCounterpartyMonthBillingDetail` の明細行のキーは
`コース × 便 × 品目 × ドライバー` で、単価は**現在の単価マスタから引く**。日付を見ていない。

月の途中で単価が変わっても、その月の個数が全部まとめられ、現在の単価1本で請求される。
「8/1〜8/25 は158円、8/26以降は157.5円」を出す手段が無い。

さらに、明細行は契約原額（税込契約なら税込額）から作られ、
総額（`systemTotal`）は集計エンジン（税抜）から作られる。壬生のように
「取引先へは税込160円、会計上は税抜145円」の二本立てだと両者は必ずズレる（8月で ¥88,971）。
これは意図どおりだが、画面でその区別がつかない。

---

## 2. 目指す状態

- 単価は「**いつからいくら**」で持つ。現在値はその射影にすぎない
- 単価を変えるとき、運営は**適用開始日**と**過去分を直すか**を明示的に選ぶ
- 請求明細は、その月に実際に適用された単価ごとに行が分かれる
- 取引先への請求（契約基準）と会計上の売上（税抜）が、画面で区別できる

---

## 3. 設計

### 3-1. 単価履歴を正本にする

`course_rate_versions` の位置づけを「保存ログ」から「**単価の正本**」へ変える。

```
course_rate_versions
  id, org_id, course_id
  effective_from date      -- 適用開始日（この日を含む）
  rate_data      jsonb     -- 正規化した単価（下記スキーマ）
  invalid_reason text      -- 値の検証に落ちた版。スナップショット生成では使わない
  created_at, created_by
  UNIQUE (course_id, effective_from)
```

適用終了日は**列で持たず、次versionの前日として導出する**。3-2 の「過去に遡ると以降を上書き」
という規則があるため版は常に一直線に並び、終了日を実体で持つと二重管理になって
不整合の元になるため。

`rate_data` は保存APIのリクエストをそのまま入れず、**保存する形を固定する**。

```jsonc
{
  "version": 2,
  "revenueRateMode": "PER_PIECE", "payoutRateMode": "PER_PIECE",
  "taxBasis": {                       // 4区分。旧 revenue_tax_basis 等は入れない
    "revenuePiece": "inclusive", "payoutPiece": "exclusive",
    "revenueFixed": "exclusive",  "payoutFixed": "exclusive"
  },
  "unitRates": [
    { "cycleNo": 0, "unitId": "…",
      "revenue": { "contract": 160, "exclusive": 145 },   // 契約額と集計用税抜を必ず両方
      "payout":  { "contract": 136, "exclusive": 136 },
      "revenueQuantityRule": { "kind": "actual" },
      "payoutQuantityRule":  { "kind": "actual" } }
  ],
  "fixedRates": [ /* 同形 */ ],
  "fixedBundle": { "requiredCycleNos": [1,2],
                   "revenue": { "contract": 17000, "exclusive": 15454 },
                   "payout":  { "contract": 11818, "exclusive": 11818 } }
}
```

**保存時の検証**（不正な履歴を二度と作らない）:

- `contract` と `exclusive` が両方あること。片方だけなら保存を拒否する
- 税込契約なら `exclusive ≒ floor(contract / 1.1)`。乖離が5%を超えたら警告して確認させる
  （税込160円/税抜145円のような意図的な差は許すが、税抜15円のような明らかな誤りは弾く）
- 同じコースの直前versionと比べて単価が±50%を超えて動くときは確認を挟む

**移行**: 既存の `course_rate_versions` は version 1 として読めるようにしつつ、
値の検証に通らない版には `invalid = true` を立て、スナップショット生成では使わない。
西宇治の7月末版のような誤値はここで隔離する。

### 3-2. 保存時に適用日と過去分の扱いを選ばせる

単価設定モーダルの保存時に、以下を選ぶ。

```
この単価はいつから？
  ( ) 今日から              … 既定
  ( ) 日付を指定            … [2026-08-01]
  ( ) 契約開始時から（全期間）

過去の確定済みデータをどうする？
  ( ) そのまま（今後の分だけ変える）    … 既定
  ( ) 指定日以降の承認済み日報も作り直す
      → 影響額をここに表示してから確定させる
          売上 ¥3,161,757 → ¥3,163,589（+¥1,832）
          支払 ¥2,292,116 → ¥2,292,116（±0）
```

**影響額を出してから確定させる**のが要点。2026-08-28 の事故は、件数だけ確認して
金額を見ずに反映したことが原因だった。この確認をUIに組み込み、人手のスクリプトを不要にする。

**適用日を過去にしたときは、その日以降の既存versionを上書きする**（2026-08-28 決定）。
`effective_from >= 指定日` の版を削除してから新しい版を1件入れる。
間の改定は消えるが、版が常に一直線に並ぶので「この日はいくらだったか」が一意に決まる。
消える版の内容は確定前のプレビューに表示する。

月次締め（`monthly_closings`）による保護は入れない。締めのUXが未整備で運用されていないため
（2026-08-28 確認）。運用が始まった時点で「締め済みの月は作り直し不可」を足す。

### 3-3. 請求明細を単価ごとに分ける

明細行のキーに**適用単価**を加える。

```
現在: コース × 便 × 品目 × ドライバー
変更: コース × 便 × 品目 × ドライバー × 適用単価（期間）
```

数量の集計時に、各日報の日付から `course_rate_versions` を引いて適用単価を決め、
単価ごとにグループ分けする。ラベルに期間を入れる。

```
西宇治 宅急便（梶原）8/1〜8/25    1,240個 × 158円     = ¥195,920
西宇治 宅急便（梶原）8/26〜8/31     310個 × 157.5円   = ¥48,825
```

承認済みの日報はスナップショットに適用単価が入っているので、そこから引く。
未承認は現在値。これで**明細合計と集計エンジンの総額が必ず一致する**ようになり、
1-3 で挙げた不一致（丸め以外）が消える。

税抜/税込の二本立ては、請求書の `displayBasis` で切り替える既存の仕組みに乗せる。
明細行は `contract`（契約額）と `exclusive`（税抜）の両方を持ち、
取引先送付用は contract、税務提出用は exclusive を使う。

## 4. 実装順

1. **履歴スキーマ v2 と検証**（3-1）
   - migration: `effective_to` 追加、`invalid` 追加
   - 保存APIで v2 形式を書く。読み出しは v1/v2 両対応
   - 既存版の検証と `invalid` 立て（dry-run で件数と内容を確認してから）
2. **スナップショット生成を v2 履歴から行う**
   - `ignoreRateVersions` を撤去できる状態にする
3. **保存UIに適用日と過去分の選択を追加**（3-2）
   - 影響額のプレビューAPI（書き込みなしで前後の金額を返す）
4. **請求明細の行分割**（3-3）
   - 明細合計と集計エンジンの総額が一致することを回帰テストで固定

各段階で本番データに対する dry-run を残し、金額を確認してから反映する。

---

## 5. 決めたこと・保留

決定（2026-08-28）:

- 適用日を過去にしたら、その日以降の既存versionは**上書き**（削除して1件に置き換える）
- 月次締めによる保護は**入れない**。締めのUXが未整備で運用されていないため
- 適用終了日は列で持たず、次versionの前日として導出する

保留:

- 月をまたぐ請求（前後半締めなど）での期間分割の見せ方。現時点で該当する請求が無いため、
  実際に必要になってから決める
