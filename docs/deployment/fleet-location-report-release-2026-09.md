## 今回決めた操作順

1. 稼働中でも日報を提出・修正できる。終了後も同じ日報画面を開ける。日報は点検写真・駐車記録の完了を待たない。
2. 稼働開始時のメーター写真は現行どおり撮る。退勤時は車両の前・右・後・左の点検写真を撮る。退勤は写真保存成功後に確定する。
3. 駐車時にメーター写真を撮り、位置を記録する。本人の閉じた稼働セッションに4方向の点検写真が保存されていることと、駐車時のメーター写真があることをAPIで確認する。引き渡し時は追跡を停止する。
4. Web日報ではPNG/JPEGのスクリーンショットを画像欄にドロップできる。従来の画像選択と同じ原本保存・端末内OCR・確認を通る。様式がなく読み取れない場合は手入力する。
5. 会社設定で追加写真の名前・撮影時点（開始／終了／駐車）・必須／任意を設定する。オイル交換シール、鍵を置いた場所、給油口のキャップ、駐車場所などを選べる。開始時と駐車時のメーター、退勤時の4方向点検は現時点で固定。

既存の報告APIには旧クライアント向けの日報・駐車同時送信経路が残る。新しい独立駐車APIとの切替・遮断時期はモバイル公開前に決める。

## 実施・検証ゲート

1. **保存と認可**: 4方向・追加写真・メーターのアップロード先、車両/本人/会社の照合、退勤と写真保存の整合性、再試行時の重複、旧日報の駐車経路を実アプリで確認する。現在の退勤は写真を先に保存するが、セッション更新が失敗した際の不要な写真記録は残り得る。写真の削除・再試行方針を決める。
2. **位置履歴**: 保存期間に従う削除ジョブを作り、`vehicle_positions` のインデックス/容量/地図の取得件数を負荷試験する。キューの再送で新しい駐車位置を古い走行点が上書きしないことを確認する。
3. **署名済み実機**: iOS/Androidの開発ビルドで前景、画面ロック、他アプリ表示、圏外→復帰、再起動、権限拒否/撤回、長時間稼働、駐車完了後停止、電池消費を確認する。Expo Goは背景測位の検証に使えない。強制終了やOS停止中の更新は保証しない。
4. **権限審査**: iOSの背景位置利用目的と権限説明を確認。Google Playには背景位置の申告、デモ動画、アプリ内の明示、プライバシーポリシーと審査用アカウントが必要。審査で不承認なら、前景測位/手動駐車を維持できる公開範囲へ戻す。
5. **段階公開**: DB migrationと撮影Web/APIは完了。次は内部配布ビルド→少数ドライバーで現場試験→履歴・権限・電池・未提出件数を確認→対象拡大。新旧アプリが混在する間は会社設定で必須項目を有効化しない。旧クライアントの退勤時メーターと駐車APIの互換性を確認して切替日を決める。

## Webとモバイルの開発単位

同じモノレポの `apps/web` と `apps/mobile` は、`@repo/core` の型とAPIクライアントを共有する。現行のEAS profileではモバイルが `https://hakotora.jp/api/...` を呼び、Web/APIを介した同一のSupabase本番DBを使う。モバイルはDBへ直接接続しない。開発用API/DBへの分離は今後の作業で、EAS profileの接続先を変更するときは明示的に照合する。

Git履歴は一つのまま、変更の性質に応じてmigration、Web/API、モバイルUI・ネイティブ設定を別コミットにする。公開順はDBの後方互換変更→Web/API→署名済みモバイル内部配布→会社設定で必須化。WebのGit push/本番デプロイはインストール済みアプリを更新しない。モバイルのJavaScriptだけの互換変更はEAS Update、権限・ネイティブ依存・runtimeの変更は新しい署名ビルドを使う。
