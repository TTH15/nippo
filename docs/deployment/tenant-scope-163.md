# DB163と画像処理修正の公開手順

現在の状態: **2026年9月14日、本番DB163とb009d45のhakotora.jp公開を完了。** 一時停止・診断用トークンは解除/失効済み。9月12日の承認待ち記録は履歴として残す。

2026年9月12日、ユーザーがNext.jsの重大な指摘への対応、本番DB163適用、Web公開を承認。

## 変更と影響

- Next.jsを16.3.5、sharpを0.35.4へ更新する。sharpのlibheifは1.23.2。公式告知の修正範囲を満たし、古いsharpの別コピーも解消する。
- DB163は共有されている報告種別を各会社へ複製し、会社内のキー一意性と所属必須を強制する。既定会社のIDと全社の従来設定を保持し、過去の報告・金額・添付は変更しない。
- Webは会社境界・非公開ファイル・請求書住所の修正を含む。移行中だけ報告種別、諸報告、会社発行の対象APIが一時的に使えなくなる。

## 切替

1. 全テスト・本番ビルド・所属検査、画像処理、開発DBで163の複製・境界・再実行を検証する。開発DB検証はROLLBACKする。
2. CLI送信一覧から環境ファイル・原本素材・作業文書を除外し、本番対象プロジェクトを明示して `vercel deploy --prod --skip-domain` で待機中のデプロイを作成する。本番設定はサーバー側の既存設定を使う。
3. 変更対象の報告種別を権限600のローカル一時ファイルへ退避する。内容をコミット・公開しない。
4. 既存Firewallの下書きがないことを確認する。`/api/admin/report-kinds`、`/api/me/report-kinds`、`/api/reports/oil-change`、`/api/admin/misc-reports/oil-change`、`/api/platform/applications` の接頭辞を拒否する一時ルールを公開する。対象API拒否と通常ログインの可用性を確認し、対象に個別のmaxDuration指定はなく、プロジェクトはFluid Computeの既定300秒。ルール反映を確認してから300秒以上待ち、旧リクエストを排出する。旧デプロイ固有URLの認証保護は維持する。
5. DBラッパーの `apply` で163を1トランザクションで適用し、台帳・会社別件数・既定ID/設定の保持・所属必須・一意性・一般ロール権限を読み取り確認する。
6. 待機中のWebを `vercel promote` で公開し、ドメインが新デプロイを指していることと公開ページ・認証拒否・画像処理を確認する。一時Firewallルールを削除して公開し、対象APIを復帰確認する。

## 障害時

- DB適用前の失敗は旧Webを維持し、一時ルールを解除する。
- DB適用失敗はトランザクション全体をROLLBACKする。台帳とスキーマを確認後に旧Webの対象APIを復帰する。
- DB適用後にWeb切替が失敗したら対象APIを停止したまま修正版を公開する。会社分離のない旧Webへ無条件で戻さず、分離済みデータの自動逆移行もしない。
- 本番利用者の状態変更・報告承認・請求書保存を検証用に実行しない。境界の否定ケースは回帰テストと開発DBで確認する。
