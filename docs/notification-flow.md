# 通知フロー 設計叩き台

ステータス: ドラフト（合意形成中）／最終更新: 2026-08-15
基盤設計: `docs/platform-design.md`（テナント/identity/認証）。本書はその上の業務フロー。
関連方針: `構成A`（通知の生成・送信は Next.js API 側。Edge Function/Realtime不使用）。

---

## 0. 目的

ドライバーに**業務情報をプッシュ**する。代表例＝翌日アサイン通知:

> 「明日は〇〇コース／集合: △△／時間: 8:00／車は××に停まっています」

設計は変更通知・休み通知・手動連絡など他種別にも拡張できる形にする。

---

## 1. ★中心方針：統合LINE（アプリ公式1本）＋テナント単位運用＋アプリ内インボックスが真実

### 1-1. 統合LINE（既定）／BYOは将来オプション
- **既定 = Nippo（仮）公式アカウント1本**で全社の通知を配信。ドライバーは1回友だち追加、送り主は常にアプリ＝わかりやすい。各社の導入摩擦ゼロ。掛け持ち・転職に強い。
- **チャネルは"配信パイプ"にすぎず、誰に/何を/いつ は全てプラットフォームのテナントスコープ・ロジックが決める**。1本でも運用は完全に会社別（A社→A社のみ、B社は22時、テンプレ/項目/休み通知ON-OFFも全てorg設定）。
- **コスト**: LINE料金はプラットフォームが負担 → SaaS料金に通知枠を同梱（例: ○○通/月込み、超過は従量）。
- **LINEとRN pushは恒久的に並行運用**（橋渡しではない）。アプリ通知をOFFでもLINEは見る層がいるため、LINEコストは恒久的に発生する前提。
- **リッチメニュー**は汎用のアプリ操作面（今日のシフト/日報/車両位置）として全社共通。
- **将来オプション = BYO-LINE**: 自社ブランドLINE＋独自リッチメニューを回したい会社向けに、各社が自前チャネルを持ち込み LINE へ直接支払う形を後から追加。そのとき LINE連携を `line_links(identity_id, org_id, line_user_id)` の org別へ拡張（既定はidentity単位）。

### 1-2. アプリ内インボックスを真実、LINE/pushは配信
```
通知レコード生成（受信者ごと・org/membership文脈、org_idを保持）
  → アプリ内インボックスに必ず表示（= source of truth）
  → LINE連携済み: 統合チャネルへ push/multicast（明示userIdリスト）
  → RNアプリ導入済み: push（後日）
```
- **LINE未連携でもアプリ内で必ず見える**（取りこぼし無し）。
- 運営画面に**LINE連携状況の一覧**を出し未連携を可視化＝催促可能。
- **配信は全有効チャネルへ並行ファンアウト**（インボックス常時＋LINE連携時＋RN push有効時）。LINEとRN pushは恒久並行。両方ONなら二重到達するが、到達率優先で許容（将来、ユーザー別チャネル設定で抑制可）。

### 1-3. ★誤爆防止（統合チャネルの肝・多層防御）
統合は「会社をまたいで全員に送る」事故が唯一最大のリスク。ソフトウェアで確実に防ぐ:
1. 受信者リストは**必ずorgスコープのクエリから生成**（platform-design §3 default-denyヘルパー経由）。
2. **LINE broadcast（全友だち配信）APIをテナント通知で禁止**。push/multicastに明示的userIdリストのみ。broadcastは§1-4の運営告知レーン専用に隔離。← 核心。
3. **送信直前アサート**: バッチ内の全受信者が送信元orgに属すことを最終確認、不一致でバッチ中断。
4. 通知レコードがorg_idを保持し、LINE送信はそのレコードから導出（データ層で分離）。
5. **UIスコープ**: 運営は自社ドライバーしか選べない。手動ブロードキャストも自社内限定。
6. **越境テスト**をCIに（org Aの通知にorg BのuserIdが混ざらない）。

### 1-4. プラットフォーム（Nippo）告知レーン
- org通知とは別の**特権レーン**。送信元=Nippo運営、対象=全identity or セグメント（リリース/メンテ告知）。
- **ここだけ全体配信(broadcast)が正当**（§1-3で禁じたbroadcastの隔離先）。統合だからこそ容易（BYOなら逆に難所）。
- 「声」の出し分け: `【A運送】明日は…` / `【Nippo運営】メンテナンスのお知らせ`。インボックスも会社/システムで分類。

## 2. 通知の種類（拡張前提）

| 種類 | タイミング | 優先 |
|---|---|---|
| 翌日アサイン通知（コース/集合/時刻/車両位置） | 前日夜（org可変） | ★まず実装 |
| 変更通知（【変更】アサイン/車両） | 変更発生時 | ★（柔軟性の要） |
| 手動ブロードキャスト（台風で休み等） | 即時 | ★ |
| 休み通知 | 前日夜 | org設定でON/OFF |
| 当日朝リマインダー / 締切リマインダー | 後 | 後 |

共通の「生成 → インボックス → 配信」パイプライン1本の上に種別を乗せる。

---

## 3. 送信トリガー（3モード＝柔軟性）

前日夜以降の変化（事故で車両不可・台風で休み等）に対応するため1種類にしない。

| モード | 例 | 仕組み |
|---|---|---|
| **定時バッチ** | 前日20:00「明日のアサイン」 | Vercel Cron → `/api/cron/daily-notifications`（cronシークレット保護、時刻はorg可変、JST） |
| **差分検知＋明示送信** | アサイン/車両変更で「【変更】」 | シフト管理画面のバー → `/api/admin/shifts/pending-changes` |
| **手動ブロードキャスト** | 「台風で本日休み」を運営が即送信 | 運営画面 → コース/全体へ |

- 定時送信後に変更が起きたら**黙って再送せず「【変更】」を追加**（インボックスに履歴が残る）。
- 冪等性: 「org×日×種別×membership」キーで定時バッチの二重送信を抑止（`notifications.dedupe_key`）。

### 3-1. ★変更通知は「イベント駆動」にしない（2026-08-15 決定）

当初はイベントバスで変更操作を拾う案だったが、**採用しない**。運営はシフト表のセルを
何度も触り、確認のために画面を行き来する。その途中経過を機械は本当の変更と区別できず、
数えた回数だけ通知が飛んでしまう（通数課金でもあり、ドライバーの信用も失う）。

代わりに**状態の差分**で出す:

```
通知レコードの payload に「その人に伝えた予定」のスナップショットを残す
  → 現在の shifts と比べて差分を出す（/api/admin/shifts/pending-changes）
  → 差分があるときだけシフト管理画面の足元にバーが出る
  → 運営が中身を読んで、送るものを選んで送信 ← ここで初めて配信
```

この形だと自然にこうなる:

- 何度触り直しても差分は1件に畳まれる
- **元に戻せば差分は消える**（通知するものが無くなる）
- 画面を再読み込みしても結果が変わらない
- **まだ通知していない日付には基準が無いので差分も出ない**
  ＝前日の通知前にシフトを組み替えている間は画面に何も現れない（UI を汚さない）

補足:
- 定時通知が流れ終わった日は、その人宛の通知が無くても「割り当ては無い」と伝えた扱いにする。
  そうしないと、休み通知 OFF の org で「通知後に初めて割り当てられた人」を検知できない。
- 送信内容はクライアントから受け取らず、送信時にサーバ側で計算し直す
  （画面を開いてから送るまでの間に状況が変わっていても、送るのは常に最新の差分）。
- 変更通知の冪等キーは通し番号を含む（`{org}:{date}:change:{driver}:{seq}`）。
  二重クリックは1通に潰れ、送信後に改めて起きた変更は別の通知として送れる。
- org 設定 `change_enabled` が OFF なら差分検知そのものを止める（画面にも出さない）。

## 4. 対象者の決定

- 翌日 `shifts`（日付×コース→driver）に割当の **status='active' membership**。org単位でループ（テナント分離厳守）。
- identity/membership: 配信は **membership の line_link**（org文脈）。複数org所属ならアサインのある各org分を送る。

---

## 5. メッセージ組み立て（org単位CMS）

「何を通知するか」を **org×通知種別のテンプレート**で管理（CMS的）。

- プレースホルダ: `{コース}` `{集合}` `{時刻}` `{車両番号}` `{駐車位置}` `{氏名}` 等。
- org設定: 含める項目トグル（駐車位置を入れるか等）、通知種別ON/OFF、送信時刻、休み通知ON/OFF。
- 文面生成は**純粋ロジック（`core/logic`）**に置きWeb/RN/種別で再利用。
- 取得元: コース名/集合/時刻=`courses`、車両位置=最新駐車位置（§7依存）、車両=`vehicles`。
- 将来: リッチメニュー連携・セグメント配信（L Message的方向）。**初期はテンプレート＋トグルでstart**、フル機能は後。
- 置き場: `org_notification_settings` / `org_message_templates`（新設）。

## 6. 配信チャネル（生成と分離・アダプタ化）

| 時期 | チャネル | 必要なもの |
|---|---|---|
| 今 | LINEプッシュ（統合チャネル） | identity単位の line_user_id（Nippo公式の友だち追加で取得）。push/multicast の明示リストのみ |
| 後 | RN push（Expo/FCM） | 端末トークン |
| 常時 | アプリ内インボックス | なし（真実の置き場） |

生成結果を複数チャネルに流せるよう、チャネルは差し替え可能なアダプタにする。

### 6-1. LINE はカード（Flex Message）で送る（2026-08-15）

予定の通知は `apps/web/src/server/line/flex.ts` がカードに組む。
**インボックスに入るのは常にテキストの title/body**（真実は §1-2 のとおりインボックス）で、
カードは LINE の見た目でしかない。

- `altText` にテキスト版をそのまま入れる。通知バナー・トーク一覧・Flex 非対応環境では
  こちらが読まれるので、**カード化しても通知の第一印象は変わらない**。
- 変更通知では変わった項目の下に変更前の値を取り消し線で添える。
- ボタンは「カレンダーに追加」（Google カレンダーの予定作成 URL）と「アプリでシフトを見る」。
  アプリの URL が解決できない環境ではボタンごと省く（壊れたリンクを送らない）。
- **通数課金はメッセージ1通単位**なので、カード化のコスト増は無い。

外部カレンダーとの連携は、この片道リンク（OAuth 不要・審査不要・カレンダーを選ばない）で
start する。ics 購読フィードによる常時同期は次の候補、Google Calendar API の双方向同期は
審査・同意フロー・トークン管理に見合わないため現時点では採らない。

## 7. 依存する未実装機能（無ければdegrade）

- **駐車位置キャプチャ**（QR/位置）→ 車両の最新位置。未取得なら位置行を省略。
- **翌日シフトのアサイン確定**。未確定なら送らない or 「未定」。
- **LINE連携（友だち追加）**。未連携ならアプリ内のみ（§1-2）。

## 8. エッジケース

| ケース | 挙動（案） |
|---|---|
| 翌日アサインなし | org設定で「休み通知」or 無通知 |
| 車両位置未取得 | 位置行を省いて送信 |
| LINE未連携 | アプリ内インボックスのみ＋運営画面で可視化 |

| 送信失敗 | リトライ＋`notification_logs`に失敗記録 |
