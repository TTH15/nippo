# 認証修正の適用記録

## 内容と影響

- Passkey応答の検証後、用途とチャレンジのハッシュをDBへ原子的に使用済み登録する。同期型Passkeyのcounter=0でも同じ応答の再送は1回だけ成功する。
- 期限はJWT検証・RPC開始時・INSERT後に確認し、DBのロック待ち中に期限を過ぎた応答も拒否する。保存障害やカウンター更新失敗時はセッションを発行しない。
- 共通requireAuthで現在の所属状態・会社・本人・token_versionを確認する。停止・削除は拒否し、所属・権限・本人の変更時にはDBトリガーで世代を増やす。
- 既存のJWTは世代0として扱い、変更のない利用者の一斉ログアウトは起こさない。停止解除でも旧JWTは復活しない。
- 承認待ちは本人登録・本人プロフィール・Passkey登録の明示したAPIだけ通す。各業務のown権限細分化と、Passkey登録／削除時の強い再認証は別途対応する。
- ログイン時にPINハッシュを含む行全体を出していた診断ログを削除した。

## 検証

- Web全122ファイル1,134テスト、Web／隔離プレビューの型検査、本番向けビルドが成功。
- 開発DBで8接続の同時送信、再送、期限切れ、ロック待ち中の期限切れ、期限切れ行の削除、一般ロールの権限拒否を検証。DBテストは親を含め6テスト成功。
- 所属の世代トリガーは一時表で氏名変更・停止・復帰・権限・会社・本人変更・世代巻き戻し禁止を検証しROLLBACK。実利用者の状態をテスト用に変えていない。
- 本番のアカウント／ログインページを再利用したプレビューで、登録・再試行・停止後の再ログイン拒否・権限変更後の再ログインをPC 1280px／スマホ390pxで実操作した。端末認証・APIはモックで、本番の鍵を使わない。
- 既存check:tenantは11件で終了コード1。今回の変更による増加はない。事前に値へorg_idを入れる保存や全社管理の例外を含み、B-3で例外の根拠と検査範囲を見直す。
