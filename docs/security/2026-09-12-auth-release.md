# 認証修正の適用記録

## 内容と影響

- Passkey応答の検証後、用途とチャレンジのハッシュをDBへ原子的に使用済み登録する。同期型Passkeyのcounter=0でも同じ応答の再送は1回だけ成功する。
- 期限はJWT検証・RPC開始時・INSERT後に確認し、DBのロック待ち中に期限を過ぎた応答も拒否する。保存障害やカウンター更新失敗時はセッションを発行しない。
- 共通requireAuthで現在の所属状態・会社・本人・token_versionを確認する。停止・削除は拒否し、所属・権限・本人の変更時にはDBトリガーで世代を増やす。
- 既存のJWTは世代0として扱い、変更のない利用者の一斉ログアウトは起こさない。停止解除でも旧JWTは復活しない。
- 承認待ちは本人登録・本人プロフィール・Passkey登録の明示したAPIだけ通す。各業務のown権限細分化と、Passkey登録／削除時の強い再認証は別途対応する。
- ログイン時にPINハッシュを含む行全体を出していた診断ログを削除した。

## 2026/11/02 認証セキュリティの本番適用

公開済み `ee0f7b34` から `codex/auth-security-release-20261102` を作成し、今回の認証修正だけを統合した。元のmain作業ツリーの未公開business基盤・車両/シフト・モバイルUI差分は含めない。公開済みの振込口座変更用パスキー確認、チャレンジ用途の区別、保存時の競合検査は保持する。

- 権限DB障害を既定の管理権限で通す処理を廃止し、503で拒否する。
- 運営キーの追加/削除には登録済みパスキーの直近確認が必要。紛失時は別の同社ADMINが承認し、管理者が1人なら独立したplatform_adminが運営窓口で本人を確認する。自己承認・別会社の一般管理者を拒否する。
- 申請は24時間、承認は15分・一度限り。本人・会社・token_version・ログインセッションへ拘束。復旧完了とキー削除で本人の全所属のログインを失効させ、通知/承認監査記録を同時保存する。
- JWTへセッションIDと絶対期限を追加。業務ログインは最大30日、運営トークンは15分。セッション更新で絶対期限を延ばさず、運営更新Cookieも元の業務ログインへ結び付ける。通常/全端末ログアウトと親セッションの失効をサーバーで検査する。失効確認の障害は503、ログアウト失敗時は再試行用の保存値を残す。
- SMS送信/照合は番号HMAC・信頼できるVercel IP・全体予算で原子的に制限する。送信は1回/分・10回/日/番号、500回/日/全体。照合は5回/分・100回/日/番号、5,000回/日/全体。拒否で部分予算を消費せず、DB障害ならTwilioを呼ばない。
- 電話番号が未登録の場合は既存パスキーで先に本人確認する。保存済み番号のSMS確認と初回登録時の競合検査を維持する。パスキーのない旧利用者は、窓口が既存の連絡先で確認して登録番号を設定する。セッションを持つだけで任意の番号を復旧先にできない。
- `20261101153820_auth_recovery_sessions_and_limits.sql` をWebより先に適用する。新規3表と関数は一般ロールに開放しない。`manage_passkey`の既存署名を保ち、旧Webと併存可能。現在の2名のactive root管理者には、それぞれ本人以外の承認者が存在し、既存キーも登録されていることを集計だけで確認した。
- `20261101160830_fix_security_function_search_paths.sql` は既存6関数のsearch_pathを `pg_catalog, public, pg_temp` へ固定する。関数本文・SECURITY INVOKER・実行ACLを維持する。publicにanon/authenticatedのCREATE権限がないことも確認した。

### 運営窓口の復旧手順

1. 申請者へSMSログイン後の復旧申請を依頼する。申請中に新たに伝えられた連絡先だけで本人と判断せず、登録済みの連絡先または対面で確認する。パスワード・OTP・秘密鍵を担当者へ送らせない。
2. 独立した管理者またはplatform_adminがアカウント設定/運営窓口の復旧一覧を開き、対象会社・氏名を確認して自分のパスキーで承認する。自分自身の申請は承認しない。
3. 申請者は同じ申請画面で状況を更新し、15分以内に新しいキーを登録して運営画面へログインする。期限切れなら再申請する。旧セッションの失効と本人通知を確認する。
4. 管理者と窓口担当者は予備のキーを別の場所に保管する。キー登録/削除/復旧通知に心当たりがなければ全端末失効後に窓口へ連絡する。秘密のローテーションや担当者の権限付与は、対象と影響を別途確認して行う。

### 公開・戻し方

DB2件→Webの順。旧運営更新CookieにはセッションIDがないため運営側はパスキー再ログインが必要。旧業務JWTは元の有効期限まで継続し、再取得による無期限延長を止める。ネイティブのサーバー失効対応は更新版配布後から有効で、既存の端末内ログアウトだけを行う旧バイナリを遠隔で置換はできない。

Webを戻す際は直前の本番deploymentへ戻し、新表・失効記録・token_versionを残す。世代を下げない。旧WebのSMS単独での運営キー追加も戻るため、修正版の再公開まで運営用の復旧を窓口対応とする。

未公開business基盤を後日導入する際は、actor作成後にauth migration末尾の再適用可能なDOブロックを適用し、失効済みセッション/親セッションの拒否を確認してから有効化する。今回、その基盤・接続キー・権限の拡張は公開しない。

### 残る運用・互換性の境界

Web本番依存の監査0件を公開条件とする。Expo CLIのZod3等はSDK57の更新版でも依然として要求され、修正版Zod4の一括強制は互換性を壊す。SDK58への移行と署名済みiOS/Androidの実機配布は別途検証が必要。実際のSMS到達、利用者のキー操作、窓口の対面確認をエージェントが代行したとは扱わない。費用アラートの通知先/金額、秘密のローテーション、監査ログの保存期間は運用者が定める。
