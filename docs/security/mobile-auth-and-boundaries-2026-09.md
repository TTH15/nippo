# モバイル再開時の認証・権限境界（2026/09/29）

## 範囲と判定の前提

この文書は元の作業ツリー `HEAD 1259eb6` と、2026/09/29時点の未コミット差分を起点とする監査・実装設計である。下記の時系列のうち、管理者コード・パスワードを維持する記述は当時の段階導入を示す。現行の運営ログインは後述の本人Passkey方式で、管理セッションは30日更新Cookieで継続する。モバイルの配布済みバイナリ、Apple/Google署名、実機での悪用可能性は別に確認する。

確認済みの良い境界は、リクエストごとの所属状態・`token_version` 照合、PasskeyのRP/origin・UV・単回challenge確認、本人の鍵だけに対する操作、モバイルのHTTPS既定値とSecureStore利用である。これらがあっても、認証手段、セッションの用途、業務権限、参照先の会社はそれぞれ別に検査する必要がある。

## 推奨する認証境界

本人のアカウントは共通にし、発行する権限を**用途別のセッション**で分ける。既存の `driverId` / `identityId` / `orgId` / `token_version` の照合を維持する。

| 用途 | 発行条件 | サーバーが許す範囲 |
| --- | --- | --- |
| 通常業務 | Passkey、または初回・復旧時のSMS。モバイルでは既存セッションを保持する。 | 本人の業務API。管理画面の表示有無に頼らず、管理権限を使うAPIは拒否。 |
| 管理業務 | 現在の本人・会社・管理権限を再確認し、**Passkeyで認証**。管理API用JWTは15分、更新Cookieは30日。 | その会社の管理APIのみ。JWTの`purpose`・`aud`・`orgId`等をガードで照合。鍵の信頼確定と再発行は別の承認手続き。 |
| 復旧 | SMS成功後、復旧専用の短命セッションを発行。 | 本人の復旧状態確認と必要な手続きのみ。既存の管理権限・口座変更・管理用鍵の自己追加は許さない。初回参加時の鍵登録は別状態として扱う。 |
| 振込先の登録・変更 | 操作直前にPasskeyで再確認し、確認結果を現在のセッション・本人・操作内容に結び付ける。鍵が使えない人は運営確認と通知付きの例外手順。 | 口座項目だけの更新。通常プロフィール項目との部分更新を分け、APIが再確認を必須にする。 |

`strongAuthMethod`は現在の認証履歴として使えるが、これだけで管理セッションにしない。SMS直後の`strongAuthAt`は、管理権限や既存アカウントの鍵追加を許す根拠にしない。既存のPasskeyがない初回登録、既存鍵の追加、端末紛失後の復旧は状態を分ける。復旧時は運営が本人と所属を確認し、必要に応じて`token_version`を上げて旧セッションを失効させる。後に個別端末の終了が必要なら`jti`とサーバー側セッション台帳を導入する。

管理用セッションの導入では、`/api/admin/*`だけでなく`requirePermission`/`requireScopedPermission`を使う全ルートを棚卸しする。ドライバー本人のAPIと会社データAPIを分類し、例外をガード内で明示する。切替前に旧JWTの扱いを決め、サーバーで拒否を有効にしてからBase・Webの管理画面を対応させる。画面だけでSMS利用を隠しても境界は変わらない。

## 実装順と合格条件

1. **会社境界の穴を閉じる。** 担当コースの作成・編集で全IDの自社所属を更新前に検査。他社IDは404または入力エラーとし、関係行が変わらない結合テストを追加。PostgRESTを含む検証環境でDB側の同一会社保証を復元し、既存結合を壊さないことを確認する。
2. **通常・管理・復旧の用途を定義する。** JWTの用途と有効期間、既存JWTの移行、全管理APIのガード、Passkey再確認challengeの本人・セッション・会社結合、権限変更直後の失効をテスト。SMSで入った管理者が管理APIへ到達できないことをサーバーテストで示す。
3. **Passkey登録・復旧を分ける。** 新規参加は登録完了を原則とし、端末非対応時は運営の例外へ誘導。既存利用者がSMSだけで管理用鍵を追加・交換できないことを確認。予備鍵・両方紛失時の承認者と記録項目を運用に定める。
4. **振込先を独立させる。** 本人による初回登録と変更のポリシーを決定後、専用APIと再確認・通知・監査を実装。Webとモバイルの同じサーバー条件で、通常JWT・SMS復旧JWT・期限切れ確認を拒否する。未登録者が支払情報を登録できる例外手順を用意してから強制する。
5. **モバイル保存と配布を検証する。** SecureStore書き込みを直列化し、ログアウト時は削除完了を待つ。失敗を利用者へ復帰可能な状態として扱い、遅延書き込み・再起動テストを追加。署名済み実機でPasskey・SMS復旧・Webとの鍵共有・ログアウト・オフライン・旧アプリからの移行を確認する。

### 運営セッションの30日継続（2026/09/30・本番公開済み）

15分の管理JWTは操作中でも絶対期限で切れていた。Passkeyログイン後に30日有効の更新用Cookieを発行し、管理API用JWTを自動更新する。更新Cookieは `HttpOnly`・`SameSite=Strict`、本番で `Secure` とし、JavaScriptから読めない。更新には通常業務JWTとCookieの両方を要求し、本人・所属・`token_version`を照合し、現時点の運営権限を再確認する。管理APIは引き続き `purpose=admin` と `aud=hakotora-admin` を必須にする。新しいタブでも更新でき、ログアウトとSMS復旧時はCookieを削除する。既発行の15分JWTだけでは更新できず、公開後に一度Passkeyログインが必要。

30日後は再びPasskeyログインする。管理JWTの流出による利用可能時間は最大15分。更新Cookieはスクリプトから読み取れないが、端末自体の乗っ取り等を完全には防げない。権限変更と全端末失効には既存のDB・`token_version`を使う。端末ごとの強制失効が必要になった場合はサーバー側セッション台帳を追加する。`/api/auth/session`による管理JWT延長は認めない。
