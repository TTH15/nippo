# 管理画面の情報設計方針

更新: 2026-08-24

## 目的

管理機能の増加に合わせてサイドバー項目を足し続けるのではなく、運営担当者が完了したい
仕事を起点にページ構成を整理する。単にメニューを折りたたむだけでなく、独立ページとして
残すもの、親画面のタブへ統合するもの、設定・履歴としてメニューから外すものを区別する。

この文書は設計意図の記録であり、2026-08-24時点ではサイドバー再編自体は未実装。

## UX原則

1. サイドバーには、反復して行う仕事の「開始地点」だけを置く。
2. 同じ対象を扱う別表示は、別メニューではなく親画面のタブにする。
3. 作成補助・設定は、対象画面の設定ボタンと設定トップの両方から到達可能にする。
4. 履歴・詳細・承認途中の状態は、原則としてサイドバーへ置かない。
5. グループ名はシステム内部のドメイン名ではなく、現場の仕事（運行、報告、収支等）で表す。
6. 権限による表示・ロックの意味は維持し、情報設計の変更と認可変更を混ぜない。
7. URLは一括変更せず、既存ルートを維持したまま共通タブ・遷移を追加し、必要な旧URLだけ
   最後にリダイレクトする。

デスクトップの横フライアウトは、全体像と現在地が見えにくくなるため、現在地のグループが
自動で開く縦アコーディオンを候補とする。展開状態は端末に保持し、件数バッジは子項目と親の
双方へ集約する。

## ページ統合候補

| 現在 | 推奨する所属・入口 | 理由 |
|---|---|---|
| 単発案件 | シフト管理の `シフト表 / シフトメモ / 単発案件` | シフト表ですでに同日の仕事として表示・相互遷移している |
| 調整履歴 | 売上の `概要 / 売上調整 / 履歴` | 入力元も表示データも売上ログで、独立した仕事ではない |
| 参加・承認 | ドライバー管理の `在籍 / 稼働終了 / 参加・承認` | ドライバーが在籍へ入る前段階である |
| 取引先 | 請求の `請求先別 / 請求書` | 単なるマスタではなく月次集計から請求書を作る作業画面である |
| 報告種別 | 日報・諸報告の設定ボタン | 報告フォームを構成する補助設定である |
| 送信後画面 | 日報の設定ボタン | 日報提出体験の設定であり、日常業務の開始地点ではない |
| コース／単価表 | 設定トップの配送設定 | キャリア・報告単位と合わせて配送マスタを構成する |
| キャリア／フォーム設計 | 配送設定の別タブ | コース設定と同じ配送モデルの上流にある |
| 会社設定 | 設定トップ＋請求からの導線 | 現状の内容は会社・振込先・社印で、請求業務との関係が強い |
| ロール・権限 | 設定トップ＋ドライバーからの導線 | 日常的な人員一覧ではなく全社設定である |

## シフト管理の決定事項

シフト管理は同じ画面内で次の表示を切り替える。

- `シフト表`: 正式な割当、車両、時刻、希望休を扱う既存画面。
- `シフトメモ`: 正式データと分離した個人下書き。半月グリッド、名前札、自由メモを扱う。
- `単発案件`: 将来統合候補。2026-08-24時点では既存ページを維持する。

シフトメモは「正しく埋める管理表」にしない。登録ドライバー以外の文字札、重複配置、担当外
配置を許し、正式シフトへの自動反映や検証を持たせない。正式データへ反映する機能は、現場で
メモ運用が定着し必要性が確認できてから別途設計する。

### シフトメモの保存境界

シフトメモはデフォルトで本人だけが閲覧・編集できる個人データとする。推奨する本番保存先は
`org_id + driver_id`で分離した個人DBで、端末変更後も同じ本人だけが継続利用できる構成とする。
localStorageは未送信変更のキャッシュ、または端末だけに残すモードとして使い、共有の代替には
しない。

他の運営者へ見せる機能が必要になった場合は、個人メモの暗黙共有ではなく、明示的に作成・公開
する別の「共有ボード」として画面・テーブル・権限を分ける。個人メモから共有ボードへの反映も
自動では行わず、対象期間と内容を確認して公開する操作を設ける。

2026-08-24時点の`shift_memo_days`は`org_id + memo_date`で組織共有される構造のため、新しい
半月グリッドの個人メモ保存先としては再利用しない。既存行を削除・個人へ推定移行せず、利用状況
を確認したうえで共有ボードとして残すか廃止するかを別途決める。

## 案件報告の配置方針

案件報告は、誤配・事故・依頼・改善事項を投稿後も追跡する独立画面とする。ただし情報設計上は
「報告・対応」グループへ置く。既存の報告フォーム基盤は入力に再利用し、案件固有の
`未対応 / 対応中 / 解決済み`、追記、変更履歴は専用データとして扱う。

既存の「単発案件」は一日限りの仕事、新しい「案件報告」は発生事項の記録であり、名称と導線を
混同させない。

## 段階的な移行

1. 新機能は上記の所属を前提に追加し、トップ階層をこれ以上増やさない。
2. 明確な重複である調整履歴、参加・承認、各種設定への入口を親画面へ追加する。
3. 共通のワークスペースタブを導入し、旧ページの中身を壊さず同じ仕事として見せる。
4. 利用導線を確認した後、旧サイドバー項目を外す。
5. 最後に不要になった一覧ページをリダイレクトし、ブックマークと既存リンクを保護する。
