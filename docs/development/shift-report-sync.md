# シフト変更と日報の連動

2026/10/17。実装・隔離検証済み、本番未適用。

## 確認した原因

10/16の対象者では「新花河原」を解除し「下京夜間」を追加した後も、解除前に提出された「新花河原」の日報が未却下で残っていた。現在の割当は「河原町七条」「下京夜間」の2コース、日報は3件。調査時点では3件とも未承認だったため、確定した請求・支払金額の過大計上まで確認したものではない。日単位の承認で解除分まで承認対象になり得る。

## 保存時の動作

- シフトの担当解除・担当変更・日付/コース/便変更・削除のトランザクション完了時、旧担当者の同日・同コース・同便に割当が残らなければ、該当する未却下の日報を却下する。手動編集、メモ反映、取込取消など、書込入口によらず共通。
- 日報・明細・単価スナップショットは削除しない。既存の `rejected_at` により、承認待ち、提出済み判定、売上・報酬計算から除外する。「すべて」の履歴では「シフト変更で対象外」として残る。自動処理の `rejected_by` はNULL、`rejection_reason` は `shift_changed`。
- 再割当だけでは旧日報を復活させない。改めて提出した日報は未承認となる。同じトランザクション内のスロット移動、別スロットに同じ割当が残る場合、車両・時間だけの変更は維持する。
- 古い画面からの再送、解除済み日報の再承認・再有効化はDBで拒否する。Webの提出前検証でも、提出済みであることを理由に現在のシフト条件を迂回しない。
- 通常のシフト書込者に日報編集権限を追加しない。トリガー専用NOLOGINロールに限った列権限、固定search_path、一般ロールからの関数EXECUTE剥奪を使用する。プロジェクトのRLS有効/無効設定は変更しない。
- 送信と解除は同じ会社・本人・日・コース・便のadvisory lockで調停する。送信側は解除中なら待たずに再確認エラーとし、日報行とシフト側の相互待ちを避ける。古いスナップショットを使う分離レベルでの対象変更は拒否する。
