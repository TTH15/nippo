# 便と日報項目の対応

2026/10/17 実装。本番の公開・DB適用・初期設定は未実行。

## 動作

- コース管理 → 編集 → 日報項目で、C1に「午前」、C2に「午後」を選ぶ。4便は別コース・別の便で「4便」を選ぶ。全項目・項目ごとの調整にも対応する。便名から数量を推定したり、4便をC1/C2へ転記したりしない。
- 既存の `course_report_fields` を利用。便固有 → コース共通(0) → 未設定なら全項目、の互換を維持。画面の初期チェックも実際に表示される項目と一致する。
- 保存ボタン、タブ移動、保存して閉じるで保存する。各便に最低1項目が必要。保存中の重複操作を止め、失敗時は入力を保持。読み取り権限のみの利用者は変更不可。
- 保存は `replace_course_report_fields` RPC の1トランザクションで行う。会社・キャリア・有効な単位/項目/便を検証し、読込時と設定が違えば409で再読込を求める。削除だけ成功する状態を作らない。
- 本人フォーム・代理入力フォームは設定項目だけを出す。送信・代理入力・管理者編集ではヘッダ更新前に入力項目を検証し、DBトリガーでも別便の新しい数量を拒否する。承認直前にも同じ対応をDBで再検証し、設定変更と重なった承認を止める。設定と明細の保存はコース単位のadvisory lockで調停する。
- 設定変更だけでは過去の明細・数量・承認単価を変更しない。設定外でも保存済みの数量/文字は一覧に残し、「便の設定を確認」と表示。未入力・0・未チェックだけを省略する。未承認の日報に設定外の実績があれば承認不可。本人・代理入力から見えない過去値を黙って消す再提出も止める。運営の編集から確認・0への訂正が可能。
- シフトでC2を追加した場合、要対応日・管理バッジ・画面はコース＋便で不足を判定。旧全体日報(cycle=0)しかない過去日は全体の提出として扱い、便別日報が混ざる場合は便を一致させる。
- 一括承認は未承認のIDだけが対象。代理入力は承認済みの便を対象外にし、明細・単価保存後に承認する。本人の再送も、車両/メーター/明細が同じ承認済み日報なら書き換えない。

## DBと初期設定

- 追加migration: `supabase/migrations/20261017081031_bind_course_report_fields.sql`。設定保存RPCはservice_roleにだけ実行を許可。明細検証は専用NOLOGINロール、列単位の読取権限、固定search_pathで行う。既存RLSの有効/無効を変更しない。
- 同時に `20261017081019_sync_reports_with_shift_changes.sql` を更新。シフト変更で外れた日報には `rejection_reason='shift_changed'` を残し、手動却下と区別。再割当だけでは復活せず、旧全体日報の一部の便が解除された場合も全体日報を対象外にして再入力へ戻す。
- 本番読取調査で「久御山 Amazon」「豊中 Amazon」は便別の日報項目が未設定だった。`scripts/repairs/20261017-course-cycle-fields.sql` に確認済み2コースだけの初期設定を用意。会社・名称・有効C1/C2・項目を再照合し、既存設定があれば中止する。既定の末尾はROLLBACK。過去の日報の書き換えは行わない。
- 吉田立汰の10/16分の補正候補は既存の `scripts/repairs/20261017-yoshida-shift-report.sql`。こちらも未実行。
- 本番適用では今回のDDL/API/UIを揃える。他の保留migrationをまとめて適用しない。公開・対象データの補正後に、現在のシフト、対象外履歴、未提出便、承認済み単価、集計結果を再照合する。
