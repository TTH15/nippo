# UI・PDF・画像出力の監査

2026年9月12日作成。UI改修の完了条件として継続する。基本は [プレビュー手順](preview-workflow.md) と [画像・PDF出力](image-pdf-export.md)。

## 毎回の確認順

1. 対象の本番ページと既存の共通部品・出力関数を先に読む。再利用元、対象の保存形式と利用目的を記録する。
2. 隔離fixtureで正常、空、長い名前、多件数、読み込み中、取得失敗、保存失敗を用意する。権限は管理者・経理・閲覧で確認する。
3. 見た目 → 操作 → 状態 → consoleの順で監査する。PC、768px、390px、320pxを確認し、実装都合の説明を利用者向けUIへ出さない。
4. 出力がある画面は、生成・保存・再生成・キャンセル・失敗復帰を確認する。画面だけでなくPNGの実寸とPDF全ページを開く。住所、長文、表の最終行、改ページ、社印、QRの読み取りを用途に応じて確認する。
5. 画質を変えない圧縮、フォント・画像の待機、同じ入力に対するPNG/PDFの一致、一時DOM・CSS・Object URLの後片付けを確認する。異なる方式を使う場合は用途上の理由を記録する。
6. 指摘は優先度、ファイル、再現条件、期待結果、検証結果、未確認事項を残す。APIテスト・静的検査だけをUI/PDFの実見確認の代わりにしない。

## 実装の棚卸し

| 優先 | 対象 | 現在の方式・差分 | 次の確認・修正 |
|---|---|---|---|
| 修正済み | 請求書住所・社印の参照 | `InvoiceSheet`と`PaginatedInvoiceSheet`のHTMLをブラウザ印刷。編集は会社APIの印影、プレビューは共通設定の印影を使っていた | 今回、両画面で同じ会社APIを使うよう修正。住所は文字として描画。通常・長文・特殊文字のPDFを各1ページで確認。実際の印影画像の読み込み待機は継続課題 |
| 1 | 請求書の自動改ページ | 45行の明細で4ページ。先頭に大きな余白があり、41行目でブラウザが再分割し、合計欄が2・3ページに重複 | `paginate.ts`のブロック計測と`InvoiceSheet`のtable/tfootの印刷規則を合わせる。手動改ページ・長文・最終行・合計欄1回を実PDFで検証する |
| 1 | 車両QRの単体・一括PDF | どちらもhtml2canvas→jsPDF。`PDF_EXPORT_OPTIONS`未使用、PNG格納の圧縮指定なし。単体scale=3／A6、一括scale=2／A4 | 共通の画質を変えない圧縮設定へ移行。フォント・QR画像の待機と失敗表示を揃え、9枚・10枚のページ境界を実ファイルで確認する |
| 2 | QRラベルの画像化 | 単体・一括でDOM計測を別実装。PNGボタンはQR本体、PDFボタンは車番入りラベルを出す | 用途の差は維持。共通のラベル描画・画像読み込み待機・後片付けを抽出し、文字位置とQR読取を確認する |
| 3 | 配達受託者控 `JukenCertificate` | html2canvasの直接importと独自の画像保存 | 多行住所、空欄、スマホでの保存・共有・失敗復帰を検証し、共通出力処理へ寄せられる部分を整理する |
| 4 | シフトメモ | DOM画像化後の補正済みPNGを`pngToPdf`に格納。固定の文字位置補正あり | 日別配車のフォント計測補正との重複を検証。既存補正に新補正を重ねない |
| 4 | 日別配車 | `captureDispatchImage`でDOM複製・一時CSS・フォント計測補正 | 共通化候補は準備と後片付け。シフトメモと生成前後の実画像を比較してから抽出する |
| 維持 | 正式シフト表 | 同じ描画ロジックをPNG/PDFで共有、PDF圧縮と日本語フォントのサブセット化あり | データ描画という用途上の違い。HTML画像化へ統一しない。長い氏名・車番・月跨ぎの回帰確認を続ける |

請求書のブラウザ印刷、シフト表のデータ描画、配車画面のDOM画像化はそれぞれ目的が異なる。一律に同じライブラリへ置き換えず、圧縮・準備・エラー表示・資源の後片付けと検証手順を揃える。

## 今回の確認記録

- 請求書・報告種別は実ページを隔離fixtureで操作。PC/768/390/320px、住所の改行・長文、取得エラー、保存失敗からの復帰を確認。請求書編集は既存仕様でスマホにPC利用案内を表示し、閲覧はA4幅を維持する。
- 請求書の通常・長文・特殊文字は各1ページ、45行は4ページ。新規一時プロファイルのheadless Chromeからlocalhostのみへ接続し、印刷CSSでPDF化。4ファイル計7ページを画像化して目視、明細1〜45の欠落なし、各PDF約278〜305KB。既存のログイン済みタブはPDF生成に使用していない。
- 報告種別の編集・保存失敗時の入力保持・再保存・削除・対象消失時の拒否を確認。経理・閲覧役では変更操作を表示しない。
- QR、受託者控、シフトメモ、日別配車はソース監査のみ。今回、それらの出力品質を検証済みとは扱わない。

## 追加で見つかったUIの課題

| 優先 | 対象・再現条件 | 現状と次の対応 |
|---|---|---|
| 1 | 請求書編集で閲覧役を選ぶ | 入力UIが表示され、保存時に拒否される。サーバーの権限は維持し、画面を閲覧用に切り替えるか編集不可の案内を出す |
| 1 | 請求書で自動保存を失敗させる | 入力は残るが再試行ボタンがない。再編集では保存できる。印刷前の保存が失敗しても印刷へ進むコードなので、保存結果と印刷開始の扱いを揃える |
| 2 | 会社設定・社印画像の取得待ち/失敗 | 共通設定の他社印影へ代替しないよう今回修正。印影が必要な帳票の出力前に、設定・画像の準備完了を扱うUIを整理する |
| 2 | 諸報告・勤怠の承認 | 諸報告UIの変更権限とAPI権限に差がある。勤怠は失敗時の再取得だけで利用者へのエラー表示がない。対象fixtureを追加して実操作を確認してから修正する（今回はソース確認のみ） |

報告種別のフォーム内の上下移動・チェック欄は共通部品への移行候補。操作を変更する回に`SortableList`・`CheckboxField`へ寄せ、今回の会社別データ分離には混ぜない。
