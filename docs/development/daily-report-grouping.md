# 日報の表示単位とメーター履歴

2026/10/17。実装・隔離プレビュー検証。本番未反映。

## 原因と修正

日報の保存単位はコース・便ごとだが、確認画面の表示と車両のメーター履歴も保存行ごとになっていた。C1/C2に同じ車両・メーターが保存されると、日報の車両・メーター・送信時刻が反復し、車両履歴の前行差分が同日に `63km` と `0km` の2行になる。

- 日報の未承認・すべて、PC・スマホを1人1日単位に統一。車両・同じメーター値・同じ表示時刻を共通表示にし、同じコースのC1/C2は1つのコース見出しの中に並べる。実績を合算した値で置き換えず、便別の実績・編集対象・混在する承認状態は残す。
- すべてタブの件数も1人1日単位。却下済みは「却下分」から `SmoothCollapse` で開く。現行の実績・共通メーター・承認状態へ混ぜない。保存・承認・却下のAPI単位は維持する。
- 編集対象をコース名と便番号で明示。PC表の操作欄から便別実績の横へ編集ボタンを移し、押す領域を44pxにする。狭いタブレット幅ではカードを使い、PC表は1024px以上。
- 車両のメーターログAPIは、自社で絞った日報のうち「同日・同じ本人・同じ車両ID・同じ値」だけを1件にする。却下分は従来どおり除外。別の値、別利用者、別日、別車両、車両未特定は潰さない。実際の0という読取値も欠測にしない。
- 日報の削除や履歴の書換えは行わない。車両履歴は日報から作るため、反映後は既存の過去分にも同じ重複除外が適用される。セッション・写真の原本記録は変更しない。
- 車両の表・グラフの差分表記を「前回との差」に揃え、日付を共通の日本語日付formatterで表示。異なる読取値を残すため、「前日比」という説明は使わない。

## 検証

- 関連6ファイル45テスト。63km/0kmになる入力の重複除外、異なる値/利用者/車両/日付/未特定車両の保持、本人IDでのグループ化、C1/C2編集先、却下履歴の開閉、閲覧権限、APIの自社スコープを確認。
- Web・preview型検査、tenant静的検査、差分の空白検査を実施。
- アプリ内ブラウザ1280/768/390/320pxで確認。C2だけの編集、保存失敗時の値の保持と再保存、全件の1人1日表示、却下分の開閉、異なる読取値/乗換え/長い名前/多件数、空/読み込み/取得エラー、管理者/経理/閲覧を操作した。車両履歴はPC/390/320pxの表とスマホのグラフで、63kmが1件で残ることを確認。意図して発生させた保存失敗のconsole.error以外に異常ログなし。
- 本番 `/admin/daily/page.tsx`・`ReportCards.tsx`・`EditReportModal.tsx`、`/admin/vehicles/page.tsx` をrunnerで直接再利用。独自画面を新設していない。
- プレビューは架空データ・メモリ内のみ。本番DB・認証・通知には接続しない。編集・承認の保存失敗は上部バーから試せ、入力を保持して再保存できる。実際のMobileアプリと、本番のシフト保存/日報送信/車両履歴との通し操作は未検証。

## 起動

`npm run preview:admin -- admin --port 3198`

- 日報: <http://127.0.0.1:3198/preview/admin/daily?scenario=multi-course&role=admin>
- 車両のメーター履歴: <http://127.0.0.1:3198/preview/admin/vehicles?scenario=meter-duplicates&role=admin> → 先頭車両の「メーターの詳細を見る」。同日に63kmと0kmを作る4件の架空入力を、3件の読取履歴にまとめる。
- 日報は通常、複数コース・C1/C2、別の読取値、途中の乗換え、シフト変更後、未紐付け、長い名前、多数、空、読み込み中、取得エラーと、管理者/経理/閲覧を切り替える。初期化・シナリオ切替・再読み込みで編集状態が戻る。

本番公開と先行するシフト連動migration・対象1件の補正は別途確認待ち。この表示修正のためのDBデータ変更・新しいmigrationは不要。
