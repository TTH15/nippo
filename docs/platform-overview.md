## 2. 横断する確定方針（全体を貫く判断）

1. **構成A**: クライアント（運営Web＋将来RN）は全て Next.js API 経由 → service-role → Supabase。**Supabase直結なし・RLS不使用**。テナント分離はAPI層で default-deny 一元化。理由＝セキュリティ＋RN化が「クライアント追加」で済む。
2. **Supabase PRO（本番）**: 理由はバックアップ＋Storage容量（機能でなく信頼性）。FREE実害＝バックアップ無/自動停止/容量。
3. **マルチテナント**: 内部キー=`org_id`(UUID不変)／参加=`join_code`(英数6・再生成可)／表示=旧company_code。既に「ソフトマルチテナント」が存在（JWTにcompanyCode）→ 完全化・厳格化。
4. **identity と membership の分離**: identity=人(顔/免許/氏名/生年月日/電話/Passkey/LINE、1人1つ)／membership=会社×役割×status(複数可)。複数アカウント問題が消える。既存driversをmembershipとして温存し`identities`を上に足す（既存driver_id参照は無改修）。
5. **認証**: ログイン=**Passkey**（Next.jsがRP）、電話=**SMS OTPで検証**（緊急連絡＋復旧）、**LINEは通知専用**。メアド/Google不要（電話＋KYC＋運営承認が復旧アンカー）。PIN廃止。
6. **2層承認**: 運営社→プラットフォーム承認(KYB・厳格・手動)／ドライバー→運営社承認(KYC・顔/免許は目視、eKYCなし)。
7. **通知**: **統合LINE既定**(Nippo公式1本、誤爆防止＝broadcast禁止・orgスコープ送信)／**アプリ内インボックスが真実**、LINE＋RN pushは**恒久並行**配信／org単位CMS／Nippo告知は別特権レーン。BYO-LINEは将来オプション。
8. **車両**: **1車両=1QR=vehicles.id**（業務開始/返却/貸与/将来も兼用、ラベルはorg画面DL）。グローバル一意＋owner_org_id＋vehicle_loansで会社間貸借（所有orgは状態フル開示、人のPIIは除く）。
9. **システムは記録者でゲートでない**: 車両利用はシフトで縛らず目的(稼働/移動/私用)を記録。稼働が主役、私用は事前申請/常時許可、整備は別入口。
10. **Storage**: 点検写真が最大の増加要因。**保存期間を各社設定→料金ティア化**＋自動削除＋端末圧縮、将来R2退避。
11. **コスト構造**: SaaS利用料(運営社→自社・エンタープライズ＋導入相談)／LINE統合分は自社負担(通知枠同梱)／SMS OTPは原価内包。会社数・写真・件数に比例の健全な構造。

## 6. リスク・注意点

- **スコープが大きい**（MVP→マルチテナントSaaS＋ネイティブ＋新機能多数）。順序管理が肝。一度に全部やらない。
- **マルチテナント移行が最リスクの基盤変更**。稼働中DBへの後付けは繊細 → 早く・段階的に・越境テスト必須。
- **法務/コンプラ**（PII・KYB・委託契約・個情法、免許/顔の保持）は**専門家レビュー前提**。元請け→下請け共有は第三者提供論点。
- **Storage増**（点検写真）はコスト要監視。保存期間ティア＋圧縮＋R2で抑制。
- **命名衝突注意**: 新 `identities`(KYC/人) と 既存 `driver_identities`(勤務区分slot) は別物。
- **アンカー顧客が使わない機能**（叩き台生成等）も他テナントには価値 → 安易に削らない。
